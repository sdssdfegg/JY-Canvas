# 静音 AI 画板 V11：AI 画板与电商换装能力升级实施方案

**方案版本：** V1.0  
**项目定位：** 在现有 JY-Canvas 项目基础上进行渐进式升级  
**执行方式：** AI 项目负责人负责源码审计、任务拆解、代码实现、测试和交付  
**当前阶段：** P0 源码审计与基线验证  
**重要约束：** 本方案只定义实施方向与验收要求。未经项目负责人确认，不得直接进入大规模代码修改。

---

# 一、项目决策

## 1.1 最终技术路线

采用：

**保留现有项目作为主产品 + 选择性借鉴开源项目 + 围绕电商换装进行专项改造。**

不采用以下路线：

1. 不推翻现有 JY-Canvas，从零开发一套新画板。
2. 不直接把其他开源画板整个替换进来。
3. 不因为某个开源项目的 Agent 能力更强，就重写现有前端、后端和数据存储体系。
4. 不把提升换装质量的任务简单归结为继续优化提示词。
5. 不在没有实际测试结果的情况下，同时接入大量图像模型、多个 Agent 和复杂自动化工作流。

现有项目已经具备前端、后端、本地运行、图像生成、批量任务、提示词及相关业务功能。应先确认哪些能力已经稳定，再围绕明确的问题进行局部升级。

## 1.2 为什么选择渐进式改造

当前真正需要解决的并不只是“画板功能不够多”，而是以下几个问题：

- 批量换装和蒙版换装的实际效果不理想。
- 即使使用 GPT 或 Gemini 等图像模型，服装细节、指定区域和其他区域的保持程度仍然难以控制。
- 单纯增加提示词，无法可靠解决模型本身的编辑能力、输入素材质量、区域约束和结果检查等问题。
- 需要支持围绕同一张图片连续修改，而不是每次都重新开始。
- 需要引入 Agent 和 Skill，让系统能够理解用户的编辑目标、执行任务并检查结果。
- 必须继续满足低配置、操作简单、本地易启动、运行流畅的要求。

因此，项目应优先形成一套稳定的图像编辑执行体系，再把这套能力逐步复用到批量换装和其他业务场景。

# 二、项目目标与不可突破的约束

## 2.1 产品目标

升级后的画板需要逐步具备以下能力。

### A. 电商服装换装能力

1. 支持模特图片与目标服装素材输入。
2. 支持单张换装。
3. 支持蒙版指定区域换装。
4. 支持批量换装。
5. 尽可能保持目标服装的颜色、图案、版型、领口、袖口、印花和其他可识别细节。
6. 尽可能保持未要求修改的区域。
7. 能够识别失败结果，并允许用户修改条件后重新生成。
8. 能够通过实际测试比较不同模型、输入素材和工作流的表现。

### B. 连续图像编辑能力

用户可以围绕同一张图片连续提出修改要求。

例如：

第一轮：
“把模特身上的衣服替换成我上传的这件 T 恤。”

第二轮：
“把 T 恤颜色调深一点，衣服上的印花保持不变。”

第三轮：
“模特姿势不变，把背景改成更适合电商店铺的室内场景。”

第四轮：
“背景再丰富一些，衣服、模特和构图不要变。”

系统应当知道：

- 用户正在修改哪张图片。
- 当前使用的是哪个版本。
- 前几轮分别修改了什么。
- 哪些区域允许修改。
- 哪些区域需要尽可能保持。
- 当前任务应当使用哪种图像编辑方式。
- 新结果与上一版本相比发生了什么变化。

注意：这些约束是系统的编辑目标，不意味着所有图像模型都能百分之百遵守。必须通过实际测试评估模型能力。

### C. AI 画板能力

逐步具备：

- 图片与素材管理。
- 图片版本管理。
- 基于当前图片的连续编辑。
- Agent 任务规划。
- Skill 调用。
- GPT、Gemini 等图像模型的统一调用入口。
- 任务执行状态展示。
- 失败处理与重新执行。
- 编辑历史查看与版本恢复。
- 为后续扩展批量任务保留统一执行入口。

## 2.2 必须保持的现有能力

在源码审计完成前，以下功能一律视为需要保护的现有资产：

- 现有用户数据。
- 现有提示词模板。
- 现有 API Key 与模型配置。
- 现有模型映射及调用逻辑。
- 现有批量生成和批量换装流程。
- 现有蒙版换装流程。
- 现有任务历史和预览能力。
- 现有本地持久化数据。
- 现有 Windows 启动方式。
- 现有并发控制、文件上传及临时文件清理逻辑。
- 现有已经验证通过的功能。

具体存储位置、调用入口及数据格式必须由 P0 阶段审计确认，不能凭经验猜测。

## 2.3 禁止事项

执行 AI 不得：

1. 未备份就批量修改或迁移用户数据。
2. 为了清理环境而删除用户配置、提示词、历史任务或本地素材。
3. 覆盖原始图片或已有结果图片。
4. 擅自清空或重置 API 配置。
5. 在没有兼容性评估的情况下替换现有框架。
6. 把大量业务逻辑直接写入 React 页面组件。
7. 在多个前端组件里重复实现模型 API 调用。
8. 把 Agent 理解成单纯的提示词拼接器。
9. 在没有基准测试的情况下宣称某个模型或算法一定能解决换装质量问题。
10. 一次性重写换装、画板、批量任务和存储体系。
11. 把需要高端显卡和大量本地模型文件的方案直接作为默认方案。
12. 未经授权上传用户的图片、提示词或其他数据到外部服务。

任何不可逆的数据迁移、配置变更或存储格式变更，都必须先提出方案并等待批准。

# 三、现有项目与开源项目的使用策略

## 3.1 主项目：JY-Canvas

现有 JY-Canvas 继续作为唯一主项目。

现有技术栈包含 React、Vite、Node.js 本地服务等组件，并提供 Windows 本地启动及现有业务功能。

执行 AI 首先要搞清楚现有架构，而不是先搭建一套新架构。

需要重点审计：

- 前端页面和组件结构。
- 模型调用的实际入口。
- 后端 API 路由。
- 批量任务与并发管理。
- 蒙版换装的实际执行链路。
- 提示词与 Skill 的存放和加载方式。
- 图片上传、临时文件及持久化机制。
- 任务历史的保存与恢复方式。
- 现有测试脚本及其实际覆盖范围。

## 3.2 开源参考一：Infinite Canvas

参考项目：

https://github.com/basketikun/infinite-canvas

重点研究：

- 无限画布与图片节点的组织方式。
- 围绕选中图片进行连续编辑的上下文设计。
- Canvas Agent 的任务组织方式。
- 通过 MCP 与外部 Agent 工具交互的方式。
- 图片资产和编辑历史的组织方式。
- GPT、Gemini 等图像模型的兼容处理。

使用原则：

**借鉴设计思想和经过验证的局部实现，不直接替换现有产品。**

其开发状态、数据兼容性、依赖以及具体代码许可，必须在决定复用代码前重新核实。

## 3.3 开源参考二：BeatDesign

参考项目：

https://github.com/BeatAPI/BeatDesign

重点研究：

- 本地优先的工作区设计。
- 图片资产管理。
- 本地 Agent 通信方式。
- MCP 接入方式。
- 项目素材与任务之间的关联。

不优先引入其视频时间线等当前业务不需要的复杂功能。

## 3.4 开源参考三：OpenTryOn

参考项目：

https://tryonlabs.github.io/opentryon/

重点研究：

- 现成虚拟试衣模型和工具链。
- 不同模型对服装细节、人体姿势和图像输入的要求。
- 预处理、推理和结果评估方式。
- 是否存在适合低配置本地环境的部署路径。
- 是否有可以通过 API 或独立服务接入现有项目的方案。

不得因为项目开源，就默认其中所有模型权重都允许商业使用。

必须分别核实代码、模型权重、训练数据及相关组件的许可证。

## 3.5 开源参考四：IDM-VTON

参考项目：

https://github.com/yisol/IDM-VTON

定位为研究和效果对照对象。

在没有解决商业许可、部署要求及模型效果验证之前，不得直接将其设定为正式产品的默认换装方案。

## 3.6 开源复用的判断标准

每个准备引入的项目或组件，必须先回答：

1. 它具体解决哪个现有问题？
2. 当前项目是否已经具备类似能力？
3. 引入它需要新增哪些依赖？
4. 是否增加本地内存、显存或 CPU 占用？
5. 是否增加 Windows 部署难度？
6. 是否需要额外模型文件或独立服务？
7. 是否会影响现有用户数据？
8. 许可证是否允许当前产品用途？
9. 能否独立测试、回滚和替换？
10. 直接参考架构是否已经足够，是否真的需要复制代码？

如果不能证明引入收益大于维护成本，就不引入。

# 四、目标架构

升级采用分层架构，避免将所有能力混合在页面组件、提示词和 API 调用中。

建议的逻辑分层如下：

用户界面
↓
任务意图识别与编辑状态管理
↓
Agent 任务规划
↓
Skill 能力调用
↓
图像编辑执行引擎
↓
模型适配层
↓
GPT / Gemini / 其他经批准的模型或服务

同时，任务执行引擎需要关联以下基础能力：

- 图片素材管理。
- 图片版本管理。
- 任务状态管理。
- 错误处理与重试。
- 运行日志。
- 配置管理。
- 结果验证。
- 本地持久化。

这是一种目标逻辑架构，不是要求立即新增这么多服务或模块。

具体是否需要独立文件、类、服务或数据库，应由 P0 源码审计后决定。

## 4.1 任务状态管理

图像编辑任务至少需要能够区分：

- 等待执行。
- 正在准备输入素材。
- 正在调用模型。
- 正在处理结果。
- 等待用户检查。
- 执行成功。
- 执行失败。
- 已取消。

现有系统如果已经有等效机制，应优先复用。

任务状态必须能够与对应图片、版本、使用模型和执行记录关联。

## 4.2 模型适配层

GPT、Gemini 和其他图像模型应通过统一的调用入口进行管理。

统一层负责：

- 输入格式转换。
- 模型参数映射。
- 图片和蒙版输入适配。
- 请求发送。
- 返回结果解析。
- 超时处理。
- 错误分类。
- 必要的重试。
- 模型能力与限制声明。

但不能假定所有模型都支持相同的图像编辑能力。

必须根据具体模型和 API 版本，核实以下能力是否可用：

- 文生图。
- 图生图。
- 多图输入。
- 参考图编辑。
- 蒙版或局部编辑。
- 连续多轮编辑。
- 输出尺寸和质量控制。

对于不支持某项能力的模型，系统应明确告知用户，或者采用经过验证的替代流程，而不是静默地把参数丢弃。

## 4.3 Agent 与 Skill 分层

必须明确区分三个概念。

**Agent：负责理解和规划。**

例如判断用户希望改变服装颜色、替换背景，还是重新进行一次完整换装，并确定哪些条件必须保持。

**Skill：负责定义可复用的业务能力和执行规则。**

例如换装任务准备、连续图像编辑、结果检查。

**执行引擎：负责真正执行操作。**

例如选择模型、准备图片、调用 API、处理结果、保存新版本。

不能只给模型加上一段“你是专业换装专家”的系统提示词，就认为已经完成 Agent 能力建设。

Agent 应当通过明确的输入、可执行的操作、结构化结果及错误处理来工作。

# 五、MVO：最小可验证版本

## 5.1 MVO 的目标

第一阶段不追求做成完整的智能画板，也不追求一次解决所有换装问题。

MVO 的目标是：

**先打通一条能够持续编辑、保存版本、追踪上下文、比较效果并进行验证的单图工作流。**

只有证明这条链路有效，才把它扩展到批量换装。

## 5.2 MVO 的完整用户流程

### 第一步：选择素材

用户选择：

- 一张模特图片。
- 一张目标服装图片。
- 需要时提供蒙版或编辑区域。
- 需要时填写补充要求。

系统识别任务类型，并检查输入素材是否满足当前执行路径的要求。

### 第二步：执行首次换装

系统根据任务类型、输入素材和模型能力，选择经过验证的执行路径。

执行完成后，展示结果。

首次结果不能覆盖原始图片。

### 第三步：连续修改

用户提出：

“衣服颜色再深一点，衣服图案保持不变。”

系统应当：

1. 识别当前正在编辑的图片。
2. 识别当前版本。
3. 结合上一轮任务记录理解修改目标。
4. 区分本轮允许修改的内容和需要保持的内容。
5. 判断当前模型是否适合执行该任务。
6. 生成修改任务。
7. 调用模型。
8. 保存新结果。
9. 将新结果与上一版本关联。

如果模型不支持可靠的局部编辑，应明确说明限制，而不是承诺完全不影响其他区域。

### 第四步：再次修改

用户继续提出：

“衣服保持不变，背景换成适合电商店铺的室内场景。”

系统应当继续使用当前图片版本和相关编辑上下文。

不应要求用户每次重新上传所有素材，也不应只根据最后一句话独立生成，导致前面已经确定的要求丢失。

### 第五步：检查与回退

用户可以：

- 查看当前版本。
- 查看上一版本。
- 比较修改前后的图片。
- 接受当前结果。
- 继续修改。
- 恢复到之前的版本。

所有操作都应保留原始图片和已有版本。

## 5.3 MVO 必须包含的四项能力

第一项：至少一条经过验证的 GPT 或 Gemini 图像编辑调用链路。

第二项：图片版本管理。

第三项：一个主 Agent 和三个可复用 Skill。

第四项：连续编辑、结果检查和版本恢复的最小闭环。

具体接入 GPT 还是 Gemini，应根据当前可用 API、图像编辑能力、费用、延迟和实测效果决定。

不能为了实现“双模型接入”而同时引入两套未经验证的复杂调用流程。

如果接入第二个模型成本很低、接口清晰且不影响稳定性，可以在 MVO 阶段一并完成；否则先打通一条可靠链路，再接入第二个模型。

# 六、Agent 与 Skill 的第一版设计

## 6.1 主 Agent：图像编辑任务 Agent

职责：

- 理解用户的编辑意图。
- 判断任务属于换装、局部修改、背景修改还是其他编辑。
- 识别当前图片及版本。
- 读取相关历史编辑记录。
- 识别用户明确要求保持不变的内容。
- 选择适当的 Skill。
- 根据实际模型能力决定执行路径。
- 调用执行引擎。
- 处理执行失败。
- 组织结果检查信息。
- 将执行结果返回用户。

Agent 不应自行修改 API Key、删除历史记录或覆盖原始文件。

Agent 也不应在没有用户授权的情况下，将不确定的编辑要求直接转化为不可逆操作。

## 6.2 Skill 一：电商服装换装

目标：规范服装替换任务的输入、执行和检查。

输入至少包括：

- 模特图片。
- 目标服装素材。
- 用户换装要求。
- 可选蒙版。
- 可选参考图。
- 当前任务可用的模型能力信息。

输出至少包括：

- 任务类型。
- 服装替换目标。
- 需要重点保持的服装特征。
- 需要尽可能保持的非目标区域。
- 适用的执行路径。
- 生成任务参数。
- 结果检查项目。

结果检查应关注：

- 是否成功替换服装。
- 服装颜色是否明显偏离参考。
- 主要图案、印花及文字是否发生明显变化。
- 领口、袖口、版型等关键细节是否明显错误。
- 人体结构是否出现明显异常。
- 背景或其他非目标区域是否发生非预期变化。

不能把“已经调用模型”当成“换装成功”。

## 6.3 Skill 二：连续图像编辑

目标：支持在已有结果上连续修改。

输入至少包括：

- 当前图片版本。
- 前序任务记录。
- 用户最新指令。
- 需要保持的条件。
- 允许修改的区域。
- 当前模型的编辑能力。

输出至少包括：

- 本轮编辑目标。
- 本轮修改内容。
- 需要保持的内容。
- 适用的执行方式。
- 执行参数。
- 新版本关联信息。

必须区分：

- 用户明确要求保持的条件。
- 系统根据上下文推断的条件。
- 模型实际上能够保证的能力。

如果用户的要求相互冲突，应优先向用户澄清，不应静默地选择一种解释。

## 6.4 Skill 三：结果检查与质量评估

目标：对生成结果进行结构化检查。

第一版可以采用简单、低成本的方式：

1. 保存原图和生成结果。
2. 展示前后对比。
3. 检查图像是否正常返回。
4. 检查结果尺寸、文件格式及可读性。
5. 对照本轮修改要求进行检查。
6. 将明显问题反馈给用户。
7. 允许用户选择重试、调整要求或接受结果。

如果后续使用视觉模型进行自动评估，必须先通过实际测试确认其判断能力。

第一版不应承诺自动发现所有服装细节问题，更不应未经验证就自动循环生成大量图片。

# 七、图片版本管理与上下文设计

这是 MVO 的核心基础能力之一。

## 7.1 版本关系

建议采用明确的版本关系：

原始图片
└── V1：首次换装
    ├── V2：调整服装颜色
    │   └── V3：继续调整局部细节
    └── V4：从 V1 分支修改背景

上述结构只是逻辑示意。

具体采用树状版本、父子版本或其他存储形式，应结合现有项目结构决定。

## 7.2 每个版本至少记录什么

建议每个版本记录：

- 唯一版本标识。
- 对应任务标识。
- 父版本标识。
- 输入素材引用。
- 生成结果路径或资源标识。
- 用户本轮指令。
- 本轮结构化编辑目标。
- 使用的模型和相关版本信息。
- 关键执行参数。
- 创建时间。
- 执行状态。
- 错误信息。
- 用户是否接受结果。

API Key 等敏感信息不得写入任务历史或普通日志。

如果现有数据结构已经能够保存部分信息，应优先扩展现有结构，避免重复建设。

## 7.3 多轮上下文规则

不能只保存一段越来越长的对话，再把全部内容无差别发送给图像模型。

系统应将上下文整理为结构化状态，至少包含：

- 当前编辑对象。
- 当前图片版本。
- 任务类型。
- 当前目标。
- 已确认的编辑要求。
- 明确要求保持的条件。
- 本轮允许修改的内容。
- 当前使用的参考素材。
- 近期执行结果。
- 已知限制和未解决的问题。

图像模型是否需要完整历史图片、上一版本、原始图和参考图，应由具体任务和模型能力决定。

对于模型不支持直接恢复编辑状态的情况，应使用适当的参考图和结构化约束重新构造输入，而不是假定模型拥有真正的跨轮记忆。

# 八、换装质量专项改造

换装效果是项目的重要业务指标，但不能只通过提示词来改善。

执行 AI 应先建立可重复的测试集，再根据测试结果确定改造方向。

## 8.1 建立换装基准测试集

第一版准备一组固定的测试素材，覆盖：

- 纯色 T 恤。
- 带有明显印花的 T 恤。
- 带文字或图案的服装。
- 不同颜色的服装。
- 不同人体姿势。
- 不同背景。
- 不同服装参考图质量。
- 不同程度的蒙版区域。
- 需要保持面部、头发、手部或背景的编辑任务。

测试集不必一开始就很大，但必须固定素材和测试要求，避免每次测试都换一组图片。

## 8.2 记录基准结果

每次测试至少记录：

- 测试编号。
- 原始输入图片。
- 目标服装图片。
- 编辑要求。
- 使用模型。
- 执行路径。
- 关键参数。
- 输出结果。
- 是否成功。
- 主要问题。
- 执行耗时。
- 失败原因。

同一任务尽可能使用相同素材和一致的评价标准比较不同方案。

## 8.3 优先检查的问题

### A. 输入素材问题

检查服装参考图是否清晰、是否存在遮挡、是否需要裁剪或预处理。

### B. 模型能力问题

确认当前模型是否真正支持所需的图像编辑、参考图约束或局部编辑能力。

### C. 执行链路问题

检查是否正确传入参考图、蒙版、提示词和相关参数。

### D. 区域保持问题

确认现有流程是要求模型自行保持非目标区域，还是存在能够实际限制修改范围的机制。

两者不能混为一谈。

### E. 结果验证问题

检查系统是否只判断 API 返回成功，却没有检查图片本身是否满足要求。

### F. 重试策略问题

确认失败后是否能够识别失败类型，并决定是否重试、调整参数、重新准备素材或请求用户补充信息。

## 8.4 蒙版换装的特别要求

必须先确认现有蒙版换装究竟如何执行。

审计内容包括：

- 蒙版的存储格式。
- 蒙版与原图的尺寸关系。
- 蒙版区域的含义。
- API 是否实际接收到蒙版。
- 模型是否支持当前蒙版用法。
- 是否存在尺寸、方向或坐标转换问题。
- 是否仅把蒙版绘制结果作为普通参考图传入。
- 输出结果是否经过额外合成或后处理。

不能因为界面上存在蒙版功能，就默认模型执行了真正的局部编辑。

如果现有路径无法可靠限制修改范围，应比较不同执行策略的效果和成本，再决定是否引入新的编辑机制。

# 九、开发阶段安排

采用逐阶段交付，不允许直接跳到全面重构。

## P0：源码审计与基线验证

**目标：搞清楚当前系统真正具备什么能力，以及问题出在哪里。**

执行内容：

1. 阅读现有源码维护文档和模块说明。
2. 建立前端、后端、模型调用、提示词、数据存储及批量任务的模块图。
3. 梳理批量换装和蒙版换装的完整执行链路。
4. 梳理 GPT、Gemini 或其他现有模型的调用情况。
5. 查明提示词、Skill 和执行逻辑之间的关系。
6. 查明图片、任务历史和用户配置的存储位置。
7. 检查连续编辑和版本管理是否已经存在。
8. 检查任务失败、超时、重试、取消和恢复能力。
9. 执行现有测试脚本。
10. 使用固定素材测试当前换装效果。
11. 整理最值得优先修复的问题。

交付物：

- 现有系统模块图。
- 模型调用流程图。
- 批量换装与蒙版换装流程图。
- 现有功能与目标功能对照表。
- 数据和配置保护清单。
- 当前测试基线。
- 已确认的问题清单。
- 尚待验证的问题清单。
- MVO 实施任务拆解。

**P0 阶段以调查、测试和文档为主。未经确认，不进行大规模代码修改。**

## P1：建立统一图像编辑执行入口

目标：为后续 Agent、Skill 和连续编辑提供稳定的底层能力。

执行内容：

1. 确认现有模型调用逻辑是否可以复用。
2. 设计或完善统一图像编辑接口。
3. 统一请求参数和结果结构。
4. 补齐必要的超时、错误处理和日志。
5. 明确不同模型的实际能力与限制。
6. 验证原有生成流程不受影响。

交付标准：

- 至少一条图像编辑路径可稳定执行。
- 失败原因可以被识别和记录。
- 不破坏原有功能。
- 原有 API 配置继续可用。
- 模型差异不会被错误地隐藏。

## P2：建立单图连续编辑与版本管理

目标：实现 MVO 的核心用户体验。

执行内容：

1. 确认或扩展图片版本的数据结构。
2. 将新生成结果保存为独立版本。
3. 保留原图和之前的版本。
4. 记录每一轮编辑要求及其执行信息。
5. 支持连续多轮编辑。
6. 支持前后版本比较。
7. 支持回退到已有版本。
8. 在界面上清楚展示当前编辑对象和版本。

交付标准：

用户可以在同一张图片上连续修改多次，并且系统能够追踪每一轮修改对应的版本。

刷新页面或重启应用后，已持久化的编辑历史仍然可用；具体恢复能力须以实际持久化方案和测试结果为准。

## P3：接入 Agent 与三个 Skill

目标：让画板能够理解和组织任务，而不只是把用户输入直接拼接成提示词。

执行内容：

1. 实现主图像编辑 Agent 的最小能力。
2. 接入电商服装换装 Skill。
3. 接入连续图像编辑 Skill。
4. 接入结果检查 Skill。
5. 为 Skill 定义明确的输入和输出。
6. 为失败任务定义处理方式。
7. 保证 Agent 通过受控的执行入口调用模型。
8. 对需要额外费用、外部上传或不可逆操作的行为设置必要的确认机制。

交付标准：

Agent 能够识别用户的编辑意图，选择适当的执行能力，并将结果关联到正确的图片版本。

## P4：把已验证的能力复用到批量换装

只有 P1—P3 的核心链路稳定后，才进入这一阶段。

执行内容：

1. 将单图编辑执行入口复用于批量任务。
2. 明确每张图片的任务状态。
3. 支持单张失败而其他任务继续处理。
4. 记录每张图片的输入、模型、结果和错误。
5. 评估任务中断后的恢复能力。
6. 在现有并发控制基础上优化吞吐量。
7. 避免一次失败导致整个批次的数据丢失。

交付标准：

- 批量任务不覆盖原始素材。
- 每张图片的结果和状态可以独立追踪。
- 单张任务失败不会无条件破坏整个批次。
- 并发量可控。
- 本地内存、CPU 和外部 API 消耗不会因引入 Agent 而无节制增长。

# 十、低配置、本地运行与性能要求

低配置、运行流畅、操作简单是项目的硬约束，而不是后续优化项。

## 10.1 本地运行

优先沿用现有 Windows 启动方式和本地服务架构。

新增能力不得无必要地要求用户安装：

- 大量额外开发工具。
- 多套独立运行环境。
- 本地大型图像模型。
- 复杂的数据库服务。
- 必须手动启动和维护的多个后台进程。

如果某项能力确实需要新增服务，应先证明它的收益，并提供尽可能简单的启动与故障排查方式。

## 10.2 任务执行

- 复用现有并发控制。
- 不让 Agent 无限制地并行调用模型。
- 不重复上传相同的图片素材。
- 不在内存中无限保留所有历史图片。
- 不默认对失败任务进行无限重试。
- 及时清理确认不再需要的临时文件。
- 不把重要的用户素材当作临时缓存处理。

## 10.3 用户体验

用户不需要理解 Agent、Skill、MCP 或模型适配层的技术细节。

界面应围绕用户的实际工作流程组织：

1. 选择图片。
2. 说明想修改什么。
3. 生成结果。
4. 检查结果。
5. 继续修改或恢复版本。

复杂能力可以由系统内部处理，不应要求用户手动配置大量技术参数。

---

# 十一、数据保护与回滚机制

这是所有阶段的前置要求。

## 11.1 修改前检查

执行任何可能影响现有功能或数据的代码修改前：

1. 确认当前分支和工作区状态。
2. 确认现有改动中是否包含用户尚未提交的工作。
3. 阅读相关模块维护说明。
4. 确认目标文件及其依赖关系。
5. 备份需要保护的用户数据和配置。
6. 明确本次修改的文件范围。
7. 记录修改前的测试结果。

不得直接覆盖用户已有的未提交改动。

## 11.2 数据与配置保护

- API Key 不得写入源码或普通日志。
- 不得将用户配置覆盖为示例配置。
- 不得将提示词模板重置为默认版本。
- 不得删除原有任务历史。
- 不得覆盖原始图片。
- 不得因为版本结构调整而丢失旧数据。
- 如果需要迁移数据，必须提供可验证的迁移和回滚方案。

## 11.3 代码变更策略

每个阶段应保持修改范围尽可能小。

推荐流程：

审计 → 提交实施计划 → 用户确认 → 创建安全回滚点 → 小范围修改 → 自动测试 → 实际运行验证 → 用户验收。

如果测试失败，应优先定位本次修改造成的问题，不应继续叠加大量新功能。

---

# 十二、测试与验收标准

所有功能都必须有可验证的验收条件。

## 12.1 基础回归测试

至少验证：

- 应用可以正常启动。
- 原有页面可以正常访问。
- 原有模型调用没有被意外破坏。
- 原有批量流程可以正常运行。
- 原有蒙版流程可以正常运行。
- API 配置仍然有效。
- 提示词模板仍然存在。
- 图片上传和结果预览正常。
- 历史任务和本地数据没有丢失。
- 原有启动方式仍然可用。

## 12.2 连续编辑测试

使用同一张图片完成至少三轮连续编辑：

第一轮：换装。

第二轮：调整服装颜色。

第三轮：修改背景，同时要求服装保持不变。

检查：

- 每一轮都生成独立版本。
- 每一轮都关联正确的父版本。
- 历史编辑要求没有串到其他图片。
- 刷新页面后，已保存的版本仍然可以查看。
- 可以回到上一版本。
- 失败时不会覆盖之前的成功结果。
- 模型不支持的约束不会被系统伪装成已保证。

## 12.3 换装质量测试

使用固定测试集，对比改造前后的结果。

建议采用五项核心指标：

| 指标 | 检查内容 |
|---|---|
| 服装一致性 | 颜色、图案、文字、版型及关键细节是否符合参考 |
| 区域保持 | 不需要修改的区域是否发生明显变化 |
| 任务完成度 | 是否完成用户指定的换装或编辑目标 |
| 结果可用性 | 是否存在明显人体结构错误、图像损坏或其他严重问题 |
| 执行效率 | 耗时、失败率、重试次数及资源消耗 |

每项可以使用统一的人工评分标准，例如 1—5 分，并记录实际问题。

如果后续引入自动评估模型，应先验证自动评分与人工判断的一致性。

不能只选择最好看的几张结果作为测试结论。

## 12.4 性能测试

在用户实际使用的目标电脑上记录：

- 启动耗时。
- 页面交互是否流畅。
- 单张任务耗时。
- 批量任务耗时。
- 任务并发情况。
- 内存占用。
- CPU 占用。
- 错误率。
- 失败重试次数。

具体性能目标应在 P0 阶段建立基线后确定。

## 12.5 交付要求

每个阶段完成后，执行 AI 必须提供：

1. 完成了什么。
2. 修改了哪些文件。
3. 为什么修改。
4. 修改前后有什么区别。
5. 运行了哪些测试。
6. 测试结果如何。
7. 哪些问题仍未解决。
8. 是否影响原有功能。
9. 是否需要用户执行额外操作。
10. 如何回滚本次修改。

不能只回复“已完成”“已优化”或“测试通过”，必须提供可核实的结果。

# 十四、给执行 AI 项目负责人的最终指令

你不是在从零开发一款 AI 画板，而是在现有 JY-Canvas 项目上进行有边界的能力升级。

你的首要任务不是增加代码量，而是查清楚现有系统为什么在换装、蒙版编辑和连续修改方面表现不理想，区分模型能力限制、调用链路问题、上下文管理缺失和结果验证不足。

你必须遵守以下原则：

1. 以现有源码为事实依据。
2. 优先复用已经稳定的模块。
3. 优先修复已经证实的问题。
4. 先建立可重复的测试基线，再讨论效果是否提升。
5. 不把提示词优化当成解决所有图像问题的唯一手段。
6. 不因为参考项目功能多，就整体替换现有产品。
7. 任何外部模型或开源组件都必须检查能力、部署成本和许可证。
8. 所有新增能力都要考虑低配置、Windows 本地运行和用户操作成本。
9. 不允许破坏现有用户数据、提示词模板和 API 配置。
10. 每个阶段都必须有明确的交付物和验收条件。
11. 如果实际源码与方案中的假设不一致，应先说明差异，再调整实施计划。
12. 不得在没有测试证据的情况下宣称问题已经解决。

**第一阶段只完成 P0 源码审计、基线测试和实施计划。完成后等待用户确认，再进入 P1。**

项目的最终目标不是做出一个看起来很智能的画板，而是建立一套用户真正用得起来、换装效果可以被验证、能够连续修改、失败可恢复、运行成本可控的电商 AI 图像工作流。
