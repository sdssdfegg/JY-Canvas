## 交付 1：真实链路问题定位报告

### 总根因：v2Planning 与 aiPlan 解耦（一切问题的源头）
- `detail-middleware.js:685`：`v2Planning = selectedSections === null`（只看是否空选板块）。
- `detail-middleware.js:664`：`aiPlan = options.aiPlan || null`（由调用方/AI 规划结果决定）。
- 两者**独立**：当"空板块默认规划路径"遇上"AI 规划失败/无 KEY"，得到 `v2Planning=true` 且 `aiPlan=null`。此时所有 V2 规划分支照常执行，但分支里读的 `aiPlan?.xxx` 全部为空 → 各层中间产物塌缩。

### 分层定位
| 层 | 应产出 | 实际（aiPlan=null 时） | 代码位置 |
|---|---|---|---|
| 商品理解 | `planning.facts[{claim,level}]`、产品结构化事实 | **顶层键缺失**；只有 `buildProductAnalysis` 的原始字段 | `detail-ai.js:283-290`（仅 schema 声明）；`detail-middleware.js:314-342` |
| 营销策划 | `consumerInsights`、`marketingStrategy.valueLadder` | **顶层键缺失**，且即使有 aiPlan 也只作审计、**从未进入提示词** | `detail-ai.js:231-239`；`detail-middleware.js:544-545`（fieldsPresent） |
| 详情叙事 | `planning.narrative`、`screenRoles` | **缺失**；标题退化为"第N屏"（`:703-704`） | `detail-middleware.js:200-224,703-704,743-749` |
| 视觉导演 | 每屏具体 composition | 退化为三段骨架串（无事实、无 DNA） | `skill-activation.js:342-366 buildScreenVisual`；`middleware:763-775` |
| 提示词编译 | 保留屏级具体任务 | 卖点轮流取原始资料或被兜底句替换；模块模板固定句进入每屏 | `middleware:753-761,815-818,852-856` |

### 三个确定性缺陷（已用真实链路复现）
1. **用户已确认事实被误拦截**：`skill-activation.js:24-25` 在 cleaning 行业把"窗帘/布艺沙发/贴身衣物…"列为禁词，注释说"仅在无对应 visible 事实时视为未确认扩展"，但 `checkSellingPointBoundary`（12-33行）**根本没检查是否有 visible 事实**——只要文本含"窗帘"就一律拦截。实测：`checkSellingPointBoundary("适用于羽绒服、羽绒被、窗帘、沙发、尼龙衣物","cleaning")` → `{allowed:false, hits:["窗帘"]}` → 整句卖点被换成空泛兜底（middleware:761）。**用户明确提供的适用范围被系统当成未确认内容丢弃。**
2. **兜底句双重污染**：761 行的兜底句经 `contentTask: sellingForPrompt.slice(0,60)`（766行）**同时进入【本屏卖点】和【画面任务】**，两处都是同一句空话。
3. **完整任务被机械拆屏**：`buildProductAnalysis:321-325` 把 `productFeature` 用 `parseList` 切成列表，`:753 selling = sellingList[index % len]` 按屏号轮流取一条——一个完整"使用方法"被拆成"挤压出清洁剂涂抹于衣物表面"（屏2）/"用清洁刷反复刷洗需要清洁部位"（屏3）/"用干净毛巾擦拭污渍后"（屏4）三个碎片屏，成分信息完全消失。

## 交付 4：人物与特殊姿势失效根因
- 用户选 `modelMode=use-model + modelPose=special + modelUsage=1`。
- `modelPolicy`（`middleware:371-382`）逐屏文案确实按 `index < min(usage,count)` 判断前1屏，但**只生成文案字串**。
- 人物任务信号 `deriveFigureTaskContextKeys`（`middleware:565-593`）**完全不读这三个参数**，只读 userInstruction 与本屏语义 → 用户未写人物词时 4/4 屏 inactive（实测）。
- 于是 `middleware:858-861` 强制输出"本屏无模特，禁止人体局部/手部"，`modelPolicy` 的 special 分支根本不被调用 → **"选了特殊姿势却被全面禁止手部"的矛盾**。
- 这是 2026-11-18 人物缺陷修复时刻意确立的边界（"不凭 modelMode 旧参数自动触发"）的副作用：防了误触发，但也让明确的 UI 选择失效。
- detail-studio 对照：`global-lock.js:37-45` 把 special 写进全局锁扩散所有屏，且 modelUsage 未传入 → "1屏"无逐屏效果（另一条链路的问题）。

## 交付 6：修改前后的验收标准
**修改前（现状基线，本轮实测）**：首屏卖点=空泛兜底；屏2-4=使用方法碎片；成分消失；画面任务四屏同骨架；人物 4/4 inactive。
**修改后验收（待实施后验证）**：
1. `checkSellingPointBoundary("…窗帘…","cleaning", visibleFacts含窗帘)` → allowed=true；无事实的扩展 → 仍 blocked（负向保留）。
2. 羽绒服案例：成分/适用范围/使用方法按任务分配到屏，无整句丢弃；无"围绕已确认…"兜底出现在卖点字段。
3. 使用方法作为一项完整任务组织，不再机械拆3屏（可合并或按真实步骤合理分屏）。
4. 仅第1屏人物 active；第2-4屏 inactive 且仍禁人物；特殊姿势仅影响第1屏措辞。
5. 各屏画面任务因内容任务不同而不同（非同一骨架）。
6. 四件套：修改差异 / 运行读取证据 / 真实链路触发测试 / 提示词污染测试；门禁与构建全绿；其他7项无回归。
