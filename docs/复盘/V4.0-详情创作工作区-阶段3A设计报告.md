4. **Agent / SKILL / 确定性程序的职责矩阵**，把事实分级、流程编排、重试/幂等/参数校验、最终提示词冻结明确分给「程序」。
5. **A / B / C 三种模式的能力调用流程图**，并附 C 路径调用图隔离证明（C 只 import `mode-c.js` + store，零 planner / skill / 质检依赖）。
6. **单网关 `postChatCompletion` 的上下文承载方案**：一次/多次调用划分、结构化 JSON 输出（`extractJsonObject`）、分段策略、失败降级、成本控制；不新增任何 Provider / baseUrl / apiKey / 网关。
7. **商品事实分级 / 用户选项结构化参数链 / 参考图三角色 / 逐屏上下文** 的完整链路与逐项验证方法（`option-effect-check` 负向对照门禁）。

## 3. 核心设计交付

### 3.1 Agent 角色与职责设计（七角色拆分/合并判断）

#### 3.1.1 落地映射：7 逻辑角色 → 5 类执行单元

| 逻辑角色 | 落地形态 | 是否独立模型调用 | 职责与输入输出 |
|---|---|---|---|
| 详情创作总控 Agent | **内部流程 / 控制器**（确定性状态机，**无模型调用**） | 否 | 任务理解 → 能力调度 → 流程管理 → 结果整合。输入：项目 `mode` + 当前 `PlanRun.stage`；输出：调度指令。仅做路由与编排，不产出创作内容。 |
| 商品分析 Agent | **规划批次①**（与电商策划合并为 1 次 `postChatCompletion`） | 共享 1 次 | 输入：商品事实原始资料 + 参考图元信息 + 行业策略包；输出：事实分级表、卖点、差异化、信息缺口。 |
| 电商策划 Agent | 同上批次①（同一次调用的结构化 JSON 两个分段） | 共享 1 次 | 输入：分析结果 + 行业决策逻辑；输出：目标消费者、痛点、购买动机、购买疑虑、转化逻辑。 |
| 详情导演 Agent | **规划批次②**（与视觉设计合并为 1 次调用） | 共享 1 次 | 输入：策划 + 屏数 + 平台节奏；输出：整套叙事结构、屏顺序、信息节奏、`ScreenSpec[]`（含每屏标题/目标/文案/构图意图）。 |
| 视觉设计 Agent | 同上批次②（同一次调用的结构化 JSON 另一分段） | 共享 1 次 | 输入：导演分屏 + 整体视觉 DNA + 行业视觉锚点；输出：每屏视觉任务、构图、场景、色彩、视觉层级、差异化指令。 |
| 生图 Prompt Agent | **确定性编译器 + 可选 LLM 微调**（**主路径零模型调用**） | 默认否 | 输入：`ScreenSpec[]` + 全局锁 + 选项 + 逐屏上下文；输出：每屏 `frozenPrompt` 文本。组装逻辑全部确定性（借鉴 `detail-middleware.js:531-550` 的 `text[]` 拼接范式）；可选对单屏提示词做 1 次 LLM 润色（批内）。 |
| 质量审查 Agent | **独立 1 次调用**（与规划批次解耦） | 是（独立） | 输入：规划产物 + `frozenPrompt` + 选项溯源 `appliedOptions`；输出：六类问题清单 + 一次定向修正建议。独立以避免「自审自话」。 |

**合计调用上限（A/B 模式）：批次① 1 次 + 批次② 1 次 + 质检 1 次 = 3 次**（若启用单屏提示词微调，可并入批次②的结构化数组，不新增独立调用）。**C 模式：0 次规划调用 + 0 次策划/质检调用**，仅确定性分屏（`mode-c.js:splitIntoScreens`）。

#### 3.1.2 合并/拆分判断的四维理由

| 维度 | 合并（分析+策划 / 导演+视觉）的理由 | 质检独立 / 编译器确定性的理由 |
|---|---|---|
| **质量** | 事实与购买逻辑高度耦合：把「卖点」与「痛点/购买动机」放进同一次调用，模型能在同一上下文里对齐，避免串行交接丢上下文、出现「卖点成立但购买逻辑不成立」的断裂（V200 §3.7 审查项之一）。导演与视觉同理——叙事顺序与每屏构图必须同框决策。 | 质检若与规划同一次调用，模型会倾向于给自己打高分（确认偏误）。独立调用 + 独立系统提示（「你是独立审查者，不得为上游辩护」）才能产出可信问题清单。提示词编译若交给 LLM，会破坏「frozenPrompt == 实际发送提示词」的架构保证（V200 §6 红线）。 |
| **稳定性** | 调用从 7 降到 3，失败面与重试面同步下降；每次调用都能拿到更完整的上下文，减少半成品交接导致的二次补偿调用。 | 确定性编译器无 LLM 抖动，生成提示词 100% 可复现；质检独立后即使规划失败也可单独降级（见 §3.5 降级）。 |
| **可维护性** | 每个批次对应一个清晰职责的 Skill 文件 + 一份结构化 JSON schema，回归测试直接对 schema 断言。 | `frozenPrompt` 编译逻辑是可单测的纯函数（与 `mode-c.js` 同口径）；质检规则分「确定性规则（程序）」+「主观判断（LLM）」两层，各改各的。 |
| **成本** | 3 次调用 vs 7 次 ≈ 节省 57% 的文本 token 与首字节延迟；批次内结构化数组共享系统提示，不重复计费。 | 确定性编译零成本；质检仅 1 次，且只在生成前发生一次。 |

**避免无意义多 Agent 串行**：商品分析的输出（事实分级表）直接作为策划与导演的输入字段，不经「总控 Agent 再总结」；总控只做状态路由，不生产内容。不引入 LangGraph / 独立 Agent 运行时（阶段 0 §1.5 已排除 MxPage `lib/agent/*`）。

### 3.2 SKILL 目录与能力设计 + 行业加载机制

#### 3.2.1 分层 SKILL 包目录（`prompts/detail-studio/`，结构化 JS 常量而非超长提示词）

```
  industry/
    index.js                 getIndustryStrategy(text) 加载器 + 覆盖优先级
    apparel.js  beauty.js  cleaning.js(新增)  home.js  food.js  electronics.js  generic.js

    index.js  taobao.js  douyin.js  xiaohongshu.js ...（平台节奏/规则/比例/文案规则）
  quality/
    checklist.js             六类检查的「确定性规则」部分（程序执行）
    qc-prompt.js             六类检查的「主观判断」系统提示（LLM 执行）
  prompts/
    analyze-strategy.js      批次①系统提示 + 结构化 JSON schema
    director-visual.js       批次②系统提示 + 结构化 JSON schema

```

**SKILL 沉淀标准**（参考 ecommerce-skills `skill.md` 边界写法 + product-shots「Hub is a router, not a generator」）：每个 SKILL/策略包 = 方法论 + 工作流程 + 结构化输出规范 + 行业知识/参考资料 + 优秀与失败案例 + 质量检查清单 + 必要的确定性脚本/规则。**明确区分模型判断 vs 程序严格执行**：
- **模型判断**（交给 LLM，固定检查项、固定输出 schema）：事实推断是否过度、购买逻辑是否成立、叙事节奏、视觉差异化、单屏文案可读性、质检主观项。
- **程序严格执行**（Node 代码，不容 LLM 现编，参考 ecommerce-skills `batch.mjs`/`check_listing.py`）：事实分级枚举、unconfirmed 禁 publish、选项→锁的映射、参数 schema 校验、结构校验、`frozenPrompt` 冻结只读、appliedOptions 溯源、`option-effect` 负向对照。

| # | 候选 SKILL | 是否独立 | 落地与边界 |

#### 3.2.3 行业策略包加载与覆盖机制（V200 §4.5）

- **现状底座**：`prompts/server/detail-skills.js` 已有 `INDUSTRY_SKILLS` 11 类（apparel/beauty/food/home/electronics/motherBaby/pet/jewelry/sports/generic + …）。目标 6 类映射：服装=apparel、美妆护肤=beauty、家居=home、食品=food、3C=electronics；**清洁日化为新增**（映射关键词：清洁/洗护/去污/除菌/家居清洁/纸品）。
- **策略包结构**（体现不同决策逻辑/内容规划/视觉表达/事实与宣传边界，而非替换行业词汇）：
  ```js
  cleaning = {
    id: "cleaning", name: "清洁日化",
    decisionLogic: "理性+信任驱动：安全/成分/认证/使用场景优先，避免夸大功效",
    contentPlan: ["首屏功效场景","核心成分/原理","使用场景","安全与认证","信任背书","收尾转化"],
    visualExpression: ["干净明亮","水感/泡沫质感","真实使用场景","不过度美白"],
    productFacts: ["成分","净含量","适用表面/材质","认证(如有的真实认证)"],
    promoBoundaries: ["不虚构除菌率/认证","不暗示医疗疗效","不改包装规格文字"]
  }
  ```
- **加载与覆盖优先级**：`getIndustryStrategy(text)` → 文本匹配 `keywords` → 命中最具体包；**generic 为兜底**。覆盖语义：策略包只覆盖「决策逻辑/内容规划/视觉表达/事实边界」四字段，**不覆盖**基座 `BASE_SKILL`（商品真实性锁、全局一致性）与平台规则。六类不要求一次做满——先交付 `generic` + `apparel` + `cleaning`（三类商品测试覆盖），其余留 3B 后续批次增量填充。
- **禁搬项**：product-shots `scripts/generate.py` 的 `OMNIMAAS_API_KEY`/自建网关（阶段 0 §1.5 排除）；ecommerce-skills `providers.mjs` 的厂商模型 ID（排除）。只搬结构化文本字段表，保留 MIT LICENSE 声明，不搬 gallery 图片/logo/品牌名。

| 职责 | 承担方 | 执行方式 | 依据 |

| 叙事/分屏规划 | SKILL（批次②模型判断） | LLM 结构化输出 | §3.1 |
| 单屏视觉/构图 | SKILL（批次②模型判断） | LLM 结构化输出 | §3.1 |
| 生图提示词编译 | **程序（确定性）** | `prompt-compiler.js` 纯函数 | §3.2.1/§6 红线 |
| 流程编排 / 路由 | **程序（控制器）** | 状态机，无模型调用 | §3.1 |
| 重试 / 幂等 / 租约 | **程序** | 借 MxPage `requestOnce`/`claimRunLease` 改写为 Express+JSON（阶段 4） | 阶段 0 §3.4/§4.2 |
| 参数校验（schema） | **程序** | `ProjectConfig` schema 校验 | §3.6 |
| 结构校验（屏数/字段） | **程序** | `extractJsonObject` + schema.parse | §3.5 |
| 最终提示词冻结 | **程序（只读）** | `frozenPrompt` 仅用户确认后写入，生成只读 | V200 §6 / 模式 C 四边界 |
| 选项溯源 `appliedOptions` | **程序** | 编译期记录，质检核对 | §3.6 |
| 质量审查（六类） | 程序（确定性规则）+ SKILL（主观判断） | `checklist.js` + `qc-prompt.js` | §3.7 |

**铁律**：确定性操作（任务状态、重试、幂等、参数校验、结构校验、提示词冻结、溯源）**必须由程序承担，不得塞进长提示词**——与 ecommerce-skills「这些是确定性动作，不该每次让模型现编」同口径。

### 3.4 A / B / C 三种模式的能力调用流程

#### 3.4.1 模式 A（专业引导策划）
- 入口：`mode-a/GuidedIntakePanel.jsx`（阶段 2 骨架，不 import planner）。
- 流程：4 阶段主动澄清（借 product-shots `STAGE_1_TASK_SKELETON → STAGE_4_STYLE_BRAND`，`completeness>0.8` 停、`max_rounds 5`）→ 商品分析 → 策划 → 分屏。
- 专业判断体现：**主动发现信息缺口**并引导完善；不一次性抛出所有问题（用 `<suggestion><label><prompt>` chips，一次只问一个维度）；不过度追问已知信息；用行业策略包驱动「该问什么」而非单纯收集表单。

#### 3.4.2 模式 B（Agent 协同策划）
- 入口：`mode-b/AssistedIntakePanel.jsx`（骨架）。
- 流程：理解 `userIntentRaw` → 找缺失 → 补购买逻辑 → 优化叙事 → 规划分屏。
- 边界：**`userIntentRaw` 永久只读**，每次 AI 产出存 `rawIntent` 与 `assistPatch` + `diff`；AI 建议作为独立补丁，用户逐条采纳；**不覆盖原文、不经解释推翻用户创意**（改动必须展示 diff 由用户确认）。

#### 3.4.3 模式 C（完整提示词直通）—— 调用图隔离证明
- 入口：`mode-c/DirectPromptPanel.jsx` + `server/features/detail-studio/intake/mode-c.js`。
- 调用图（依赖集合）：`direct` handler **仅 import** `mode-c.js`（确定性纯函数：`tidyPrompt`/`computePromptDiff`/`splitIntoScreens`/`parseModeCTidy`）+ `project-store.js`（落库）。**零 import**：`planner/`、`prompts/detail-studio/**`、`quality/**`、任何 SKILL、`postChatCompletion`。
- 行为：只识别分屏边界、切分独立生成任务；`rawPrompt` 落库后只读，`tidyVersion` 可选默认关，`frozenPrompt` 仅用户确认后写入，生成只读 `frozenPrompt`。**不调用任何策划/质检/改写节点**。
- **隔离强制门禁**：新增 `mode-c-purity-check.mjs`（须注册 `run-all.mjs`），断言 `intake/mode-c.js` 与 C 路由文件不出现 `planner`/`skill`/`quality`/`postChatCompletion` 引用；与 V199 阶段 2 已落地的 `mode-c.js` 零 planner import 同口径。V200 要求「设计文档里必须有一张调用图或依赖表证明 C 路径不经过任何策划/质检/改写节点」——上表即该证明。

#### 3.4.4 三模式统一收口
A/B 经规划批次产出 `ScreenSpec[]` → `prompt-compiler` 编译 `frozenPrompt` → 用户确认冻结 → 生成只读 `frozenPrompt`。C 直接由用户原文冻结。三模式在「冻结→生成」之后汇合，生成模块**对任何模式都只读 `frozenPrompt`**。

### 3.5 现有模型 API 与上下文承载

- **单网关复用**：`server/core/ai-chat-shared.js:151 postChatCompletion({baseUrl, apiKey, body, signal})` → `${baseUrl}/chat/completions`，KEY 经 `resolveApiKey`、`modelName(input,{fields,fallback})` 适配（阶段 2 已把 `textModel` 进 `body.model`）。**不新增任何 Provider / baseUrl / apiKey / 网关**（V200 §6 / 阶段 0 §1.5）。
- **一次/多次调用划分**：A/B 模式 3 次（批次①、批次②、质检），每次调用只承载一个职责边界的上下文，避免单调用上下文膨胀；C 模式 0 次。
- **结构化 JSON 输出**：沿用 `extractJsonObject(text, label)` 抽取；每批次定义 `requiredGroupFields` / `requiredPromptFields`（借鉴 `BASE_SKILL.outputJsonFormat`），异常时抛带 label 的错误文案（不统一文案，因要弹给用户）。上游不支持 `response_format/json_object` 时，`shouldRetryWithoutJsonFormat` 剥约束重试一次（`:73`）。
- **上下文窗口与分段策略**：批次①上下文 = 商品资料 + 参考图元信息（不含像素，用 `fileMeta`）+ 行业策略包；批次②上下文 = 批次①结论 + 屏数 + 平台节奏 + 整体视觉 DNA；质检上下文 = 前述全部 + `frozenPrompt` + `appliedOptions`。**逐屏提示词不单独发起调用**，而是批次②结构化数组里的 `ScreenSpec[]` 元素（单调用内完成多屏规划），确定性编译器再据此拼每屏 `frozenPrompt`，天然规避逐屏调用爆炸。
- **失败与降级**：规划调用失败 → 回退「本地规则兜底」（借鉴 `detail-middleware.js:152 mergeAiAnalysis` 的 `aiError → local-rule` 分支，用 `INDUSTRY_SKILLS` 默认卖点/视觉锚点），不阻断用户；`shouldRetryWithoutImages` 在上游不支持多模态时剥图重试（`:61`）。质检失败不阻断生成，仅给出问题清单交用户。
- **成本控制**：3 次调用上限 + 确定性编译零成本 + 批次内共享系统提示；不引入第二套计费体系。

### 3.6 商品事实、用户选项、参考图与创作上下文传递

#### 3.6.1 商品事实分级
四级：`user`（用户明确提供）/ `visible`（商品图可见可合理推断）/ `inferred`（合理推断、需标注）/ `unconfirmed`（待用户确认，**禁止擅自编造**）。程序强制：`unconfirmed` 不得 `publish`，功效/参数/认证/材料/性能未确认为 `unconfirmed` 时不得包装成事实（呼应 V200 §3.6 与阶段 0 §3.6 质检）。

### 3.7 质量审查与定向修正机制

- **六类检查**：① 事实错误/编造（unconfirmed 禁 publish、禁功效/认证/参数虚构）；② 消费者逻辑不成立；③ 策划缺购买价值/内容重复/顺序不合理；④ 视觉模板化/不统一/信息密度异常；⑤ Prompt 不可执行或冲突（缺身份锚/未继承 visualDNA/未继承全局选项/单屏专属缺失/约束冲突）；⑥ 用户参数未生效（appliedOptions 传递链完整性）。
- **执行分层**：④⑤⑥ 中的确定性项由 `quality/checklist.js` 程序执行；①② 主观项由 `quality/qc-prompt.js` 独立 LLM 调用执行（固定检查项，避免自由发挥）。
- **定向修正 + 再审查**：针对实际问题给**修改建议**（不是只打分）；程序/LLM 产出一次定向修正 → 重新编译 `frozenPrompt` → 再审查一次。**仍不合格即明确列出问题交用户，禁止无限自动修正**（与任务书 §十二、V200 §3.7 一致）。修正上限 = 1 次（门禁/常量 `MAX_AUTO_FIX = 1` 强制）。
- 审查发生在**正式生成图片之前**；生成只读 `frozenPrompt`，审查结论不回写提示词。
