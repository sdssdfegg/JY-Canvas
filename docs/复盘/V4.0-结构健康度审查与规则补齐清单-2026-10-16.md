但有两颗定时炸弹，都跟"后续持续开发"直接相关：

其余都是可排队的小债，没有一条是"必须马上停工重做"。

## 2. 问题清单（按"后期会不会越来越多麻烦"排序）

### P0-1　状态未分层：文件已拆，大脑还是一个

**证据**：211 个 `useState`；`outfit-workflow.jsx` 57 个、`main.jsx` 28 个；`App()` 组件体约 1708 行、`OutfitWorkflow` 组件体约 1200 行；`OutfitWorkbench` 39 个 props；全仓 `useCallback` 只有 7 处。

**为什么后期会炸**：
- P6 已经证明"把代码搬走"能降行数，但**状态还在原地**。下一步加任何功能（比如新的批量模式、新的画布工具），仍然只能往这两个组件里加 state + handler。
- 57 个 state 的组件里，改一个字段的影响面无法静态推断 —— 这正是 P6 期间连续踩 TDZ、漏传 ctx 字段的根因（每次都是"跑起来才发现"）。
- `useCallback` 几乎为零，加上没有 memo 策略，画布/批量这类重交互场景会随着功能增加越来越卡，而且**卡顿不会出现门禁红灯**。

**建议动作（分阶段，不要一次做完）**：
1. **先立纪律（成本≈0）**：新增 state 一律进板块自持 hook（`useXxxState`），禁止再往 `main.jsx` / `outfit-workflow.jsx` 加第 58 / 29 个 `useState`。可用门禁：单文件 `useState` 数超阈值（如 30）判红。
2. **再引状态容器（成本中）**：上 `zustand`（1 个依赖、无 Provider 改造）或 Context+Reducer，按板块拆 store：`canvasStore` / `outfitStore` / `settingsStore`。跨板块通信走显式事件，不走 props。
3. **最后补记忆化（成本低）**：给 92 个 props 的 `OutfitWorkbench`、`main-top-bar`、`main-canvas-board` 加 `React.memo`，热路径 handler 加 `useCallback`。

> 提醒：这一步是**另一量级的重构**，不要在功能开发高峰期启动。建议先做完下面的 P0-2（门禁），再开工。

### P0-2　规则没有全部变成门禁（用户诉求的核心）

现在 AGENTS.md 里的纪律，只有一部分有自动兜底：

| 规则 | 有门禁？ | 实测 |
| --- | --- | --- |
| 文档不写死本机绝对路径 | ✅ `docs-path-check` | 有效 |
| 基线/文档漂移 | ✅ `frontend-duplication-check` 等 | 有效（本次加文件立刻判红，很灵敏） |
| 不在组件里散写 `fetch` | ❌ | **5 处违规**（`canvas-generation-handlers.js:388`、`detail-state.js:285`、`outfit-task.js:215/832` 等） |
| 跨 feature 依赖方向 | ❌ | 24 组横向依赖，只有 cycle-scan 保"无环"，没有"允许/禁止"白名单 |
| 死代码清理 | ❌ | 12 处真死导出，无人发现 |
| 单文件/单函数体量 | ❌ | 已有 578 行函数、2283 行文件，无阈值告警 |
| bundle 体积 | ❌ | 最大 chunk `feat-outfit` 261 kB（gzip 82 kB），无预算 |
| 代码格式统一 | ❌ | 无 Prettier / `.editorconfig` / `.gitattributes`，本次提交就出现了 LF→CRLF 警告 |

**建议动作（成本低、收益高，建议优先做）**——新增 5 个门禁脚本，全部纯源码扫描，跑得飞快：

1. `api-layering-check.mjs`：除 `src/api/**` 外禁止 `fetch("/api/...")`（`fetch(dataUrl)` 这类非后端调用加白名单）。先把现存 5 处要么迁进 `src/api/`、要么进白名单并注明理由。
2. `dead-export-check.mjs`：导出符号跨文件无人 import 且本文件内无使用 → 判红（先跑一次把现存 12 处写进基线，之后新增即失败）。
3. `complexity-ratchet.mjs`：**只报不拦**，输出 TOP 榜（单文件 useState 数 / 单函数行数 / 组件 props 数 / 文件行数），并写基线，下次比基线变差就提示。
4. `bundle-budget-check.mjs`：build 后解析 chunk 体积，超预算（如单 chunk > 300 kB）判红。
5. `dep-direction-check.mjs`：features 之间依赖走白名单（`features/*` 可依赖 `shared/`、`api/`、`lib/`；跨 feature 只允许已登记的组，新增组必须显式加白名单并写理由）。

### P1-1　持久化数据没有 schema 版本化

**证据**：`localStorage` / `indexedDB` 散落在 9 个文件（`detail-state.js`、`outfit-task.js`、`outfit-panels.jsx`、`storage-store.js`、`json-storage.js`、`image-split.js`、`prompt-library.js`、`image-editor-helpers.js`、`outfit-workflow.jsx`）；只有 `storage-store.js` 有 `HISTORY_DB_VERSION = 1`、画板有 `EDITOR_BRUSH_DEFAULTS_VERSION = 2`，**大部分没有版本号**。

**后期后果**：改一次数据结构，老用户打开就是白屏或错位，而且这类 bug **本地复现不了**（你的数据是新的）。这是续开发中最容易吃大亏的一条。

**建议动作**：立规范——每个持久化 store 必须有 `version` 字段 + `migrate(from, to, data)` 函数，读数据时版本不匹配就迁移或降级。加一个 `persistence-schema-check.mjs` 扫所有 `localStorage.setItem` / IDB 写入点，要求 key 已知的 store 都登记版本（先基线后棘轮）。

### P1-2　没有单元测试，也没有类型

**证据**：dev 依赖里没有 vitest/jest；41 个 verify 脚本本质是"业务语义端到端快照"（很棒，但跑一次 30 秒起步、且依赖真实流程）；`src/shared/` 25 个文件是**纯逻辑**，改了没有快速回归网。全仓 JS/JSX，无 TS、无 JSDoc 类型检查。

**为什么现在就要管**：P6 连续出现"build 全绿但运行白屏"的 TDZ、以及"钩内解构了但父没传字段"（运行期 undefined）——这两类正是类型系统/单测能拦住的。体量再翻倍，这类事故频率会跟着涨。

**建议动作（渐进，别硬转 TS）**：
1. 先给 `src/shared/**` 加 vitest 单测（1 个 dev 依赖），把 25 个纯函数模块的边界钉死。立刻见效。
2. 类型走渐进路线：先开 `checkJs` + JSDoc（0 迁移成本），再对新增模块用 `.ts`。不建议现在全量 TS 化 —— 3 万行 JS 一次性转换的收益/风险比不划算。

### P2-1　门禁本身在本机跑不通（可信度风险）

**证据**：`lint-ratchet-check` 依赖 `spawnSync`，在本机恒 EBUSY，实际靠 `scripts/dev/lint-ratchet-mirror.mjs` 人工替代；`check-launcher` 剩 5 项判环境。

**风险**：一旦"某道门禁在本机跑不起来"变成常态，人会习惯性跳过 → 门禁形同虚设。建议单开一张单，把恒失败的脚本改成不 spawn 的等价实现（或明确标记"仅 CI 生效"并写进 AGENTS.md）。

### P2-2　仓库卫生

- 24 个本地分支全部已合入 main，可批量清理（保留 tag/commit 即可）。
- `server/skill-baselines/**` 18608 行历史快照已被 lint 忽略，但仍占仓库、拖慢全仓扫描；建议整体挪到 `archive/`。
- `src/local-edit-mask.js` / `src/models.js` 两个 1 行转发壳：src 内 0 引用（只有 skill-baselines 引用）。要么删、要么在文件头写明"仅历史快照引用，勿用"。
- `docs/` 根目录平铺 12 个 md（与 `规划/`、`设计/`、`复盘/` 等子目录并存），归类略漂移，建议归入对应子目录。

## 3. 建议立刻写进 AGENTS.md 的 8 条硬规则

（现有 AGENTS.md 纪律保留，以下为补充；每条都要配一个门禁，否则不写）

1. **状态归属**：新增 state 必须进板块自持 hook/store，禁止往 `main.jsx`、`outfit-workflow.jsx`、`outfit-panels.jsx` 追加。→ `complexity-ratchet`
2. **API 分层**：所有后端请求走 `src/api/**`，组件与 feature 层禁止 `fetch("/api/...")`。→ `api-layering-check`
3. **依赖方向**：`features/*` 只能依赖 `shared/`、`api/`、`lib/`；跨 feature 依赖必须进白名单并写明理由。→ `dep-direction-check`
4. **无死代码**：新增导出必须有消费方；清理存量时同步刷新死代码基线。→ `dead-export-check`
5. **体量红线**：单文件 ≤ 800 行、单函数 ≤ 150 行、单组件 props ≤ 20；超线需在任务单写明理由。→ `complexity-ratchet`
6. **持久化必须带版本**：任何写入 localStorage/IndexedDB 的结构都要有 `version` + `migrate`。→ `persistence-schema-check`
7. **体积预算**：单 chunk > 300 kB 或总包 > 1.5 MB 需说明理由。→ `bundle-budget-check`
8. **门禁可用性**：任何门禁脚本若在本机恒失败，必须在 24h 内修好或标记"仅 CI"，不允许长期靠"镜像脚本/人工替代"绕过。→ 单开维护单

## 4. 建议的排产（供统筹参考，ROI 从高到低）

| 序 | 事项 | 成本 | 收益 |
| --- | --- | --- | --- |
| 1 | 5 个工程门禁（api 分层 / 死代码 / 复杂度棘轮 / 体积预算 / 依赖方向） | 低（纯扫描，每个约 100 行脚本） | **把"规则"变成"自动拦"**，长期收益最大 |
| 2 | 修现存 5 处散写 fetch + 12 处死导出 | 低 | 立即让新门禁可绿着上线 |
| 3 | `src/shared/**` 加 vitest 单测（先覆盖 25 个纯函数模块） | 中 | 纯逻辑改动从此有回归网 |
| 4 | 持久化 schema 版本化 + 门禁 | 中 | 避免"改结构炸老用户" |
| 5 | 状态分层（zustand / Context+Reducer 分板块） | **高** | 唯一能解 P0-1 的动作，但要在功能空窗期做 |
| 6 | `freezeIntentIntoTask`（578 行）与 `outfit-panels.jsx`（2283 行）二次拆分 | 中 | 降冲突面，属 P6 的自然延续 |
| 7 | 仓库卫生（分支/快照归档/转发壳/docs 归类） | 低 | 清爽，减少误判 |

## 5. 不建议现在做的事

- **不要立刻全量 TypeScript 化**：3 万行 JS 一次性转，风险远大于收益。走 "shared 层先 JSDoc/checkJs + vitest" 的渐进路线。
- **不要在功能开发高峰启动状态分层**：这是另一量级重构，建议先做完第 1–4 项（把网织好）再动。
- **不要为了行数继续拆文件**：P6 已经把行数降到合理区间，再拆下去只是把状态换个地方塞。真正的杠杆在状态分层，不在文件行数。
