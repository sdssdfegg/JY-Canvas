## 6. 遇到分叉 / 与设计文档不符之处

**有 3 处，均已实测核实并处置，无需统筹裁决：**

1. **`sharedConstrainCropRect` 不是真实导出名**（与设计单 §3.2 ⑨ 表述略有出入，但结论一致）。
   实测 `src/shared/local-edit-geometry.js:89` 导出的是 `constrainCropRect`；两巨石各以
   `constrainCropRect as sharedConstrainCropRect` 引入。设计单说「⑨ 约束函数不同源不实，同为别名」——**结论正确**，
   但实现时必须写成 `import { constrainCropRect as sharedConstrainCropRect }`。
   ⚠ 教训：**ESLint 不校验 import 名是否存在于目标模块**，照抄别名时 ESLint 全绿、**只有 vite/rollup build 会拦**。
   本单阶段 B 首次跑就因此 build 失败，已修。

2. **`fallbackToItem` 是真分叉，不是假分叉**（设计单 §8.1 #4 列为"待确认"，现实测坐实）。
   `cropLocalEditFile(imageItem, cropRect, suffix = "local_edit", { fallbackToItem = false } = {})`（geometry:434），
   440 行 `resolveLocalEditBaseFile(item) || (fallbackToItem ? item : null)`。
   outfit 原本**省略**第四参 ⇒ 有效值 = **false**；main 显式传 **true** ⇒ 两者不同。
   处置：工厂入参 `fallbackToItem`，main 传 `true`、**outfit 显式传 `false`**。
   为什么不沿用"省略"：省略虽数值等价，但会让工厂体的参数化形同虚设，并给后续读者造成"两侧无差异"的误导 —— 违反 §6 原则。

3. **`onImageLoad` 可以搬**（停手条件 #7 未触发）。
   设计单担心 main 19 行嵌套三元 vs outfit 11 行扁平无法用「同体+入参」表达；实测可行 ——
   统一体 + 入参 `lockRatioForLoad` + `defaultCropRect`，main 传 `ratioLocked` + `defaultQuickLocalEditCrop`、
   outfit 传 `true` + `defaultLocalEditCrop`。对照组对 main 的 `lockRatioForLoad=true/false` **两个分支**均验证与 BASE 一致，
   证明没有被统一成 outfit 的恒 true。

**与设计文档不符：无。** 其余（函数清单、区域边界、参数化方案）与设计单 §4/§5 完全一致。
