## 一、阶段目标与「框架优先」编排原则（设计交付概述）

Owner 明确本阶段价值排序：**框架与契约 > 内容质量调优 > UI / 视觉细节**。五批之内先做扎实可单测、可回归的框架主体，能力插件后置。

| 优先级 | 批次 | 性质 |
|---|---|---|
| **P0 框架主体** | B1 规划底座 → B2 导演分屏 → B3 提示词编译与冻结 | 事实分级、结构化 schema、选项参数链、逐屏上下文、`frozenPrompt` 编译与冻结；纯函数可单测，是「展示提示词 == 实际生成提示词」的架构保证 |
| P1 能力插件 | B4 质量审查 | 六类检查 + 一次定向修正 + 再审查（`MAX_AUTO_FIX=1`），框架稳后再挂 |
| P2 增量内容 | B5 行业策略包 | 先 `generic` / `apparel` / `cleaning` 三包跑通机制，其余行业留后续增量，不一次做满 6 类 |

**三类商品测试是验证框架是否通用的手段，不是调提示词大赛**（清洁日化 / 服装 / 食品或 3C，覆盖不同购买决策逻辑）。不出图、不比美观，验的是同一套框架在不同品类下是否都能产出合规、不套模板、参数生效的结构化结果。

**明确不做**（防止范围漂移）：批量生成与任务队列（阶段 4）、单屏版本管理与连续编辑（阶段 5）、长图预览与导出（阶段 6）、任何全局视觉系统 / 主题研究、旧详情模块改造、模型选择与渠道配置扩展（阶段 2 已定稿）。

**核心设计约束（全部守纪）**：单网关 `postChatCompletion` 承载、八文件禁改清单零改动、`src/main.jsx` 零改动、KEY 只在设置页填一次（前端不出现任何 KEY 输入）、不引入第二套 Provider / API Key / 网关、项目数据落 `data/detail-studio/` 不进 `seed/manifest.json`、CSS 零 hex、新增 verify 必须注册 `run-all.mjs` 且按基线棘轮（R6）上线。

- 事实分级四类（`user` / `visible` / `inferred` / `unconfirmed`）唯一真相源 = 3A 报告 §3.6.1；程序强制 `unconfirmed` 不得 `publish`，敏感字段（功效 / 参数 / 认证 / 材料 / 性能）未确认为 `unconfirmed` 不得当事实。

- A 模式引导：按 `completeness > 0.8` 停止追问；B 模式保留用户原始意图字段，AI 补强不得静默改写。

**交付落点**：

- `prompts/detail-studio/core/option-trace.js`（选项 → 约束影响溯源）

**实测结论（✅ 机器可验）**：批次① 1 次调用返回结构化 JSON；`appliedOptions` 完整；事实分级四类可枚举；`normalizeAnalyzeResult` 双重兜底剔除 `unconfirmed` 当事实。前端 API 薄封装按纪律等有真实消费方后再加，规避 `dead-export-check` / `size-ratchet` 双红。

## 四、B3 提示词编译与冻结交付（框架主体 · 红线所在）

**设计要点**（3A §3.3 / §3.5，MxPage `never compile over user edits` 口径）：
- `prompt-compiler.js` 为**确定性纯函数**（照 `detail-middleware.js:531-550` 的 `text[]` 拼接范式），主路径零模型调用。
- 用户确认后写 `frozenPrompt`；**生成端只读它**，用户看到的提示词 == 实际发送提示词，后台不得再经任何 Skill / Agent 改写。
- 模式 C 四份边界不变：`rawPrompt` 永久只读、`tidyVersion` 可选默认关、`diff` 可核对、`frozenPrompt` 仅确认后写。

**交付落点**：
- `prompts/detail-studio/core/prompt-compiler.js`（确定性编译，零模型调用）
- `prompts/detail-studio/core/option-trace.js`（记录每个选项影响了哪句约束）
- `scripts/verify/frozen-prompt-parity-check.mjs`（字节一致断言）+ `mode-c-purity-check.mjs`（C 隔离）

**实测结论（✅ 机器可验）**：`frozenPrompt` 与生成请求体 `prompt` **字节一致**（用户改什么就生成什么，后台零改写；冻结端点服务端重编译落库，展示 == 实际 == 落库同源）。C 路径 purity 门禁绿：`mode-c-purity-check.mjs` 断言 `intake/mode-c.js` 与 C 路由零 `planner` / `skill` / `quality` / `postChatCompletion` 引用，四份边界不因新增能力变化。

## 五、B4 质量审查交付

**设计要点**（3A §3.7）：
- `quality/checklist.js`（确定性规则）+ `quality/qc-prompt.js`（LLM 主观），六类：商品事实 / 购买逻辑 / 内容完整性 / 视觉设计 / 提示词 / 用户选项。
- 独立 1 次调用，`MAX_AUTO_FIX=1`：**一次定向修正 + 再审查**封顶，仍不合格就明确告知用户、交回人工（`needsHuman`），禁止无限循环。

**交付落点**：
- `server/features/detail-studio/quality/checklist.js` + `qc-prompt.js`
- `scripts/verify/qc-ceiling-check.mjs`（上限常量生效断言）

**实测结论（✅ 机器可验）**：`qc-ceiling-check.mjs` 5/5 全绿；`MAX_AUTO_FIX=1` 生效，review + re-review 合计 ≤2 次；定向修正只发生一次、不无限循环；仍不合格明确交回人工，绝不触发第三次调用。

## 八、三类商品测试设计（框架通用性验证）

**目的**：验证同一套框架在不同购买决策逻辑下都能产出合规、不套模板、参数生效的结构化结果，不出图、不比美观。

| 品类 | 购买决策逻辑侧重 | 框架验证点 | 真机覆盖 |
|---|---|---|---|
| 清洁日化 | 功效 / 成分 / 使用场景 | 命中 `cleaning` 包（专属词，不误判家居）；事实边界禁功效夸大 | 🔴 真机完整链路（分析→策划→分屏→冻结→质检）交 Owner 实机覆盖 |
| 服装 | 版型 / 面料 / 穿搭场景 | 命中 `apparel` 包；8 屏内容规划 + 柔和四面光视觉 | 🔴 同上 |
| 食品或 3C | 口味 / 参数 / 信任状 | 命中 `generic` 兜底或后续增量包；决策逻辑驱动屏结构 | 🔴 同上 |

**测试设计原则**：
- 屏数 / 顺序 / 构图由品类与内容驱动，固定 10 屏结构不得出现；相邻屏构图须轮换。
- 参数生效须对关键选项做**负向对照**（切换 → `frozenPrompt` 约束变化；塞违法内容 → 判红）。
- 不套模板的判定需对比三类商品的屏结构差异，确认无统一模板残留。
