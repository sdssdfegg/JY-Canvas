## 5. §4 重复常量的看法（**待统筹裁决**）

```
src/features/outfit/outfit-panels.jsx:76    export const CHANNEL_UPLOAD_MAX_SIDE = 3072;   // 批量侧
src/features/upload/reference-upload.js:217 export const CHANNEL_UPLOAD_MAX_SIDE = 3072;   // 快捷侧
```

**我的判断：是同一笔债，倾向合并，但需要先确认一个产品问题。**

支持合并的证据：
- 名字带着 **CHANNEL**（上游渠道限制）⇒ 语义上就是"同一个渠道约束"，本该只有一个值
- 当前**值完全相同**（3072），且用法一致（都是 `Math.min(1, MAX_SIDE / max(w,h))` 算缩放）
- 疑为 RF-081/082 把批量侧搬进 features 时，快捷侧复制了一份而非 import

合并要注意的点（执行单提到的 `maxSide` 默认值）：
- `outfit-panels.jsx:365` 有 `export function outputSizeForRatio(ratio, maxSide = CHANNEL_UPLOAD_MAX_SIDE)`
  —— 它是**默认参数**，合并后从 shared import 即可，语义不变
- `outfit-top.js:11` 从 `outfit-panels.jsx` import 这个常量 ⇒ 合并后要改 import 源（跨目录重定基）

**唯一需要产品确认的问题**：批量生成与快捷生成的上传上限**未来是否会独立演进**
（比如不同渠道/不同模型给不同上限）？
- 若**永远一致** ⇒ 合并，抽到 shared，零风险
- 若**可能独立** ⇒ 保持两份，但建议改名区分（如 `OUTFIT_UPLOAD_MAX_SIDE` / `QUICK_UPLOAD_MAX_SIDE`），
  现在的"同名不同源"是最糟的状态：看着像同一个，改一个不影响另一个

本单**未合并**（遵守硬约束），只按 §4 让断言同时覆盖两份。
