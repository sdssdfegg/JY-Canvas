## 〇、总体判断（先看这个）

工程质量在同类项目里属于**偏高**水平：分层清晰（core/routes/features）、错误语义分层做得非常细（image-error-policy）、有完整的门禁与基线体系、注释把"历史事故原因"写在了代码里。本次审计**没有发现会导致日常使用崩溃的语法/逻辑 bug**，问题集中在三类：

1. **可信边界被功能设计突破**（SSRF 面、CSRF 面、内存上限缺失）—— 这是最需要优先处理的；
2. **并发状态机缺少序列化**（队列头阻塞、history.json 丢失更新、即发即忘的后台任务）；
3. **依赖补丁滞后**（multer / proxy-addr 有已知高危/严重 advisory，修复成本极低）。

## 一、安全（4 条）

### 🔴 S1. `/api/connection-test` 是无限制 SSRF + API Key 外传原语

- **位置**：`server/routes/system.routes.js:112-190`
- **问题**：客户端传 `baseUrl`，服务端直接 `fetch({baseUrl}/models` 并带上 `Authorization: Bearer <用户KEY>`。**没有任何主机白名单**——而同项目的图片代理（`parseProxyTarget`）是有的（`isSafeRemoteImageUrl` 挡内网/非 https），渠道层也有 `LOCKED_CHANNEL_API_BASE_URLS`。这里两者都没用。
- **后果**：
  1. 可探测内网（`127.0.0.1:*`、`192.168.x.x`、`169.254.169.254` 云元数据、公司内网服务），响应里的 status + latencyMs 是一个不错的 SSRF 判研 oracle；
  2. **用户的 API Key 会被发到攻击者指定的主机**。UI 上"连接测试"本来就允许填自定义中转站地址，用户从中转站卖家处拿来的地址一旦是恶意的（或被中间人篡改的配置分享），KEY 直接外泄；
  3. 错误文案只脱敏了 `sk-xxx` 和 `Bearer xxx` 两种形态，其他 KEY 格式会随 message 回显。
- **缓解现状**（所以没评为"必炸"）：服务端绑死 `127.0.0.1`（`app-bootstrap.js:100`），且 express.json 只解析 `application/json`，跨站表单无法驱动这个端点。真实利用需要用户主动填恶意地址，或前端被注入。
- **修复方案**：把 baseUrl 限制在已有白名单内；确实需要支持自定义地址时，至少挡内网/环回：

```js
// server/routes/system.routes.js（connection-test 入口处）
import { isLockedChannelBaseUrl } from "../channel-config.js";
import { isSafeRemoteImageUrl } from "../../src/shared/image-hosts.js";

const baseUrl = requestedBaseUrl || fallbackBaseUrl;
// 方案 A（推荐，最严）：只允许已登记的渠道地址
if (!isLockedChannelBaseUrl(baseUrl)) {
  return res.status(400).json({ ok: false, status: 0, message: "请求地址不在已登记的渠道列表内", latencyMs: 0 });
}
// 方案 B（需要保留自定义地址时）：复用图片代理同一份内网/协议判定
if (!isSafeRemoteImageUrl(baseUrl)) {
  return res.status(400).json({ ok: false, status: 0, message: "请求地址不允许访问本地或内网", latencyMs: 0 });
}
```

同时把脱敏正则升级为通用形态：`raw.replace(/[A-Za-z0-9_-]{24,}/g, "***")` 之外，对 `sk-`、`Bearer`、`key`、`token` 片段统一替换（现在只有前两个）。

### 🟡 S2. multipart 端点可被跨站表单直接触发；全站缺少 Host / Origin 校验

- **位置**：`server/app.js`（中间件装配层，无任何 CSRF/Host 防护）
- **问题**：`multipart/form-data` 的 POST 属于浏览器"简单请求"，**不受 CORS 预检保护**。`/api/images`、`/api/generate-outfit`、`/api/save-processed-image`、`/api/cache-result-image` 都能被恶意网页里的自动提交表单直接打到 `http://127.0.0.1:8787`。JSON 端点（express.json 只认 `application/json`）对此免疫，但 multipart 这条缝是实的。
- **后果**：① 触发本地上传解析（对应下方 S3 的 multer 漏洞面）；② `/api/image-proxy?url=...` 是 GET，可被 `<img src=...>` 直接打（对应 M1 的内存消耗）；③ DNS rebinding 场景下浏览器会被诱导把 127.0.0.1 当合法源通信。当前这些端点大多靠"没有 API Key 就 400"兜底，但 `/api/image-proxy`、`/api/storage/reveal`、`/api/client-diagnostic-event` 不需要 KEY。
- **修复方案**：加一个全局 Host 白名单中间件（拼在 `app.use(express.json())` 之后），一行成本挡掉 rebinding + 跨站表单：

```js
// server/app.js
app.use((req, res, next) => {
  const host = String(req.headers.host || "").toLowerCase();
  const allowed = new Set([`127.0.0.1:${PORT}`, `localhost:${PORT}`, `[::1]:${PORT}`]);
  if (!allowed.has(host)) {
    return res.status(421).json({ ok: false, message: "非法请求源" });
  }
  next();
});
```

> 注意：这会让"用 IP 访问内网部署"失效——目前服务端本来就绑死 127.0.0.1，IP 访问不可达，所以无回归。若将来真要支持局域网访问，必须同时补 Token 鉴权，不能只开绑定。

### 🔴 S3. 依赖漏洞：multer（高危，直接依赖）+ proxy-addr（严重，express 传递依赖）

- **位置**：`package.json` / `node_modules`（`npm audit` 实测：10 个漏洞 = 4 moderate + 5 high + **1 critical**）
- **问题**：运行时相关的两个：
  - `multer@2.2.0`（声明 `^2.0.2`）——advisory 覆盖 `<=2.3.0`，**高危**。而 multer 解析的正是本应用最主要的输入面（上传文件），且如上所述可被跨站表单触达；
  - `proxy-addr@2.0.7`（express 4.22.2 传递）——**critical**。本应用未启用 `trust proxy`，实际影响有限，但修复成本是零。
  - 其余高危（undici / nanoid / brace-expansion / source-map-js）都在 vite/esbuild 开发工具链，随 `npm audit fix` 一起处理即可。
- **修复方案**：

```bash
npm install multer@^2.4.0
# proxy-addr 是传递依赖，用 overrides 钉住（express ^4.22.2 的 range 允许 2.0.8）
```
```jsonc
// package.json
"overrides": { "proxy-addr": "^2.0.8" }
```
升级后跑一遍现有上传相关门禁（`scripts/verify/` 下有 upload 系列断言）。

### 🟡 S3b. `/api/image-proxy` 无响应体大小上限（GET 可被 `<img>` 触达的内存消耗面）

- **位置**：`server/core/image-proxy.js:109-156`（Range 下载）、`185-223`（流式代理）
- **问题**：`firstRange.total` 取自上游 `Content-Range` 头，**没有任何总量校验**，`Buffer.concat(chunks, total)` 会按上游声明的大小分配。流式分支同样无上限转发。主机白名单只挡"非 https + 内网"，挡不住"公网恶意大文件"。
- **后果**：恶意网页 `<img src="http://127.0.0.1:8787/api/image-proxy?url=https://evil.com/10gb">` 可让本地服务持续下载并缓冲大文件 → 内存上涨、带宽占用；批量触发即 OOM。
- **修复方案**：下载前校验总量、下载中累加校验：

```js
// image-proxy.js downloadExternalImageWithRanges 内
const MAX_PROXY_IMAGE_BYTES = 64 * 1024 * 1024; // 与 OUTFIT 上传上限对齐
if (!Number.isFinite(firstRange.total) || firstRange.total <= 0
    || firstRange.total > MAX_PROXY_IMAGE_BYTES) {
  throw new Error("range_download_too_large");
}
// while 循环内每次 push 后：
if (chunks.reduce((n, c) => n + c.length, 0) > MAX_PROXY_IMAGE_BYTES) {
  throw new Error("range_download_too_large");
}
```
流式分支给 `res` 加计数，超限 `destroy()`。

## 二、稳定性 & 异常（4 条）

### 🟡 T1. `history.json` 并发写=丢失更新，且非原子写

- **位置**：`server/core/history-store.js:278-285`（`writeHistoryResults` 全量重写）、`348-364`（`appendHistoryResults` 先读后写，无锁）
- **问题**：两条链路都会并发触发——`persistGeneratedItemsInBackground` 是**每个请求各起一条**即发即忘的后台任务（`setTimeout(..., 0)`），快捷生成 + 批量换装 + 两个标签页同时收图时，两个 `appendHistoryResults` 会在 `await readHistoryResults()` 处交错：都读到同一快照、都全量写回 → **后写者把先写者的新条目静默吞掉**。另外 `writeFile` 直写目标文件，进程崩溃/断电（本用户的机器就是断电自动启动场景）会留下半个 JSON。
- **后果**：历史记录无声丢失（用户视角："我生成的图莫名其妙少了几张"）；断电后 history.json 损坏（已有备份+扫描恢复机制兜底，值得肯定，但恢复出来的是无提示词的 recovered 条目）。
- **修复方案**：① 写入串行化（项目里已有现成模式——`asset-persist.js` 的 `withSaveFilenameLock`，照抄即可）；② 原子写（临时文件 + rename）：

```js
// history-store.js
let historyWriteLock = Promise.resolve();
export function withHistoryWriteLock(task) {
  const previous = historyWriteLock;
  let release = () => {};
  historyWriteLock = new Promise((r) => { release = r; });
  return (async () => { await previous; try { return await task(); } finally { release(); } })();
}
export async function writeHistoryResults(results, options = {}) {
  return withHistoryWriteLock(async () => {
    const normalized = /* ...原逻辑... */;
    await mkdir(dataDir, { recursive: true });
    const tmp = `${historyFile}.${process.pid}.tmp`;
    await writeFile(tmp, JSON.stringify(normalized, null, 2), "utf8");
    await rename(tmp, historyFile); // 原子替换，断电最坏丢一次写而非半个文件
    if (normalized.length > 0 || options.replaceBackup) {
      await writeFile(historyBackupFile, JSON.stringify(normalized, null, 2), "utf8");
    }
  });
}
```

顺手把 `appendHistoryResults` 整体包进 `withHistoryWriteLock`。另外建议给历史上限（如保留最近 2000 条），现在每次追加都是全量读写，条目过万后单次写盘就是几 MB。

### 🟡 T2. 出图队列头部阻塞（head-of-line blocking）

- **位置**：`server/core/image-concurrency.js:15-23`
- **问题**：`drainImageQueue` 只看 `imageRequestQueue[0]`：队头是 weight=3 的请求、当前 active=3、上限 5 时，`3+3>5` 放不进去，**后面 weight=1 的请求明明有空位（3+1≤5）也只能干等**。批量场景（n=3/4 与 n=1 混合）会放大这个排队时延。
- **修复方案**：改为扫描队列中第一个"放得下"的条目（保持同权重间 FIFO）：

```js
function drainImageQueue() {
  let progressed = true;
  while (progressed && imageRequestQueue.length > 0) {
    progressed = false;
    for (let i = 0; i < imageRequestQueue.length; i += 1) {
      const item = imageRequestQueue[i];
      if (activeImageRequestCount + item.weight <= IMAGE_CONCURRENCY_LIMIT) {
        imageRequestQueue.splice(i, 1);
        item.grant();
        progressed = true;
        break;
      }
    }
  }
}
```

### 🟡 T3. 排队期间客户端断开 → 请求仍会完整跑完（含计费与上游转发）

- **位置**：`server/routes/images.routes.js` / `outfit.routes.js` 主链路（全程没有 `req.aborted` / `res.writableEnded` 检查）；`generation-trace.js` 只记录了 aborted 日志
- **问题**：客户端在并发队列里等不及关掉页面，服务端随后照常：prepare 计费 → 转发上游（真实扣费）→ 下载归档 → 后台落盘。即发即忘的 `finalizeBillingInBackground`（setTimeout 0）在进程退出时同样丢账。
- **修复方案**（三选一或组合）：
  1. `acquireImageSlot` 接受 `AbortSignal`，排队期间 abort 直接移除队列项；
  2. 在 `acquireImageSlot` 返回后、`prepareImageBillingForRequest` 之前加 `if (req.aborted || res.writableEnded) return;`（顺手 `removeUploadedFiles`）；
  3. 给 `finalizeBillingInBackground` 的 pending 集合在 `process.on("SIGINT"/"beforeExit")` 里做一次 flush——桌面应用被用户随手关掉是常态，丢账=对账噩梦。

### 🟡 T4. `pickDirectory` 的 PowerShell 子进程无超时，HTTP 请求可永久挂起

- **位置**：`server/core/directory-picker.js:31-86`
- **问题**：`spawn("powershell.exe", ...)` 后 promise 只在 `close` 时 resolve/reject。对话框卡住、powershell 启动异常（开发机上 PowerShell 本身就不可用）、或用户永远不选目录 → 这个 HTTP 请求永远不返回，前端一直转圈。`openDirectory` 用 `explorer.exe` + 数组参数，没有注入面，这点是对的。
- **修复方案**：加 120s 看门狗，超时 `child.kill()` 并 reject：

```js
const watchdog = setTimeout(() => { child.kill(); reject(new Error("目录选择器超时")); }, 120_000);
child.on("close", () => { clearTimeout(watchdog); /* ...原逻辑... */ });
child.on("error", (e) => { clearTimeout(watchdog); reject(e); });
```

## 三、性能（3 条）

### 🟡 P1. 单请求内存峰值过高：100mb JSON + 96mb 内存存储 + base64 重复副本

- **位置**：`server/app.js:47`（`express.json({ limit: "100mb" })`）、`server/core/uploads.js`（`largeImageUpload` 96MB 内存存储、`upload` 25MB×16 内存存储）、`server/core/image-channel-candidates.js:52-59`（`prepareJsonImageUrlsForChannel` 把文件 buffer 再转成 base64 data URL，体积 +33%）
- **问题**：JSON 大字段（香蕉 Pro 的 referenceDataUrl 就是 1536 长边 JPEG 的 data URL）+ multer 内存缓冲 + base64 副本三重叠。乘以并发上限 5，理论峰值 1GB+。用户机器从 64GB 到 8GB 都有，低配机器上批量 + 快捷生成同时跑会 OOM（Node 默认堆约 4GB，但 Buffer 是堆外，RSS 先炸）。
- **修复方案**：① JSON limit 降到实际需要（32mb 足够覆盖现有最大合法请求体）；② `upload`（内存存储那份）改磁盘存储——`imageForwardUpload` 已经是磁盘 + `ensureFileBuffer` 按需读回的成熟模式，直接复用；③ `prepareJsonImageUrlsForChannel` 里转换完及时释放原 buffer 引用（或在磁盘存储下用 `openAsBlob(file.path)` 流式转 base64，项目里 `appendUploadFile` 已有这个写法）。

### 🟡 P2. 每次出图请求写 5~10 次日志，且每次先 stat 再 append

- **位置**：`server/core/generation-logger.js:39-51`（`writeGenerationLog`：mkdir + stat + appendFile + appendTaskTextLog 内部再 mkdir + appendFile）
- **问题**：`/api/images` 一次请求打点 6~8 次，每次 2~4 个 fs 调用。单用户场景无感；接口一旦变快（本地缓存命中路径几百毫秒），日志 I/O 占比会变得可观。磁盘满时 stat/append 失败走 catch，不会炸，值得肯定。
- **修复方案**：同请求内的阶段日志在内存里聚合，响应结束时一次 append（或接一个简单的可写流 + 定时 flush）；`rotateLogFileIfNeeded` 的 stat 结果缓存几秒。

### 🟡 P3. 视频生成端点没有并发槽位

- **位置**：`server/routes/videos.routes.js:69`（`/api/videos/generations` 无 `acquireImageSlot`）
- **问题**：图片侧有 5 并发槽 + 权重排队，视频侧每个请求握一个最长 2 分钟的 fetch，纯靠前端自觉串行。用户连点/多标签页就会同时打 N 个上游视频任务，每个都是真金白银。
- **修复方案**：视频单独一个小槽位池（如 limit=1~2，env 可调），复用 `acquireImageSlot` 的模式另开一个 `video-concurrency.js`；注意项目有 `state-singleton-check` 门禁，新状态文件按同样纪律声明。

## 四、功能逻辑（3 条）

### 🟡 F1. 工作流模式判定依赖中文关键词正则匹配用户可见文本

- **位置**：`server/routes/outfit.routes.js:166-209`
- **问题**：服务端用 `pageName` / `uploadLabels` 里的中文关键词（"换背景"、"白底精修"、"局部回贴"…）正则反推工作流，用来决定文件切片、最少文件数、提示词编译分支。用户改一个页面名字 → 服务端行为静默改变；前端发的 `workflowMode` 明明是权威值，却被文本猜测覆盖/补充。这是全项目**最隐性的行为耦合点**，后续加工作流时最容易踩（"我明明选了 X，服务端按 Y 处理"）。
- **修复方案**：把 `workflowMode`（客户端显式值）定为唯一权威，正则降级为"缺失时的 legacy 兼容"并打日志标记命中；新增工作流只加枚举，不加正则。可以加一个契约测试：给定 `workflowMode`，无论 pageName 写什么，路由到的分支一致。

### 🟡 F2. `requestId` 客户端可控，跨端复用会合并历史条目

- **位置**：`server/routes/images.routes.js:135`（`x-jingyin-client-request-id` 头直接采用）、`asset-persist.js:91`（历史 id = `${requestId}_${index}`）
- **问题**：两个不同生成用了同一个 requestId（前端复用/重放）时，`appendHistoryResults` 的 `byId` 会按 id 合并，后到的覆盖先到的。文件名侧有 `sanitizeFilePart` 兜底无穿越，但语义上会串。
- **修复方案**：历史 id 追加随机后缀或时间戳分量（`${requestId}_${index}_${Date.now().toString(36)}`），requestId 只做日志归集。

### 🟢 F3. `.env.example` 与代码默认值漂移

- **位置**：`.env.example`（`IMAGE_REQUEST_TIMEOUT_MS=420000`）vs `server/core/runtime-config.js:16`（默认 900000）
- **后果**：用户复制 .env.example 后实际拿到 7 分钟超时，与文档/注释口径不一致，排查时会看错基准。
- **修复**：二选一拉齐；或在 runtime-config 注释里显式写明"发布默认 900s，示例文件为演示值"。

## 五、架构设计（2 条）

### 🟢 A2. `deferOutfitAutoSave` 是带着 ESLint 警告故意留存的未用变量

- **位置**：`server/routes/outfit.routes.js:407`（注释已说明是 G-5 刻意保留）
- **评价**这是本项目少见的健康做法——把"未定的产品决策"留在门禁视野里。建议给它建一个待决项（docs/执行单或看板），避免留成永久孤儿。

## 六、工程化（3 条）

### 🟢 E1. 压缩中间件用同步 zlib，大响应会阻塞事件循环

- **位置**：`server/core/http-compression.js:65-67`（`brotliCompressSync` / `gzipSync`）
- **影响**：本地单用户可接受；响应体到 MB 级（大批量 historyItems）时，压缩期间整个进程停转（包括其它请求的日志写入）。建议改 `zlib.brotliCompress` 异步版，`res.send` 包装里转 promise——注意 `res.send` 同步契约，需要包一层 or 用 stream。低优先级。

### 🟢 E2. `/api/client-diagnostic-event` 无频率限制

- **位置**：`server/routes/system.routes.js:236-252`
- **影响**：前端每个 error/unhandledrejection 都上报，遇到报错风暴（白屏死循环）会打爆日志文件——有 8MB 轮转兜底，磁盘无险，但 fs 压力实打实。建议按 requestId 维度做 1 条/秒的简单限流。

### 🟢 E3. `safeSignedRouteHeaders` 不校验头名/头值格式

- **位置**：`server/core/route-helpers.js:30-41`
- **影响**：目前靠 undici 对非法头名/CRLF 抛错兜底（不会打成注入），且计费网关是自有可信边界。建议补一个 `!/^[!#$%&'*+\-.^_`|~0-9A-Za-z]+$/.test(name)` 的白名单校验，把"依赖下游抛错"变成"自己显式拒绝"。

### 🟡 D2. Node 运行时版本未在 package.json 声明 engines

- **位置**：`package.json` 无 `engines` 字段
- **问题**：代码用到了 `statfs`（Node 18.15+）、`openAsBlob`（18.13+）、`AbortSignal`/`fetch`（18+）、`queueMicrotask` 等。打包发布的 exe 内置 runtime，但用户若用 `node server/index.js` 直跑（README 有这条路径），Node 16 会在 `statfs` 上直接启动崩溃。
- **修复**：`"engines": { "node": ">=18.17" }` + 启动时一次性 capability 自检（`typeof statfs === "function"`），给出人话错误而不是栈溢出。

## 九、整体项目结论

**适合继续迭代，不需要重构；建议做一次"安全与并发收口"小专项（估 3~5 个执行单），然后按现有节奏走。**

理由：
- 架构底座是健康的：core/routes/features 分层、单例门禁、逐字节搬运纪律、错误语义分层、日志隐私约定（不写 KEY/base64）——这些是很多同类项目没有的。局部重构（拆 main.jsx / outfit-workflow.jsx）已在收敛中，继续即可，**不要推倒重来**。
- 真正的风险不是"代码烂"，而是三个假设正在被侵蚀：①"只绑 127.0.0.1 所以不需要鉴权"——被 connection-test 的自定义地址和 multipart 跨站面侵蚀；②"本地单用户所以并发不存在"——被后台即发即忘任务 + 多标签页侵蚀；③"依赖装上就不用管"——被 multer/proxy-addr 的已公开 advisory 侵蚀。
- 修完 S1/S2/S3 + T1/T2/T3 这 6 条，项目的风险面会从"有明确攻击原语"回落到"本地工具的合理水位"。其余按迭代排期。

## 十、后续开发避坑清单（写新代码时对照）

**安全红线**
1. 任何"客户端给地址、服务端就 fetch"的新功能，必须先过 `isSafeRemoteImageUrl` 或 `LOCKED_CHANNEL_API_BASE_URLS`——connection-test 是反面教材，image-proxy 是正面教材。
2. 新端点默认问三个问题：需要 KEY 吗？会被跨站表单打到吗（multipart/GET）？会回显上游原文吗（脱敏）？
3. 新增本地子进程调用：数组参数（不拼 shell）+ 超时看门狗 + `unref`。directory-picker 的 explorer 是范本，pickDirectory 的 powershell 是反范本（缺超时）。
4. 不要把用户 KEY 写进任何日志/文件名/回显；脱敏函数在 `sanitizeClientDiagnosticValue`，复用而别重写。

**并发与状态**
5. 任何"读-改-写"共享文件（history.json、app-settings、序号命名）必须走锁或原子 rename；项目里有 `withSaveFilenameLock` 现成模式。
6. 新的即发即忘后台任务（setTimeout 0 + promise）先想三件事：进程退出怎么办（flush）？客户端断了要不要继续？两个同时跑会不会互相覆盖？
7. 新队列/会话状态遵守 `state-singleton-check`：全服务端一份声明，放 core，外部只读快照。

**金额相关**
8. 动计费链路（prepare/finalize/attempts）前先读 `billing-attempts.js` 头部注释；任何"多打一次上游"的改动（新 variant、新重试）都要评估重复扣费，宁可不发不可多发。
9. 失败定性优先查 `image-error-policy.js` 的既有分支顺序，不要新造正则——那里的顺序就是产品故障语义。

**依赖**
10. 升级依赖只加不改语义（multer/proxy-addr 这类补丁优先）；动 `runtime-config.js` 默认值 = 改出图行为，必须先更新基线 JSON 再提交（防漂移门禁会拦）。
11. 引入新 npm 包前 `npm audit` 一遍；发布前跑一次全量 audit，高危/严重清零或写明接受理由。

**前端**
12. 新组件遵守 objectURL 成对创建/撤销；localStorage 读写走 `json-storage.js`（有 try/catch）；渲染兜底用现成 `ErrorBoundary`。
13. 工作流相关新需求：显式传 `workflowMode` 枚举，不要靠页面文字猜（outfit.routes 的正则反猜是待还的债）。

**提交前**
14. 代码 + 基线 JSON + 文档同单完成；`npm run check` 全绿才提交；每单必跑 build（import specifier 只有 build 能验）。
