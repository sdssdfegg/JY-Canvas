## 1. 给 Owner 看的结论（白话）

**你清了客户的浏览器缓存就好了——这正好证明了原因：卡住是因为浏览器里攒了太多旧图和旧数据，不是软件要求电脑配置高，也不是客户电脑不行。**

- 那个弹窗是**客户电脑上的浏览器（Chrome / Edge）自己弹的**，不是你的软件报错。这个封装版本质是「一个 exe 在后台起服务，然后自动打开系统默认浏览器」，窗口归浏览器管。
- 弹窗的意思是「这个网页这会儿忙不过来，点不动了」。**清理前连图片都传不进去**，就是浏览器被攒下的旧图旧数据占满了、腾不出手；清掉缓存就好了，说明是「攒多了卡」，不是机器不行。
- **你已经现场验证有效的办法：清理客户浏览器缓存 / 软件存下的旧数据**。这一步直接把卡住的原因清掉了，是**马上能用的止血办法**，以后客户再遇到，先做这一步。
- 为什么旧代码会「攒多了就卡」：客户装的是 **2026-11-08 打的 v5.0.1**，而专门修「图片一多就把浏览器卡住/内存撑爆」的那个改进是 **2026-11-11** 才做的。客户包里是修复前的老代码，攒下的旧图越多、越容易卡。清缓存相当于绕开了这个毛病。
- 封装版还有两个「加重」的地方：① 封装时为了防破解，把界面代码做了一层很重的加工，同样一件事要多费不少电脑力气；② 封装版一打开默认进的是最重、图最多的那个板块。**这两条只是让它更容易犯，不是病根**。
- 所以两件事分开看：**眼下治愈已经验证有效（清缓存）**；**想以后少折腾，还是用现在改好的源码重新打一个新包发给客户**（里面含上面那个 11-11 的改进和之后 95 次改进），新代码本来就能扛住攒图。要不要发新版由你定，这轮我一点没动。

## 4. 为什么「偏偏封装版」：三个放大因素

1. **前端全量 JS 混淆（封装版独有）**：`scripts/secure-win-release.mjs:291-312` 对 `dist/*.js` 逐文件混淆，`compact:true`、`controlFlowFlattening:true`(阈值 0.25)、`deadCodeInjection:true`(0.05)、`splitStrings:true`(chunk 10)、`stringArray:true` + base64 编码(0.75)、`transformObjectKeys:true`。运行时控制流平坦化 + 字符串解码让**每段同步活 CPU 成本成倍上升**；服务端 bundle 混淆（`:334-351`，`controlFlowFlattening:false`）跑在 exe 进程、**对浏览器主线程无直接影响**。体积旁证：`.secure-build/server.bundle.cjs` 5.23 MB → `server.protected.cjs` 11.87 MB（2.27×），内嵌 `static-assets.generated.js` 3.93 MB / 32 文件；`发布工程/tmp-build-v501-r2.log:64` `feat-outfit` 267.30 kB 为最重 chunk。源码版 vite dev **完全不混淆**。
2. **首屏默认进最重板块**：`src/features/storage/storage-store.js:33` public 版首屏 `outfit`（源码版默认 `quickgen`）；`src/main.jsx:1603-1604` 首渲染被 `publicReleaseStorageResetPromise` 门禁；`storage-store.js:57-106` 首启动同步清 11 个键 + 删 6 个 IDB 库 + 种子导入（`src/shared/release-seed.js:182-225`，9 entry 逐项 localStorage 写）。该链为常量级、不随用户数据增长，但叠加首屏重视图。
3. **生产分支额外负担**：`secure-win-release.mjs:272-276` 注入 `NODE_ENV=production` / `VITE_JINGYIN_PUBLIC_RELEASE=1` / `STORAGE_PREFIX`；`:283/:751` `.release-mode` 静态托管内嵌 dist；`server/core/app-bootstrap.js:77-79` `/assets/*` immutable 强缓存；`secure-win-release.mjs:329` 日志开关 define 成 `"0"` ⇒ 生成日志强制开启（每请求写 `generation.jsonl` + 单任务 TXT）。

## 6. 「吃配置」判定：**无证据支持**

| 判定 | 依据 |
|---|---|
| 无最低配置要求 | 全仓未找到最低 CPU/内存要求或「配置不足致弹窗」记录 |
| 冒烟内存很低 | `发布登记表.md:86/106/126/146` 多次冒烟 RSS 仅 171–189 MB；`/api/health` 报内存四项（`server/routes/system.routes.js:230-249`） |
| 拆包目的是兼容低配 | `vite.config.js:12-14` manualChunks 注释「缓解低端机解析单包的压力」⇒ 适配低配而非要求高配 |
| 构建日志里的 OOM 是另一回事 | `发布工程/tmp-build-v501-r2.log:95-97` `WebAssembly.instantiate(): Out of memory` 属**构建机 postject 注入 blob**，V197 已用独立进程绕行；不是客户机运行期内存 |
| V206 的 OOM 是浏览器标签页 | `V4.0-快捷生成OOM修复验收报告.md:9-13` 指一次性解码大量高分辨率历史图撑爆**标签页**内存，与整机配置无必然关系 |

**结论**：机器配置只决定触发阈值（同样的同步活，低配耗时长、更早弹窗），**不产生也不消除阻塞**。代码路径里不存在「配置够就不执行」的分支。让客户升级硬件只能缓解，不能根治。
