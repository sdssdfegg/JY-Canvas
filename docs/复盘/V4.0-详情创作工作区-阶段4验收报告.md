## 一、阶段目标与范围（阶段 4 边界、R1 / R2 口径）

- 单项目最多 **20 屏**，每屏一个独立生成任务；详情任务队列**本身不设数量上限**（20 屏全量入队、状态可见、进度可查），全局 5 并发只是执行层资源保护（R1）。
- 复用现有 `/api/images`，**不新建图片体系、不改 `IMAGE_CONCURRENCY_LIMIT`**（八文件禁改清单：`image-concurrency.js` / `runtime-config.js` 零改动）。
- R2 授权落地的通用持久化任务层（从 `server/ai-tryon/task-store.js` 抽取），须验证旧 AI 换装任务完整兼容。
- 交付物七项：批量出图、任务状态机、失败隔离、单屏重试、断点恢复、幂等、异常保护（分类 + 退避 + 有限重试，不确定请求不自动重试）。

## 二、R2 通用任务层抽取与旧换装兼容

- 隔离：`server/features/detail-studio/generation/task-store.js` 仅作薄适配层，绑定到 `data/detail-studio/generation/tasks/`，**不 import 旧 `task-store.js`、不共用索引**。
- 旧换装兼容：**`server/ai-tryon/task-store.js` 零改动**（`git diff` 校验无差异，属八文件禁改清单只读参照）。旧换装任务走原文件、原目录 `data/ai-tryon/tasks/`；R2 核心层经同口径冒烟（10 项断言）覆盖六机制，兼容由「零改动」保证、非重新实现。

## 三、服务端批量编排（状态机 / 幂等 / 失败隔离 / 重试退避 / 断点恢复）

- 状态机：`queued → running → success | failed`，外加 `cancelled`（用户主动中断）与 `needs_confirm`（不确定请求 / 重启恢复）；迁移由 `canTransition` 程序判定。
- 幂等：`idempotencyKey = sha256(projectId | screenIndex | frozenPrompt)`，入进程内账本；重复提交直接复用已有任务，绝不二次扣费 / 二次出图（冒烟「重复提交 skipped=1、上游调用仅 1 次」通过）。
- 失败隔离：单屏失败只写该任务，其余成功屏与已落盘图片原样保留（冒烟「2 成功 1 失败，成功屏保留」通过）。
- 重试与退避：`MAX_ATTEMPTS=3`；可重试错误（429/5xx/网络）自动重试，指数退避 + 30% 抖动；不可恢复（401/413/400）直落 `failed`；**不确定请求（超时 / 504）不自动重试 → `needs_confirm`**（冒烟「超时→needs_confirm 不自动重试」通过、冒烟「重试次数==MAX_ATTEMPTS、未无限循环」通过）。
- 断点恢复：`recoverOnStartup` 在路由注册时执行，`running` 且无结果的任务标 `needs_confirm`，不盲目重跑（冒烟通过）。
- 可测性：`generator` 依赖注入，编排层单测用 mock 脱离真实上游；11 项断言覆盖幂等 / 隔离 / 有限重试 / 超时 / 401 / 取消 / 恢复。

## 四、图片生成链路（复用 /api/images、frozenPrompt 字节一致、结果图落点）

- 仅复用现有 `POST /api/images`：`server/features/detail-studio/generation/local-images-generator.js` 内部自调，复用其全局 5 并发闸门 + 计费 + 持久化；不另立 Provider / KEY / 网关。
- `prompt` 直接读 `current.frozenPrompt` 组装请求体，字节一致（V202 B3 `frozen-prompt-parity` 口径延续），不经任何 Skill / Agent / 提示词编译。
- 结果图落 `data/detail-studio/generation/results/`（由 `app-paths` 新增 `detailStudioGenerationResultsDir` 锚定）；**严禁** `data/results`（7 天 TTL）、`seed/manifest.json`、安装包默认种子（R4 红线）。
- `persistResult` 把上游回传的 `file://` / 绝对路径拷贝到 `results/`；若上游仅回 URL 则 `resultPath` 留空、保留上游引用（不因复制失败致命）。

## 八、真机端到端验证与多屏测试设计

- **沙箱限制**：无真实 KEY / 上游，单元层用 mock generator 覆盖全状态路径；真机端到端出图（接真实 `/api/images`、真实扣费）**未在沙箱跑**。
- **建议真机验证清单**（上线前 Owner 执行）：① 选一项目「开始批量生成」跑满 2–3 屏，确认只调一次上游 / 不重复扣费；② 制造一次上游 5xx，确认自动重试到 `MAX_ATTEMPTS` 后落 `failed`；③ 制造一次超时（或杀服务），重启后确认该任务标 `needs_confirm` 而非盲目重跑；④ 点单屏「重试」确认不影响其它屏。
- 多屏 / 多模式：A/B（AB 测试多组提示词）与 `direct`（模式 C `screens[]`）均经 `buildBatchSpec` 消费同一份 `frozenPrompt`，路径一致；三类商品（清洁日化 / 服装 / 食品 3C）复用阶段 3 的 `frozenPrompt` 产出，本阶段不改变提示词内容。
