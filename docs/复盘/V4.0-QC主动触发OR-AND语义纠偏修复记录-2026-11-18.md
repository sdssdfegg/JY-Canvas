## 1. 根因定位（先取证结果）
| 核查项 | 真实代码位置与当前表达式 |
|---|---|
| ① SKILL08 正式定义 vs 配置 | 正文 §02："满足任一条件时可激活"（OR）；配置 `professional-skills-v1.json` 原 `activation_conditions=["user_clicks_qc","user_requests_review"]`（两键并列） |
| ⑤ 最终判定 | `skill-activation.js:230 conditionsMet`：`conditions.every((cond)=>ctxKeys.has(cond))`——AND 语义，两键必须**同时**存在 |
| ②③ 按钮/用户请求信号 | `user_clicks_qc`/`user_requests_review` 全仓**只出现在配置**；前端"运行质检"按钮实际走 `PlanningPanel.jsx:254 onClick` → `use-detail-studio-state.js:574 qualityReview()` → `detail-studio.js:153` → `POST /api/detail-studio/projects/:id/planning/quality`（B4 独立链路），**不进 V2 activation**；无代码把"检查详情"文本识别为 `user_requests_review` |
| ④ Middleware | `detail-middleware.js` 的 `triggerCtxKeys` 从不 push 任何 QC 键 |
| ⑥ 执行器/编译器 | `detail-middleware.js` `activeSkillIds` 只用 model-pose；`skillActivation` 仅作审计证据，QC 激活结果不参与执行 |
| ⑦ AND 合并层 | **错误层 A**：配置两键并列 + `conditionsMet.every` = AND（本意 OR） |
| ⑧ 隐式触发路径 | 无其他 Skill 自动触发 QC 的代码路径（grep 仅 directive 文本与 pending config） |

**结论**：错误在两处——A 层（配置把两个独立入口塞进同一 AND 数组）、B 层（V2 链路从未派生这两个信号，QC 在 V2 永远 inactive）。

## 3. 修复后契约
```
QC_trigger = ButtonClick OR ExplicitUserRequest
```
- 两个入口各自独立派生统一信号 `qc_requested`（单键 activation 经 `every` 等价"存在即触发"）。
- 同时成立只返回**一个** `qc_requested` → 只判定一次、不重复执行。
- 旧键 `user_clicks_qc`/`user_requests_review` 仅在输入侧归一化，正式契约只认 `qc_requested`。
- 默认 inactive：无入口信号、普通生成/修改、其他 Skill 自检均不派生 → QC 不自触。
