## 一、纠正参数理解：插入反转屏的真实语义
**[事实-前端]** 控件标签"插入反转屏"（DetailView.jsx:275），字段 `reverseScreens`，选项 0~4（basic-param-options.js:82），默认：老视图 app-defaults.js=2、studio=0。
**[事实-服务端]** `buildScreenTitles`（detail-middleware.js:810-830）：`targetReverseCount = min(clamp(reverseScreens,0,4,0), count-2)`，按间隔把 `titles[slot] = "痛点反转"`；`buildRounds:934` 写"本组 N 屏，反转屏 X 屏"。
**[事实-模块]** `SCREEN_MODULES.painReverse`（detail-skills.js:282-289）：name="痛点反转"，purpose="把用户常见顾虑转成购买理由"，composition="可以用左右对比、上下对比或场景前后变化，但不要制造虚假效果"——**是营销叙事模块，不是颜色跳色、不是前后对比产品能力**。
**[事实-路径隔离]** 用户当前测试场景 `selectedSections=null → v2Planning=true`，标题直接取 `aiScreens[i].title`（detail-middleware.js:1342-1345），**完全绕过 buildScreenTitles**。实测 `reverseScreens=2, count=10` 本地兜底与 AI 规划两路径 text 中均无"痛点反转"、标题全为"第N屏"——**该参数在默认规划路径下被彻底忽略**。
**[结论·已修正，见第零节]** `painReverse`「痛点反转」是用户确认以前使用正常的**既有功能，保留不改、不改名、不重设计**。事实层面仍成立：当前默认 v2Planning 路径绕过 `buildScreenTitles`、`reverseScreens` 未进入规划决策（这正是本轮要排查的问题）。**待验证**：用户选择数量（2）是否真正影响①分屏规划②反转屏内容任务③最终提示词——目前实测三者均无体现，属"参数未进入规划"的缺陷，而非"用户需要改变功能"。修复方向应是让既有功能接入规划路径，而非改造功能语义。

### 2.2 顾问六问逐条回答
1. **"使用率2"语义** `[已修正，见第零节]`：控件定义 1~12、语义为**本套详情计划安排模特屏的约定数量**。当前实现 `index < Math.min(modelUsage, count)`（:802/:1035）把它做成**从首屏起的前 N 屏硬编码**——**这与产品要求冲突**：产品要求模特不必从第 1 屏开始、具体哪几屏由商品特点/分屏任务/营销策划/视觉主体分配决定、不适合模特的屏不应凑数、用户明确指定某屏必须出现时用户优先。当前实现是待调整项，不是应保留的正确行为。
2. **默认值覆盖**：服务端 clamp fallback=4、studio 默认6、app-defaults 默认4——**用户显式传2时不被覆盖**（探针 params.modelUsage=2）。
3. **是否被 Skill/行业忽略** `[已修正]`：figure-usage-scene 按屏激活探针——前2屏 `conditional`、后8屏 `inactive`，deriveFigureTaskContextKeys（:1029-1041）对前2屏派生 `screen_needs_figure/user_requires_figure/explicit_figure_task`、后8屏返回 `no_figure_requirement`。Skill 链路本身**未忽略字段**，但它继承的是**错误的前 N 屏假设**——按产品语义，授权屏应由策划决定而非 index 顺序。
4. **可选建议 vs 必须执行**：modelPolicy 对授权屏输出确定性硬约束"本屏使用特殊姿态模特：…"，对未授权屏输出"本屏不使用模特…"——**按屏任务是硬约束，不是可选建议**（这点与产品要求一致）；问题只在"哪些屏被授权"的判定规则。
5. **规划结果是否安排屏幕** `[已修正]`：探针（count=10, modelUsage=2）最终 text 确实前2屏"本屏使用特殊姿态模特"、后8屏"本屏不使用模特"——**但这正是产品不认可的"前 N 屏"安排**：它按 index 机械分派，未结合分屏内容任务/营销策划/视觉主体，也未体现"用户明确指定某屏"的优先级。
6. **最终 prompt 是否保留**：是，实测 `特殊姿态模特` 出现 2 次、`无模特` 8 次，两路径（本地兜底/AI规划）一致——**保留层面无丢失**，需调整的是分派规则而非保留机制。

### 2.3 对用户实际结果"10张图没模特"的判断
**[事实]** 服务端完成了"用户选择→按屏分派→prompt 硬约束"链路；但按第零节2的修正，这里的"按屏分派"用的是**前 N 屏硬编码**，与产品要求冲突（应策划决定屏位）。**[推断]** 图片没出现模特的最可能环节是**生图模型未执行 prompt 要求**（模型执行层），或**用户实际提交的参数与报告描述不一致**（需真实 `/api/images` 请求体取证）。**不能据此认定参数传递失败**——需按 P2-0.5 基线先抓真实请求体确认，再区分"分派规则问题"与"模型执行问题"。
