## 1. Skill 数量与输出映射

### 1.1 正式注册表（`prompts/server/detail-v2-planning/index.js` 的 `detailV2SkillRegistry`）

### 1.2 输出映射表（`server/detail-middleware.js:1109` 的 `SKILL_OUTPUT_MAP`）

### 1.3 `product-specialty-expression` 的真实身份
- 是 `professional-skills-v1.json` 的 `activationContracts["product-specialty-expression"]` 一个**聚合契约**（execution_mode=conditional），其 `formal_professional_contract_v1.six_specialties` 定义 6 类子专项；**不是 6 个独立注册 Skill**。
- 本项实现中 **未向注册表新增任何 Skill**，六类作为 specialtyId 子级记录。

### 1.4 正式 Skill 与聚合专项是否重复统计 —— ⚠️ 发现表述问题
实测 `evaluateAllActivations({contextKeys:[]})` 返回 **16 条结果**，而注册表只有 8。逐项对比：
- 表有注册表无（10 条）：`figure-usage-scene`、`model-pose`、`product-specialty-expression`、`product-structure`、`industry-routing-retained`、`cross-screen-coherence-retained`、`effect-evidence`、`ingredient-mechanism`、`industry-cleaning`、`product-authenticity`。
- 注册表有表无（2 条）：`industry-routing`、`cross-screen-coherence`。

**结论**：这 16 条**不是 16 个正式 Skill**。激活表用的是工程引擎 id 层（`BASE_ACTIVATION` + `FORMAL_TO_ENGINE_ID`，skill-activation.js:97/162），存在**同一能力的双 id 表示**：
- `figure-usage-scene`（正式契约 id）与 `model-pose`（引擎 id）指向同一能力（:165 映射）；
- `product-specialty-expression`（聚合契约）与 `product-structure`（引擎 id）指向同一能力；
- 注册表的 `industry-routing`/`cross-screen-coherence` 在激活表中以 `*-retained` 兼容 id 出现。

**问题归类：状态语义/文档表述**。实施报告"所有 Skill 的真实 ID 与映射"一节把 16 条结果表述为"8 正式 Skill + retained/引擎 id，共 16 个判定结果"，但"判定结果数"与"Skill 数"未显式区分，易被读成 16 个 Skill。**修正方式（仅文档）**：明确"五态逐条来自 16 个 activation 判定 id（含 formal/engine 双表示与兼容 id），正式注册 Skill 恒为 8；双 id 是同一能力的两个标识，不构成第二个 Skill，也不是重复交付"。**未改代码、未删任何 id**（删除会破坏既有门禁与映射）。

## 2. Output / Downstream 的真实归属

### 2.1 五态是否只是对映射字段的校验与消费记录 —— 是，符合设计
核实 `buildFiveStateLifecycle`（detail-middleware.js:1124-1175）：Output 仅调用 `validateSkillOutput` 对 `SKILL_OUTPUT_MAP` 声明的字段做结构/非空校验；Downstream 仅依据 `spec.consumer` 是否存在登记消费状态；Injection 仅对命中段做 hash/次数。**没有模型内部行为推断，没有把共享 aiPlan 整体归因为某 Skill 独立产出**——每个 Skill 只被标注其映射字段的契约有效/consumed。

### 2.2 三个语义边界（逐项确认）
- **不将模型共享输出归为某 Skill 独立产出**：aiPlan 由一次模型调用生成，映射只是"该 Skill 的契约字段视图"；Execution 的 `modelCallSucceeded` 表示共享调用成功，非独立执行（见补充一 Execution 语义）。
- **`valid` 只表示对应输出契约有效**：`validateSkillOutput` 返回 valid 的条件是字段非空/非占位/结构符合 `itemFields`/`requiredFields`（skill-activation.js:294-319），不表示专业质量，不表示模型遵循了该 Skill。
- **`consumed` 只表示对应字段被真实消费者读取**：`spec.consumer` 为真实函数/槽名（如 mergeAiAnalysis、buildScreenVisual），`consumer:null`（qc/industryProfile）一律 `not_consumed`。

### 2.3 多 Skill 对同一字段的重复归因 —— ⚠️ 发现真实归因瑕疵
- `planning.facts` 被 **detail-story-planning**（:1111，`consumer:"screenRoles/moduleId"`）与 **product-specialty-expression**（:1116，`consumer:"structure/effect entry"`）**同时映射**——同一字段被两个 Skill 各记一次 output=valid/downstream=consumed，存在**共享输出的重复归因**。
- `screen.modelPolicyHint` 记为 figure-usage-scene 的输出字段（:1115），但它是运行时 `modelPolicy()` 策略计算的派生的值（detail-middleware.js:725-736），**不是模型 aiPlan 的原生输出字段**——把它标为该 Skill 的"输出契约字段"语义略夸大。

**问题归类：状态语义标注问题（非运行时缺陷）**。字段确实被两处消费、派生的值确实影响模特指令，真实消费无误；但"一个字段归两个 Skill 独立产出"会夸大归因。
**按授权处理**：仅在本记录中明确——
- `planning.facts` 的重复归因应理解为"同一共享输出被两个 Skill 的契约各自视图引用"，**不是两份独立产出**；如顾问要求收紧，后续单可改为在证据里加 `sharedField:true` 标记（**本项不改代码**）。
- `screen.modelPolicyHint` 更准确的说法是"figure-usage-scene 的运行时派生的指令输入"，而非模型输出契约字段；实施报告 §五"figure-usage-scene"行按此说明修正（文档层）。
**未改代码、未扩大修复范围**，交顾问裁定是否需要后续微调。

## 3. 三阶段 Injection 来源与 hash 能力

### 3.1 三阶段逐条（代码位置 / 来源 / hash 位置）
| 阶段 | 实际代码位置 | 规则来源 | hash 计算位置 |
|---|---|---|---|
| A 规划模型请求 | `server/detail-ai.js:182-186`（`skillModuleV2.directives/constraints` + `V2_REGISTERED_SKILLS.map(directive)` + calibration），`:329-346 buildDetailChatBody`，`:365 postChatCompletion` | **直接 Skill directive**（V2_SKILL_DIRECTIVES:24-33，裸文本注入 instruction）+ skillPack.registeredSkills（:112-114，带 marker） | **本项未计算 hash**（阶段 A 不在 P1-4 追踪范围；仅记录 directiveDispatched 运行事件） |
| B 最终详情提示词编译 | `server/detail-middleware.js:1410-1437 text[]`；追踪在 `buildFiveStateLifecycle:1124-1175` | **Skill 派生字段**（figure-usage-scene→`【模特与镜头】`、ecommerce-copy-layout→`【本屏文案】`）vs **非 Skill 规则**（行业包 globalLock、平台策略、模块规则、商品事实、全局约束）——只对前者标 Skill injection | `middleware:1171 contentFingerprint(injectionNeedle)`；工具在 `skill-activation.js:289-296`（FNV-1a，确定性，不存原文） |
| C 生图请求 | `src/features/detail/detail-state.js:496 form.set("prompt", prompt.text)` | 仅转发阶段 B 的 `prompt.text` 全文，**无 per-Skill 标识** | 无（本项未改，也不追踪阶段 C hash） |

### 3.2 三类内容不得混淆（确认）
- 规划请求中的直接 Skill directive：只有阶段 A 的 `V2_REGISTERED_SKILLS` 裸文本是"直接 Skill 规则"；
- 最终详情提示词中的 Skill 派生字段：仅 figure/文案两类生成指令被标 Skill injection（:1164-1165）；`【全局一致性锁定】`（行业包 analyzeAttributes/taboos）、平台策略、模块规则、商品事实均为**非 Skill 直接注入**，五态未把它们记为某 Skill 的注入；
- 生图请求：只转发 text，无标识。
**行业包、平台策略、模块规则未被误记为 Skill 直接注入**（核对 :1164 的 injectionNeedle 仅两类 Skill 派生段）。

### 3.3 occurrenceCount 的检测能力边界（明确，不夸大）
- 实现：`occurrences()`（:1126-1131）用 `text.indexOf(needle, i)` 对**精确子串**计数；hash 是该精确 needle 的 `contentFingerprint`。
- **只识别"精确文本重复"**（同一字符串在 text 中出现 ≥2 次）；**不识别语义重复**——同义改写、换序、跨平台策略文案雷同均不计入 `duplicate`。
- 实测：`contentFingerprint("模特") !== contentFingerprint("人物模型")`（语义近但字不同 hash 不同），印证只做精确比对。
- 报告中"重复注入识别"一律按此口径理解；P1-5 若治理语义级重复需另行能力，本项未提供。

## 4. 非枚举生命周期对象可达性与并发隔离

### 4.1 属性定义代码
- 收集器：`server/detail-middleware.js:1318 const skillLifecycleByScreen = {}`；按屏写入 `:1519`。
- 非枚举挂载：`:1673 if (v2Planning) Object.defineProperty(result, "skillLifecycleByScreen", { value: skillLifecycleByScreen, enumerable: false, configurable: true })`。

### 4.2 服务端读取位置
- 门禁 AP 组：`scripts/verify/detail-v2-control-chain-check.mjs` 的 `apLife = apGroup(...).skillLifecycleByScreen.screen_1`（及 AP4/5/7/8/9/10 的读取），是**真实 buildDetailPromptGroup 产出后读取**，非手工构造临时对象。
- 生产端：服务端内部可读（同进程），前端因非枚举 + 不序列化而不可见（前端本就零消费，见 P1-4-RESEARCH §2.4）。

### 4.3 读取与复制/展开/序列化的先后顺序
1. `prompts.map` 循环内计算五态 → 写入闭包变量 `skillLifecycleByScreen`（:1519）；
2. screen 落盘时 `skillActivation` 被剥离 lifecycle（:1558-1560），**prompts[] 不含五态**；
3. `const result = {...}` 构造返回对象（:1596 起）时**未展开**五态；
4. `Object.defineProperty(result, ..., enumerable:false)`（:1673）后再 `return result`——**序列化（`JSON.stringify`）发生在 return 之后、由调用方触发**，此时非枚举属性被跳过。
实测：`g.skillLifecycleByScreen` 可直接访问；`JSON.parse(JSON.stringify(g))` 不含该键；`g.prompts[0]` 不含 `skillLifecycle`。

### 4.4 两个并发请求的 runId 隔离（实测）
交错调用两次 `buildDetailPromptGroup`（A=cleaning/model mA/timing 11ms，B=electronics/model mB/timing 22ms）：
- `runId A=run_fp_c032775f`，`B=run_fp_7d4b0192`，**不同**；
- `analysis.industry A=清洁日化 / B=数码家电`，各自独立；
- 每方 16 条结果，首 Skill execution.runId 分别等于各自 runId，无串扰。
原因：`skillLifecycleByScreen` 是**每次函数调用闭包内的局部对象**（:1318），非模块级共享。

### 4.5 请求完成时无意外 null（实测）
两个请求各 16 条结果，逐条检查 `activation/execution/output/downstream/injection` 五态：**A null 数 0、B null 数 0**。初始 null 只在未激活/不适用路径按事件填充为明确状态，无遗漏。

**结论：lifecycle 是真实运行时数据**（由 buildDetailPromptGroup 真实事件产生、闭包隔离、服务端可读、非枚举避免污染序列化），**不是测试代码临时对象**。
