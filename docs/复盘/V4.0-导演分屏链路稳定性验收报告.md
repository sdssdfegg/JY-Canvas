## 二、根因诊断（不是渠道，是结构问题）

1. **渠道可排除**：同网关（`api.jingyin.online/v1`）、同 KEY、同模型 `gpt-5.6-luna`、同一 `postChatCompletion`、同样 `response_format: json_object`；analyze 成功即证明全链路通畅。
2. **结构错配（小输出能回，大输出回不来）**：
   - analyze：路由超时 60s、`max_tokens` 2000，出一份小 JSON ⇒ 成功。
   - director：路由超时 90s、`max_tokens` 3000，要产出**最多 20 屏 ScreenSpec[]**（每屏约 10 类字段）⇒ 紧约束，天然慢且易截断。
3. **两条高概率失败路径（因零日志无法区分，正是 P0 先补日志的原因）**：
   - 路径 A（超时/截断）：90s abort → `504`；或 3000 token 截断 → `extractJsonObject` 抛错 → `502 parse_failed`。
   - 路径 B（静默空结果）：模型返回合法 JSON 但 `screens` 缺失/结构不符 → `normalizeDirectorResult` 得 `[]` → `directVisualPlan` **仍返回 `ok:true, screens:[]`** → 路由落库 `planning.screens=[]` → 界面停在 0 屏。**完全匹配截图。**
4. **可观测性缺口**：`grep -c planning logs/generation.jsonl` = 0；`server/features/detail-studio/planning/` 与 `server/core/ai-chat-shared.js` 零日志埋点 ⇒ 三批次（analyze/director/quality）耗时、上游状态码、返回长度、解析结果全部无记录。

## 三、修复方案（参数分档，不拍脑袋）

- 超时与 `max_tokens` 抽为**按目标屏数分档**常量（≤8 / 9–14 / 15–20 三档），从 `context.screenCount` 取值；20 屏档必须给足输出空间。`analyze` 的 60s/2000 **保持不变**。
- 错误类别枚举固定：`timeout` / `upstream_error` / `parse_failed` / `empty_screens` / `no_content` / `unknown`；返回前端的是**类别 + 人话建议**，不是上游正文。
- `normalizeDirectorResult` 增加屏数校验；空屏显式抛错，禁止静默 `ok:true`。
- 前端反馈：已等待 N 秒、错误类别、建议动作（重试/减少屏数/检查网络）、重试按钮；错误 banner 置顶且滚动可见。
- 保持：A/B 各 3 次 `postChatCompletion` 上限、C 模式 0 次、`frozenPrompt` 字节一致、后台零改写。
