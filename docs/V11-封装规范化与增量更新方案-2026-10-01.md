## 一、现状盘点

### 1.1 现有封装链路（`npm run release:win`）

```
1/8  vite build（VITE_JINGYIN_PUBLIC_RELEASE=1）
2/8  混淆 dist 下所有 .js
3/8  generate-static-assets.mjs → dist 全量 base64 内嵌进 server/static-assets.generated.js
4/8  esbuild bundle server/index.js → server.bundle.cjs（9.9 MB，minify）
5/8  混淆 server bundle
6/8  node --experimental-sea-config → jingyin-sea.blob（useCodeCache 必须 false）

8/8  postject 注入 NODE_SEA_BLOB，写 version.json / 更新日志 / 启动 bat / 诊断脚本 / 校验和
```

产出：`静音AI画板.exe`（单文件）+ `version.json` + `更新日志.md` + `启动（推荐）.bat` + `使用说明.txt` + `导出诊断日志.bat/.cmd` + `export-diagnostics.ps1` + `tools/校验和.txt`

### 1.2 已经做对的地方（这些别推翻）

下面几条是专业做法，重构时要保留：

- **数据目录与代码目录分离**：运行时数据写 `%LOCALAPPDATA%\静音AI绘画数据`，不含在安装包里。这是增量更新的**前提条件**，你们已经具备。
- **便携模式**：`DATA_ROOT` / `JINGYIN_RELEASE_ROOT` 可覆盖数据目录。
- **不内置任何 KEY**：说明里明确写了，合规。
- **rcedit 改掉 Node 原始属性**：把 OpenJS 的公司名/原始文件名换成自己的，避免"属性里露馅"。这一步很多人漏。
- **用 OpenJS 官方签名的 node.exe**：比自己编译的更不容易被杀软拦截。
- **SHA256 校验和 + version.json**：分发核对已有基础。
- **诊断日志一键导出**：面向非技术用户的排障设计，很实用。
- **构建前强制清空 dist**：注释里记录了 29 个旧 bundle 导致混淆器 OOM 的踩坑，这是真经验。

## 二、增量更新的核心障碍（为什么现在做不到）

### 2.1 三层嵌套 = 更新代价恒定

```
静音AI画板.exe ≈120 MB
└── NODE_SEA_BLOB 9.9 MB
    └── server bundle（前端 dist 已 base64 内嵌在里面）
```

`generate-static-assets.mjs` 把 `dist/` 下**每个文件都 base64 编码**塞进 `server/static-assets.generated.js`，再被 esbuild 打进 bundle，再打进 blob，再注入 exe。

结果：**改一个前端文案 → 三层全部重打 → 用户重新下载约 120 MB**，其中 110 MB 是从没变过的 Node 运行时。

### 2.2 混淆让差分在数学上失效（最容易被忽略的一条）

当前混淆配置里有：

```js
deadCodeInjection: true,          // 随机注入死代码
identifierNamesGenerator: "hexadecimal",  // 随机标识符
```

`javascript-obfuscator` 默认 `seed = 0`（随机）。意味着：**即使源码一行没改，两次构建出的 blob 字节也完全不同**。

所以：
- bsdiff / courgette 这类二进制差分算法**完全无效**（差异率接近 100%）
- 你无法用"文件 hash 没变就跳过"来判定，因为每次 hash 都变

**好消息**：混淆器支持 `seed` 选项（`typings/src/options/Options.d.ts:68: readonly seed: string | number`）。设固定 seed 后，相同输入 → 相同输出，构建可复现，差分才有意义。

> ⚠️ 需实测验证：`seed` 对 `deadCodeInjection` 随机性的控制程度。建议先做一次"同源码连打两次、比对 SHA256"的验证，一致才算数。若不一致，则须关闭 `deadCodeInjection` 才能保证可复现（安全性损失很小，它主要是增大体积和干扰阅读）。

## 三、增量更新方案（推荐：三阶段渐进）

### 阶段 1 · 可复现构建 + 产物清单（半天，零风险）

**目标**：让"哪些文件变了"变成可计算的事实。这是后面所有工作的地基。

1. 给两处混淆加固定 `seed`（建议取 `internalVersion` 的数字，如 `20261001`）：
   ```js
   seed: Number(internalVersion.replace(/\D/g, "")) || 20261001
   ```
2. 构建结束后生成 `build-manifest.json`：遍历 `dist/` + server bundle，记录每个文件的**混淆后实际字节**的 SHA256、大小、相对路径。
   > 坑：vite 生成的文件名 `index-a1b2c3.js` 是**混淆前**内容的 hash，混淆后就对不上了。manifest 必须读最终字节算 hash。
3. 加一个门禁脚本 `scripts/verify/build-reproducible-check.mjs`（可选）：同源码连打两次，manifest 应逐字节一致。

**收益**：这一步不改发布结构，但让你第一次能回答"这次改动到底影响哪些文件"。

### 阶段 2 · 前端资源外挂（关键一步，1–2 天）

**思路**：把 `EMBEDDED_STATIC_ASSETS` 从"唯一来源"改成"兜底来源"。

改造 `server/core/app-bootstrap.js` / `sendEmbeddedStaticAsset` 的读取逻辑：

```
请求 /assets/index-xxx.js
  ↓
① 先看 app/web/index-xxx.js 磁盘文件是否存在
  ↓ 存在 → 直接读磁盘返回（这是可更新的部分）
  ↓ 不存在
② 回退到 EMBEDDED_STATIC_ASSETS（内嵌 base64）
```

配套改动：
- `secure-win-release.mjs` 第 3 步不再内嵌**全部** dist，改为只内嵌一份"最小兜底集"（如 index.html + 入口 js），其余输出到发布目录的 `app/web/`。
- 发布目录新增：`app/web/`（前端资源，可独立更新）。

**收益**：
- 改前端文案 → 只替换 `app/web/` 里的 1 个 js，**几十 KB ~ 2 MB**
- 单文件 exe 的"双击即用"体验**不变**（兜底集仍在）
- 即使 `app/web/` 被用户删了，软件依然能用（回退内嵌）

这是**改动最小、收益最大**的一步，强烈建议优先做。

### 阶段 3 · 完整分层 + 自更新器（1–2 周）

**目标目录结构**：

```
静音AI画板/
├── 静音AI画板.exe        启动器外壳（几乎不变）
├── runtime/node.exe      运行时（不变，≈110 MB）
├── app/
│   ├── server.cjs        服务端 bundle（常变，≈10 MB）
│   └── web/*             前端资源（常变，几十 KB 起）
├── updates/              下载暂存 + 上一版备份（回滚用）
└── version.json
```

**更新器设计**（用项目自带的 node 写，不引入新依赖）：

1. **manifest 格式**（服务端静态文件，如 `https://<分发域名>/jingyin/manifest.json`）：
   ```json
   {
     "latestVersion": "3.8.2",
     "runtimeRequired": "24.9.0",
     "requireFullReinstall": false,
     "files": [
       { "path": "app/web/index-a1b2c3.js", "sha256": "...", "size": 1843200, "url": "..." },
       { "path": "app/server.cjs", "sha256": "...", "size": 9900000, "url": "..." }
     ]
   }
   ```
   - `runtimeRequired` 变了 → `requireFullReinstall: true` → 才让用户下完整包
2. **更新流程**：
   ```
   启动时异步拉 manifest（不阻塞启动，超时 3s 静默跳过）
   → 比对本地文件 hash，得出"需要下载的文件列表"
   → 下载到 updates/tmp/
   → 逐个校验 SHA256（错一个就整体放弃）
   → 备份旧文件到 updates/backup-<版本>/
   → 原子替换（先写 .new 再 rename）
   → 写新的 local version.json
   ```
3. **失败回滚**：启动后自检失败（比如 server.cjs 语法错）→ 自动从 `updates/backup-*/` 还原，并提示用户。
4. **文件占用问题**：Windows 下正在运行的 exe 无法覆盖。
   - 前端资源 `app/web/*`：可在服务运行时替换（下次请求生效）
   - `app/server.cjs` / 运行时：**必须先退出主进程**再替换 → 更新器需独立进程，主程序退出后再动手
5. **分发**：manifest + 差异文件放静态 CDN / 对象存储即可，可复用现有 `api.jingyin.online` 的静态能力，或单独买个对象存储（成本极低，因为流量主要是几 MB 的差分包）。

### 方案对比（为什么不用别的）

| 方案 | 评价 |
| --- | --- |
| **Electron + electron-updater** | 差分更新最成熟，但要把整个应用迁到 Electron，与现有"本地服务 + 浏览器"架构冲突，改造量巨大。**不建议**。 |
| **继续单文件 exe + bsdiff 二进制差分** | 被混淆随机性打死（§2.2），且 bsdiff 对 120 MB 文件内存开销大。**不可行**。 |
| **每次只发前端 zip，让用户手动覆盖** | 能解决 80% 的更新场景（前端改动最多），零开发量。可作为**阶段 2 之前的临时手段**立即启用。 |
| **三层分层 + 自建更新器**（推荐） | 契合现有架构，改动可控，且你们已有 node 运行时和 SHA256 基础设施。 |

## 四、封装规范化清单（配合增量更新一起做）

### 4.1 打包前

- [ ] **统一版本真相源**：只保留 `package.json` 的 `version`；`secure-win-release.mjs` 的 `releaseName` / `productVersion` 全部改为从它派生（或强制要求传环境变量，缺失即报错而不是静默用默认值）。
- [ ] **发布文案外置**：把 `使用说明.txt`、`更新日志.md` 的内容抽到 `release-assets/` 目录下的模板文件（支持 `{{version}}` 占位符），脚本只负责渲染。这样发版不用改脚本。
- [ ] **混淆加固定 seed**（阶段 1）。
- [ ] **生成 build-manifest.json**（阶段 1）。
- [ ] 发布目录固定：`JINGYIN_WIN_RELEASE_DIR` 默认改为 `D:\RJ\静音AI绘画-WIN（v<version>）`，带版本号，避免覆盖旧包。

### 4.2 打包中

- [ ] 步骤 3 改为"最小兜底集内嵌 + 其余输出到 `app/web/`"（阶段 2）。
- [ ] 构建产物归档：`releases/<版本>/` 保留 `build-manifest.json` + exe，便于回溯"这一版到底发了什么"。
- [ ] 混淆器 `useCodeCache: false` 的坑沉淀进 `docs/发布包记录.md`，换 Node 大版本时先看这条。

### 4.3 打包后

- [ ] `version.json` 增加字段：`runtimeVersion`（node 版本）、`manifestUrl`（更新检查地址）、`minUpdatableVersion`（低于此版本必须整包重装）。
- [ ] 更新器 `updater` 接入启动 bat（`启动（推荐）.bat` 里先跑更新检查再启动主程序）。
- [ ] **回滚演练**：故意放一个坏文件，验证自动回滚能救回来。这条不能省。

### 4.4 源码侧（承接上一轮架构评估）

上一轮发现的源码问题会间接影响封装：

- 98 个跨文件同名函数 → esbuild 不会自动去重，bundle 体积虚高；抽到 `src/shared/` 后 `server.cjs` 会变小，更新包也变小。
- 根目录 42 个 md、`API/`（中转站运维资料）、`server/skill-baselines/`（旧版快照）→ 虽不会被打进包，但建议移出源码树，避免误改和搜索干扰。

## 五、落地顺序建议

| 优先级 | 动作 | 工作量 | 收益 |
| --- | --- | --- | --- |
| P0 | 版本号统一 + 发布文案外置 | 半天 | 发版不再改脚本，消灭一类人为错误 |
| P0 | 混淆加固定 seed + 生成 build-manifest.json | 半天 | 让"变了什么"可计算，差分的前提 |
| P1 | **前端资源外挂（阶段 2）** | 1–2 天 | 更新体积 120 MB → 几十 KB~2 MB |
| P1 | 临时手段：前端改动只发 zip 让用户覆盖 | 1 小时 | 立刻可用，不等阶段 3 |
| P2 | 完整三层分层 + 自更新器 | 1–2 周 | 全自动静默更新 |
| P2 | 回滚演练 + 门禁脚本 | 1 天 | 防止更新把用户的软件搞挂 |

**一句话**：先把"可复现"和"清单"做掉（地基），再把前端资源从 exe 里拿出来（最大收益），最后才做自动更新器。不要一上来就写更新器——在不可复现的构建上做增量，等于在流沙上盖楼。
