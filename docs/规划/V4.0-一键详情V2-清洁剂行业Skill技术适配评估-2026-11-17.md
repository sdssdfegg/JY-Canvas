## 0. 给 Owner 看的结论（白话）

**这份清洁剂专业规则我逐章对着现在的软件看过了：它想解决的问题，正好就是你上次真机指出的那些毛病，方向对、而且写得很细。但它现在还只是一份"专业说明书"，软件里没有它的位置——直接塞进去会出三处对不上。**

1. **行业名字对不上**：新规则要求判成"日化清洁剂"，专业清单里确实写了这个名字，但软件真正查的行业表里**没有这一类**，现在清洁剂是靠"清洁"两个字被算进"家居百货"。要落地，得先让软件认识这个新行业。
2. **"分级"的档位数对不上**：新规则用 6 档判断资料可信度，现在软件只认 3 档。这个不是 bug——当初我们为了先跑通，特意把 6 档合成 3 档，而且已经写好了"怎么换算"。所以不用改软件的分级，只要在新规则里说清楚"判断用 6 档、输出按老规矩折算成 3 档"就行。
3. **测试案例编号会撞车**：新规则里 A/B/C 三个案例的意思，和现在软件测试表里 A/B/C 的意思不一样（比如新规则案例 B 是厨房油污，现有案例 B 是资料不足）。你之前定过"测试清单只留一份"，所以不能两套并存，得先合成一套。

**还有一个形态问题得你拍板**：这份规则把"看商品、判行业、想卖点、排屏幕、管画面、写文案、查质量"全写进了一份文档，而我们软件现在是**8 份分开的**。是要把它拆进现有 8 份里，还是单独加成第 9 份专管清洁剂？这会影响后面怎么改、怎么测。

以下是给负责人/顾问看的技术细节。

## 3. 三处必须裁决的冲突（详细）

### 3.1 🔴 六级事实分级 vs 三级运行时枚举

- **新文档 §3.2** 定义六级：`observed / user_provided / verified / inferred / unknown / prohibited`。
- **当前运行时**：`planning-result.schema.json:59-63` 的 `factLevel` 只允许 `visible / inferred / mustNotClaim`；8 个 Skill 的输出字段全部按三级写（如 `product-understanding/SKILL.md:17-20/30`、`consumer-marketing-strategy/SKILL.md:13/27`、`ecommerce-copy-layout/SKILL.md:24`）。
- **这是既定决策，不是缺陷**：V219 §9 明确把"事实分级六级→三级"列为四项收窄偏差之一，理由是兼容现有 outputSchema 枚举、避免改旧链路。
- **映射层已经存在**：`server/detail-ai.js:45` 的 `V2_CALIBRATION_DIRECTIVES` 第一条已写明换算规则——`observed/user_provided/verified → visible（user_provided 视可靠度记 visible/inferred）、inferred → inferred、unknown → inferred（须标注不可确认）、prohibited → mustNotClaim`，并声明"输出仍只用三级枚举，不改 schema 既有值"。
- **适配结论（三种选项，须 Owner 选）**：
  1. **沿用映射（推荐，零改 Schema）**：新文档按六级做专业判断，注入时沿用 `detail-ai.js:45` 既有映射折算成三级输出。优点：不动 Schema、不动 8 Skill、不动门禁锚点；缺点：六级中的 `user_provided 可靠度细分`、`unknown 须标注` 在三级里表达力弱。
  2. **新增映射指令（小改）**：在 `V2_CALIBRATION_DIRECTIVES` 增一条"清洁剂六级→三级"专项映射，配门禁 phrase 回链；仍不改枚举。
  3. **改 Schema 为六级（大改，不建议）**：推翻 V219 收窄决策，连锁改 8 Skill 输出字段、detail-ai.js outputSchema、`detail-state.js` 白名单、门禁 phrase，违反"不破坏旧版"。
- **未核实**：新文档是否要求六级值**原样出现在最终提示词**？其 §十一只列"策划数据字段"未列分级值落点。若要求原样落地，则在任何选项下都需先解决"三级枚举承载六级语义"的问题。

### 3.2 🔴 行业 `cleaning` 资产已声明、运行时词表缺失

- **资产层已声明**：`industry-routing/SKILL.md:14` 的候选集明确包含 `cleaning（日化清洁剂，V219 §4 六类）`；`:36/40` 规定"衣物 vs 清洗剂按场景词不越权、取日化清洁剂，不加载服装规则"；`product-understanding/SKILL.md:26/42` 同口径；测试集 `:22/33` 案例 A 也要求判日化清洁剂。
- **运行时缺失**：`prompts/server/detail-skills.js` 的 `INDUSTRY_SKILLS`（`:45-160`）只有 `apparel/beauty/food/home/electronics/motherBaby/pet/jewelry/sports/generic` 十类 + generic，**没有 cleaning**。`getIndustrySkillByText`（`:403-412`）按关键词计分，`home.keywords` 含"清洁"（`:82`），故清洗剂当前落进 `home 家居百货`。
- **真机后果**：D-REV-06 P0-1 三屏均输出 `行业识别：家居百货；重点观察：款式结构…袖口/领口/纽扣…` + 服装禁忌——因为 `home` 命中后，行业观察点与禁忌取自 skill 对象；而 apparel 关键词含单字"包/面料/模特"（`:49`），与"包装"形成双路径，无强特征优先。
- **Owner 裁决⑤约束**：G-2 词表禁改，走"新增覆盖层"。因此**不应直接改 `detail-skills.js` 十类表**，而应新增 cleaning 覆盖层条目（与 V219 覆盖层同构），并让 `detail-middleware.js:481 aiIndustry` 的确定性选择消费它、落实"展示行业=规则行业同一决策源"。
- **适配结论**：这是新文档能否成立的**硬前置**——不解决它，文档 §2.1B/§3.1②/§10 案例 A/E 的"零服装规则"要求无法在运行时兑现。属工程可自主项（强特征优先 + 弱语境词不越权），无需专业内容输入。
