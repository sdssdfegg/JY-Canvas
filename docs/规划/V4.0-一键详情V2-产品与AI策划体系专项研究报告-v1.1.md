### 2.4 三个「看起来生效、其实没有」的重点发现

> 这三条是 V2 必须正视的真实缺陷，不是推测。

1. **自定义板块 `customLabel` 落空**：`detail-ai.js:120` 指令要求「可为该屏填 `moduleId=custom` 并在 `customLabel` 写回客户原文」，但 `outputSchema.screens[].moduleId`(:170) 枚举**不含 `custom`**、schema 无 `customLabel` 字段、`normalizeAiScreens`(`detail-middleware.js:130-149`) 不读 ⇒ 该指令无落点。目前自定义板块只靠 `label` 进 `【客户指定内容板块】` 文案行(:550) 起作用。
2. **「顺序影响策划优先级」未真正落地**：`detail-ai.js:117` 写「按 `order` 作为叙事优先级」，但 middleware 的板块消费是 **`selectedSections[index % len]`**（`detail-middleware.js:480,505`），即按屏号循环取板块，`order` 仅用于 :550 的文案数字。客户拖出来的顺序目前**不改变屏序**。

## 4. 同质化问题根因分析

按影响强度排序，全部可定位到代码：

| # | 根因 | 证据 |
|---|---|---|
| 1 | **屏数恒等于 `count`、模块与标题按 `index` 取模轮转** ⇒ 同平台同行业必得同一序列 | `detail-ai.js:88,139`；`detail-middleware.js:318,447,502,513`；`detail-skills.js:421-423`（非首尾屏一律 `coreSellingPoint`） |
| 2 | **无叙事层，strategy 三字段定义后零消费** ⇒ 各屏沦为并列卖点，没有因果递进 | `detail-ai.js:160-166`；`detail-middleware.js:152-189` 只取 `pageRhythm`/`globalStyle` |
| 3 | **每屏 `text` 同构 + 全屏共用恒定光线** ⇒ 视觉表达几乎一致 | `detail-middleware.js:546-568` 固定 17 槽位；`:19` `V1_LIGHT_LINE`；`:565`；`:554` 同一 globalLock |
| 4 | **AI 上下文只有表单白名单，无商品图结构化分析阶段** ⇒ 策划与商品特征弱相关 | `detail-ai.js:123-145`；`:257` 单调用；`detail-middleware.js:266` 自承「未额外调用视觉分析模型」 |
| 5 | **无跨屏去重 + 无视觉 DNA / 构图差异**（v1 默认关） | `detail-middleware.js:502-596` 逐屏独立 map；`:511-512` `screenPack=null`/`variant=null`；`:564-565` 恒定光线 |
| 6 | 词表全硬编码，只拼接不生成 | `detail-skills.js:45-362`；`detail-middleware.js:311-332` |
| 7 | 板块消费 `index % len`，客户顺序不进屏序 | `detail-middleware.js:480,505`（详见 §2.4-2） |
| 8 | AI 输出被丢弃的字段多（qc / strategy / riskNotes / customLabel） | `detail-ai.js:157,162-165,188-192` vs `detail-middleware.js:152-189` |
| 9 | 兜底收敛：缺屏补 `{}`、非首尾屏一律 coreSellingPoint | `detail-middleware.js:131`；`detail-skills.js:423` |

> **一句话结论**：现在不是「AI 不够聪明」，而是**结构层把 AI 的自由度锁死了**——屏数固定、序列取模、槽位同构、叙事字段没被消费。V2 的价值应优先投在「叙事层 + 视觉差异化 + 消费已有 schema 位」，而不是单纯换更大的模型。

## 7. 详情叙事策划规则

### 7.1 判定原则

「勾了 A、B、C」≠「第 1 屏 A、第 2 屏 B、第 3 屏 C」。总策划先产出一条**叙事主线**，再把板块作为「内容素材与优先级」编入屏序；允许合并、拆分、调整先后，但**不得无故忽略客户选择的方向**（延续 V214 §四口径）。

**未选择任何板块时（v1.1 按审查意见 1 明确）**：由 AI 在用户指定的 `count` 屏数内**自主规划**叙事主线、各屏内容任务、顺序与视觉表达，综合商品图可见事实、4 项内容输入、`workflow` 平台节奏与行业 Skill；**不套用固定默认模板，不回退到 `detail-middleware.js:318` 的 `seedTitles[index % len]` 轮转**，也不因缺少板块输入而降低原有生成能力（延续 V214 §四「非必选」口径）。首屏海报仍是默认核心任务。

### 7.2 四种基础叙事（可扩展，不写死）

| 叙事 | 适用信号（Agent 判断依据） | 主线 | 典型屏序节奏 |
|---|---|---|---|
| 痛点解决型 | `productFeature`/`userInstruction` 含问题、困扰、替代方案 | 痛点 → 原因 → 解法 → 证据 → 行动 | 首屏 → 痛点引入 → 功能原理 → 效果 → 收口 |
| 专业品质型 | 材质、工艺、参数、成分信息充分 | 定位 → 工艺证据 → 结构拆解 → 参数 → 信任 | 首屏 → 材质工艺 → 结构 → 规格 → 品牌 |
| 生活场景型 | 场景词丰富、模特/使用方式可选 | 场景代入 → 使用演示 → 多场景 → 适配人群 | 首屏 → 场景 → 操作方法 → 效果 → 选购 |
| 效果展示型 | 有可确认的效果/对比信息 | 结果先行 → 过程 → 对比（有据才用） → 行动 | 首屏 → 效果 → 对比 → 说明 → 收口 |

**选择规则**：由单次模型调用综合 `workflow` 平台节奏(`detail-skills.js:158-269`)、行业 `INDUSTRY_SKILLS`(:45-156)、4 项内容输入、商品图可见事实、客户勾选板块，输出 `narrative: {id, reason, confidence, fallback}`，并给出「为什么不用其它叙事」的一句理由。`confidence` 低时由 AI **自主做保守但非模板化**的规划（明确禁止回退到「核心卖点型」固定序列或现有 `buildScreenTitles` 轮转），**不得强行套用叙事模板**。

### 7.3 叙事数据模型（建议复用已有 schema 位）

```js
// 落在 detail-ai.js outputSchema 的 strategy（:160-166 已有 5 字段，当前零消费）
strategy: {
  narrativeId, narrativeReason,
  copywritingTone,       // :162 已定义未消费 → V2 启用
  platformNotes,         // :163 已定义未消费 → V2 启用
  consistencyRules,      // :164 已定义未消费 → V2 启用
  screenRoles: [{ index, role, sectionRefs[], transitionFromPrev }]
}
```
> 关键判断：**不需要新造一张表**，把 `detail-ai.js:162-165` 三个已定义却被丢弃的字段接上，再把 `detail-middleware.js:152-189` 的 `mergeAiAnalysis` 补上消费即可。这是最小改动路径。

### 7.4 与「不机械凑屏」的机制保证

- 屏数恒等于 `count`（`detail-middleware.js:447`），板块数与屏数解耦——架构上就不存在「为凑板块加屏」。
- `screenRoles[].sectionRefs` 允许多个板块指向同一屏（合并），也允许一个板块跨多屏（拆分）；但 `sectionRefs` 必须覆盖客户所选的全部板块（**覆盖率检查**，见 §10.4 质检）。
- 客户顺序只影响 `sectionRefs` 的先后与首几屏的 `role` 分配，**不再用 `selectedSections[index % len]` 循环**（`detail-middleware.js:480,505` 是必须修的点）。
- **v1.1 补充（审查意见 1）**：屏数仍由用户指定的 `count` 决定，AI 只在该范围内规划内容；「AI 自主决定屏数」是另一个产品决策，本版不涉及。

## 8. 总策划 Agent 与 Skill 架构设计（单次模型调用 + Skill 注入 + 确定性编译）

### 8.1 技术定义：一键详情总策划 Agent = 单次模型调用 + 专业 Skill 注入 + 确定性编译执行

**v1.1 按审查意见 2 更正术语**。本项目所称「一键详情总策划 Agent」的**准确技术定义**是：

> **单次模型调用**（一次 `postChatCompletion`，`detail-ai.js:257`）**＋ 专业 Skill 以静态文本注入模型上下文**（`compactSkillPack` :27-83 与 `skillPack` :146）**＋ 服务端确定性编译执行**（`buildDetailPromptGroup` / `detail-middleware.js:446-655` 的 17 槽位拼装、屏数 clamp、跨屏差异检查）。

**它不是完整 Agent Runtime，本版也不打算做成完整 Agent Runtime**。明确边界：

| 能力 | v1.1 是否具备 | 说明 |
|---|---|---|
| 自主工具调用（tool use / function calling） | **无** | 模型只输出结构化 JSON，不调用任何工具 |
| 循环推理 / 自我迭代（ReAct、多步反思） | **无** | 一次请求一次响应；失败走既有 4 种 mode 降级(`:247-256,273-274`)，不是推理循环 |
| 动态 Skill 调度（运行时按意图挑 Skill） | **无** | Skill 在请求组装期**静态条件注入**，不由模型选择 |
| 多 Agent 编排 / 消息总线 | **无** | 任务书明确不为技术复杂度引入；B 域编排器已搁置且 A 域零 import |
| 确定性后处理 | **有** | 编译、屏数、槽位、去重、质检规则全部在服务端确定性代码里执行 |

**不引入多 Agent** 的理由：① 现有链路只有一次 `postChatCompletion`(`detail-ai.js:257`)，多 Agent 会成倍增加延迟、扣费与失败面；② 任务书明确「不要为了技术复杂度引入多个没有必要的 Agent」；③ B 域（多 Agent/编排器）已被 Owner 搁置，且 A 域零 import。

```
[输入层]  商品图像素 + 22 参数白名单 + 客户板块 + 基础资料
   ↓
[单次模型调用（总策划）]  一次 chat/completions（沿用现有网关/KEY/超时/降级）
   ├─ 商品理解 Skill        （事实分级：可见 / 可推断 / 不可断言）
   ├─ 消费者与营销策略 Skill（购买动机、阻力、决策路径）
   ├─ 内容叙事 Skill        （§7 四种叙事 + screenRoles）
   ├─ 视觉导演 Skill        （§9 DNA + 逐屏差异）
   ├─ 文案策划 Skill        （沿用 copywriting/richness 规则 + tone）
   ├─ 提示词编译 Skill      （复用 detail-middleware.js 的 17 槽位）
   └─ 可选质检 Skill        （独立端点，默认关，见 §10.4）
   ↓
[输出]  group.prompts[].text（与现有结构完全兼容）
```

> 图中 `Skill` 均为**请求组装期静态注入的模型上下文文本**，不是运行时可调度的工具；「提示词编译」「可选质检」由服务端确定性代码执行，模型不做工具调用。

### 8.6 Skill 注入验收标准（v1.1 按审查意见 2 补充）

> **不能仅以「Skill 文件存在」或「import / 加载成功」作为验收**。必须同时证明两件事，且写入 S1 / S3 门禁断言：

1. **真实进入模型上下文**：在 `createDetailAiPlan` 组装完成后、发起 `postChatCompletion` 前，对最终 `messages`（`detail-ai.js:227-233` 的 system + user）做断言——自建 Skill 的**标志性文本片段**必须出现在实际请求体中；对 `compactSkillPack`(:27-83) 的输出做字段级检查，防止像 v1 词表那样把 `composition` / `aliases` / `promptDirectives` 裁掉（§3.3 已有实证：词表存在但从未进上下文）。
2. **对模型输出产生实际影响**：用**同一商品、同一参数、同一随机种子**做 A/B 对照（注入 Skill vs 不注入 Skill），断言输出 JSON 在 `narrative` / `screenRoles` / `visualSpec` / `copywritingTone` 等目标字段上出现可归因差异；并在否定方向做**负向对照**（故意移除注入后门禁必须判红）。
3. **证据留存**：A/B 两次请求体与响应摘要落 `logs/`（脱敏、不含 KEY），随阶段验收报告提交；只提交「模块单测通过 / JSON 结构合法」**不得**判定 Skill 生效。
4. **归因边界**：若 A/B 无差异，须判定是「Skill 未进上下文」还是「进了但指令被忽略」，分别回到第 1 条或指令措辞，不得直接标 PASS。

> 该验收标准的必要性来自 §3.3 的一手证据：`SCREEN_MODULES` 的 `composition` / `aliases` / `promptDirectives` 被 `compactSkillPack`(:61-67) 裁成 5 字段，**从未进模型上下文**；`outputSchema.qc`(:188-192) 与 `strategy` 三字段(:162-165) 定义后服务端零消费。**「文件里有」不等于「发挥作用」**。

## 9. 全局视觉 DNA 与逐屏视觉差异化

### 9.1 全局视觉 DNA（整套统一，写入 `globalLock`）

建议在 `detail-middleware.js:397-408` 的 `globalLock` 条件追加一段 DNA 锁（现状是 `stylePack` 全组风格锁 `:541`，但仅 v2 生效）：

```
【全局视觉 DNA】主体一致性 / 主色与辅色 / 材质质感 / 光线逻辑 /
```

### 9.2 逐屏差异控制维度（v1.1：整组两两比较，非仅相邻屏）

| 维度（v1.1 至少六项） | 控制方式 | 复用资产 |
|---|---|---|
| **composition 构图** | 中心 / 三分 / 对角 / 俯拍 / 特写 / 局部裁切 / 留白偏置 | `composition-variants.js:5-390`（9 模块 × 4 变体） |

| **镜头与景别** | 广角 / 标准 / 微距 / 长焦压缩 / 平视 / 低角度；远景 / 中景 / 近景 / 特写 | `variantFor`(`index.js:40-55`) |
| **场景** | 棚拍 / 家居 / 户外 / 使用现场 / 纯色背景 | `useScenario` 模块 |
| **光影** | 硬光 / 柔光 / 侧逆光 / 轮廓光 / 阴影方向 | `V1_LIGHT_LINE`(:19) 现为恒定 → 改为按屏取 |
| **视觉表达类型** | 产品实拍 / 结构示意 / 场景演绎 / 信息图表 / 对比呈现 / 文字主导 | 需自建字段（审查意见 3 点名） |
| 色彩（辅助维度） | 主色占比、辅色点缀、背景明度、是否单色系 | 风格包 `style-packs.js:7-104` |
| 文字排版（辅助维度） | 标题位置、字号层级、是否留白、信息密度 | dlazy「中文排版四条件」思路（自建实现） |

**执行机制（v1.1 按审查意见 3 重写）**：

1. `visualSpec`（每屏六维度）与 `screenRoles`（每屏叙事角色、板块引用、与上一屏的承接关系）由单次模型调用**一次产出**；确定性编译阶段再结合**跨屏上下文**（已生成屏的 `visualSpec` 摘要 + 全组 `visualDna`）做校验。
2. **对整组页面做两两比较**（`O(n²)`，n = `count` ≤ 12，成本可忽略），**不是只比相邻两屏**：任意两屏在 `composition` / `subjectPosition` / `镜头与景别` / `场景` / `光影` / `视觉表达类型` 六维度上不得出现完全相同的组合；相似度超阈值即判冲突并记录 `dedupLog`。
3. **差异化不得破坏商品逻辑**：冲突消解优先更换「视觉表达类型 / 镜头 / 光影 / 场景」，**不得为了差异而改动该屏的商品事实、板块归属或叙事角色**；不得只换标题、换背景色或随机改构图来凑差异。每屏差异必须能由 `screenRoles` 解释「为什么这样表达」。
4. **现有构图变体用完后应重新规划，而不是机械轮换**：`MODULE_VARIANTS` 为 9 模块 × 4 变体(`composition-variants.js:5-390`)，若某模块变体在整组内耗尽仍有冲突，应回到 `visualSpec` / `screenRoles` 层重新规划该屏的表达任务（或合并该屏内容），**禁止 `index % 4` 机械取下一个变体**——这正是 §4 根因 1 的同质化机制，不能换个地方复现。
5. 所有冲突与重规划只写 `dedupLog` 与建议，**不静默改写客户已确认的 `prompt.text`**（§1.5 展示=生图）。

### 9.3 复用而非重造

- `prompts/server/detail-skills-v2/composition-variants.js` 已有 390 行、9 模块 × 4 变体，`variantFor`(:40-55) 已有按模块取变体的逻辑——V2 只需**把 v1 默认关的开关打开或按新 DNA 层调用**，不必另写一套变体库。

### 9.4 跨屏去重执行器（当前完全缺失）

在 `buildDetailPromptGroup` 生成 `prompts[]` 之后、返回前，增加一次纯函数遍历：**整组两两比较**（非相邻比较）§9.2 的六个视觉维度 + `title` / `selling` / `copywriting` 归一化相似度；冲突按 §9.2 第 3–4 条消解（优先换表达方式、不破坏商品逻辑、变体耗尽则重规划），记录 `dedupLog`（只写日志、不静默改客户已确认内容）。证据：现状 `detail-middleware.js:502-596` 逐屏独立 map，只有 `uniqueList`(`detail-skills.js:389-393`) 做单层去重，**无任何跨屏比较**。

### 10.3 可选质检（任务书 F；v1.1 按审查意见 4 分层）

#### A. 已确认的产品决策（Owner 任务书 + 已定口径，v1.1 不改动）

#### B. 架构建议（**待 Owner 裁决，不是已确认决策**）

> 外部架构顾问建议：用户**主动点击质检后**，执行「模型质检 + 本地确定性规则检查」。以下为该建议的成本、质量收益与取舍，供裁决；**本版不把它写成用户已确认的决定**。

| 项 | 内容 |
|---|---|
| 建议做法 | 点击后并行/串行执行：① 本地确定性规则（禁虚构词表、板块覆盖、首屏存在、整组两两差异、平台合规）；② 一次模型质检（复用同一网关与 KEY，不新增通道） |
| 质量收益 | 模型能发现本地规则覆盖不到的语义问题（文案语气不一致、图文不符、叙事断裂、无证据的具体断言）；本地规则稳定、零成本、可回归 |
| 成本 | **模型质检会产生额外一次模型调用及费用**，并增加一次等待与失败面；必须在 UI 点击前**明确提示可能产生额外模型调用及费用** |
| 取舍 | 若只做本地规则：零成本、零等待，但语义类问题漏检；若加模型质检：质量更完整但有成本。**建议默认只做本地规则，模型质检作为点击后的显式二次确认**，是否启用仍待裁决 |
| 回退 | 任一路径失败只返回「质检不可用」与本地规则结果，**不得阻断生图**，回落现有链路（§12.4 风险 4） |

#### C. 接口与返回（沿用 v1.0 设计，不因分层改变）

- 建议端点 `POST /api/detail-prompts/quality-check`，入参整组 `prompts[]`（+ `planningContext`，见 §10.2.1），返回：
  ```js
  { ok, findings: [{ screenIndex, type, severity, evidence, suggestion, source: "local"|"model" }], summary }
  ```

  `type` 覆盖：事实越界（无证据的材质/认证/对比/销量）、跨屏重复、板块覆盖缺失、首屏缺失、DNA 冲突、平台合规、文案语气不一致。
