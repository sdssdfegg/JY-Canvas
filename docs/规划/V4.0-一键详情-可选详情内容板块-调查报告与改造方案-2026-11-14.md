## 1. 结论摘要（先给判断）

1. **需求可落地，且现有架构恰好支持「不机械凑屏」**：分屏数量由基础参数的「生成数量」决定（`detail-middleware.js:447`），板块只影响每屏的内容方向与文案侧重。因此「一个板块 ≠ 一张图」「不为凑板块数机械加屏」是**机制性保证**，不靠提示词自觉。
2. **真正进入 Agent 的关键只有一个白名单**：`detail-ai.js:112-129` 逐字段挑 `input`，不是整包透传。板块字段必须显式加在这里，否则前端勾得再好，AI 也看不到——这是「不能只做前端勾选」的技术分水岭。
3. **服务端已有防虚构约束**（`detail-ai.js:101,104`、`detail-skills.js` 多处 `qcRules`/`taboos`），本方案不新写一套，只在新增指令里引用并针对「品牌背书 / 对比 / 参数」三类高风险板块点名强化。
4. **必须绕开两处禁改**：`prompts/server/detail-skills.js`（`server/routes/detail.routes.js:27-33` G-2 历史决策 + V213 §3）、`src/features/detail/detail-image-form.js`（V213 §3 + 被 B 域复用）。本方案**两者均零改动**。
5. **数据落点裁决：不进 `detailSettings`**。否则会随预设 / 分组持久化、并随发布种子扩散（`src/shared/release-seed.js:144-146`），污染历史数据与封装边界。改为 `useState` 会话态，生成时显式条件注入 payload。
6. 本方案预计 **新增 2 个文件、修改 6 个文件**（含 1 份索引文档），零改动清单见 §8.3，调用链路增量 4 处注入点，详见 §8 / §9。

## 4. 调查中的四个决定性发现

### 4.1 服务端已有「内容板块」真相源，且禁改

`prompts/server/detail-skills.js:271-362` 定义 `SCREEN_MODULES` 9 个：`hero` 首屏主视觉 / `painReverse` 痛点反转 / `coreSellingPoint` 核心卖点 / `materialDetail` 材质细节 / `useScenario` 使用场景 / `specInfo` 参数说明 / `trustProof` 信任背书 / `conversionClose` 收尾转化 / `fitStructure` 版型结构。每个含 `aliases / purpose / composition / promptDirectives / qcRules`。

它们**已经是** AI 的 `moduleId` 枚举（`detail-ai.js:158`）、已注入 `skillPack.modules`（`detail-ai.js:61-67`）、已用于每屏取 `moduleSkill`（`detail-middleware.js:492-494`）。而 `server/routes/detail.routes.js:27-33` 明令「不得改动 `prompts/server/detail-skills.js`（G-2：一键详情/主图保留完整规则集）」，V213 §3 同样列为禁改。

⇒ **裁决：预设板块以这 9 个 `moduleId` 为锚，前端 12 项做映射，绝不新增第二套板块体系。** 这正是「结合现有生成逻辑判断最终分类命名、不为分类过度复杂化」。

### 4.2 所谓 Agent 是「单次 LLM 出结构化 JSON + 确定性模板拼装」

`detail-ai.js:228-286` 是单次 `postChatCompletion`，无工具调用、无多轮、无反思；`detail-middleware.js:490-578` 用模板确定性拼出每屏 `text`。所以「让 Agent 理解板块」= ① 把板块写进送模型的 `textPayload`；② 在 `outputSchema` 层面要求 `screens[].moduleId` 按板块分配；③ 模板层兜底也认板块。三者缺一都可能出现「AI 懂了但提示词没变」或「有 KEY 生效、无 KEY 不生效」。

### 4.3 防虚构约束已存在，不需要重写

`detail-ai.js:101`「不要凭空发明材质、参数、认证、疗效、销量、品牌背书」、`:104`「无法从图片确认则写保守描述，不要假装确定」；`detail-skills.js:287`（不制造虚假效果）、`:326`（不虚构未提供参数）、`:337,339`（不能虚构认证/销量/机构）、`:370,381`（虚假卖点/认证）。本方案只在新增指令里**引用并点名强化**三类高风险板块，不新增第二套规则。

### 4.4 屏数机制天然保证「不机械凑屏」

`detail-middleware.js:447` 屏数恒等于 `count`（由 `BASE_SKILL.screenCountRule` 与 `DEFAULT_COUNT` 定界，前端默认 10）。板块数量无论是 0、3 还是 12，屏数都不变；板块只改变每屏的 `moduleId` / `title` / 文案侧重。因此「不得为了满足板块数量机械凑屏」「可合理拆分合并」在架构上自动成立，只需在指令里写清「按 order 作为叙事优先级，允许同模块承载多个侧重、允许合并，禁止一板块一屏」。

# 第二部分 · 改造方案

## 6. 产品口径裁决：预设板块最终分类与命名

**裁决：保留 Owner 给出的 3 组 12 项 UI（不擅自删客户要的选项），每项携带一个既有 `moduleId`；服务端只认 `moduleId + label + order`。** 分组只用于弹窗视觉归类，不进入数据结构、不产生嵌套实体。

| 组 | 客户可见板块 | 映射 `moduleId` | 说明 |
|---|---|---|---|
| 产品核心展示 | 产品功能展示 | `coreSellingPoint` | 与「优势卖点」同模块，label 区分侧重 |
| | 产品材质细节 | `materialDetail` | 一一对应 |
| | 产品结构拆解 | `fitStructure` | 一一对应 |
| | 产品优势卖点 | `coreSellingPoint` | 同上 |
| 使用与体验 | 实际使用场景 | `useScenario` | 一一对应 |
| | 使用方法说明 | `useScenario` | 同模块，label 区分 |
| | 使用效果展示 | `painReverse` | 效果/前后对比走痛点反转，受「不虚构效果」约束 |
| | 适用人群与对象 | `useScenario` | 同模块 |
| 辅助决策 | 产品对比展示 | `specInfo` | 受「不虚构对比结果/参数」约束 |
| | 规格参数说明 | `specInfo` | 一一对应 |
| | 品牌故事与背书 | `trustProof` | 受「不虚构认证/资质/机构」约束 |
| | 购买须知与注意事项 | `conversionClose` | 结构性收尾模块，勾选时作为叙事权重，不新增屏 |

**为什么不让 `hero` / `conversionClose` 成为独立新增屏**：这两者是详情页结构性屏（首屏/收尾），由 `screenTitles` 的既有 rhythm 固定；客户勾选只影响叙事权重，不改变屏数。

**关于「多对一」**：多个板块共享同一 `moduleId` 时，AI 仍收到 12 个不同 `label` 与 `order`，指令明确「label 是客户具体侧重，按 label 组织该屏文案与画面；moduleId 仅用于选取构图/质检规则；同一 moduleId 可出现在多屏，按 order 分配」。这样客户的每一项选择都真实影响策划，且模板层仍能查到 `moduleSkill`。

**可选精简案（不推荐改动链路，仅供 Owner 拍板）**：若认为 12 项过密，第一版可收敛为 7 项（排除 `hero`/`conversionClose` 两个结构性模块后的 7 个 `moduleId`），只改前端常量表，**数据结构、调用链路、服务端注入点全部零改动**。

### 6.1 弹窗文案与交互规格

- **标题**：`选择详情展示板块`；**副标题**：`勾选你希望详情页重点展示的内容，可多选并调整顺序。`
- **入口按钮**：`选择内容板块`（基础参数区独立行，`size="sm"` 次级样式，不做成主操作按钮、不加必选标记）。

**防虚构**（对应 Owner §5）：
