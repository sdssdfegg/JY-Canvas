## 1. 目标与四条硬约束

Owner 本轮诉求可归为四条硬约束，后续任何功能方向都不得绕过：

1. **可回退**：详情板块更新出问题时，能按「整仓 / 域 / 阶段 / 单文件」四级回退，且回退不带走其他板块的改动、不破坏用户数据。
2. **归置分类有序**：文件按域、按层、按职责落位；同类文件不散落；命名统一；新增文件有唯一允许落点。
3. **视觉统一不破坏**：沿用既有设计令牌与共享组件，不改名、不迁移既有样式类，新增内容不得引入第二套视觉体系。
4. **零外溢、可剔除**：详情域的改动不得影响快捷生成、批量换装/改色、参考生图、AI 无限画布、视频、提示词助手；整体删除任一详情子域时，其他板块零改动即可继续运行。

第五条是对上述四条的元约束：**文档与流程本身也必须有序**。Owner 明确「不管给出什么调整优化方案，都不能随便让文档归置混乱，修改调整必须有序规范」。因此本规划把「变更秩序」写成可执行管道（§5）与可验证门禁（§6），而不是写成一句口号。

**本规划不做什么**：不定义任何具体功能优化内容（方向由 Owner 后续给出）；不在本轮改业务代码；不替代 V213 执行单；不调整门禁判据；不搬迁或改名任何存量文档。

## 3. 目标架构

### 3.1 域边界定义

```
detail-domain（详情域）
├── 子域 A：一键详情/主图  detail-main      ← 可独立插拔、当前冻结
├── 子域 B：详情创作      detail-studio     ← 可独立插拔、当前活跃
└── 共享内核 K（不属于任何子域，也不许被反向依赖）
    ├── 形态层：src/shared/ui/**、src/styles/tokens.css
    ├── 能力层：src/api/client.js、images.js、config.js、server/core/**
    └── 契约层：buildDetailImageForm 等被两域共用的纯函数 / 常量
```

**核心裁决**：共享内核必须**去归属化**——`detail-image-form.js` 现状放在 `src/features/detail/`（A 域私有目录）却被 B 域依赖，属于归属错误。目标态把它提升到 `src/shared/`（或域级 `_kernel/`），并把 `source` 白名单改为参数注入，使 A、B 两域各自只依赖 K，互不依赖。同理，`prompts/server/detail-skills.js` 的 `getPlatformSkill` 被 B 域规划链引用，也须判定归属后收口。

> 该动作与 V213 §3 零改动清单（把 `detail-image-form.js` 列为禁改）**直接冲突**，因此列为阶段 1 的 Owner 裁决项（§9-3），未裁决前一律不动。

### 3.2 目录归置与命名分类规范

| 层 | 允许落点 | 命名规则 | 禁止 |
|---|---|---|---|
| A 域视图/状态 | `src/features/detail/` | `detail-*.jsx` / `detail-*.js` | 新增非 `detail-` 前缀文件、放 JSX 到其它 feature |
| B 域业务区 | `src/features/detail-studio/<区>/` | 沿用 README 的 `constants / state / components / intake / planning / generation / versions / styles` 八区 | 新建未登记目录、跨区直接 import |
| B 域状态出口 | `src/features/detail-studio/state/` | 唯一 `use-detail-studio-state.js` | 第二套状态源 |
| 前端网络出口 | `src/api/detail-studio.js` / `src/api/prompts.js` | 一个域一个出口文件 | 组件直拼 `/api/...` URL、feature 内裸 fetch |
| 服务端装配 | `server/app.js` + `server/routes/*.routes.js` | `registerXxxRoutes` | 路由内写业务、第二次 `express()` |

**单文件体量**：沿用 B 域 README 的「区内单文件 ≤300 行、先区内拆」。当前超标：`state/use-detail-studio-state.js` 724、`styles/detail-studio.css` 1898、`versions/VersionPanel.jsx` 374、`planning/PlanningPanel.jsx` 311、`server/.../orchestrator.js` 540、`project-store.js` 464。阶段 3 先拆后搬，避免整块搬迁引发 TDZ 与基线漂移。

### 3.3 依赖方向（单向 DAG）

```
其它 feature ────禁止────▶ A 域 / B 域 私有目录
A 域 / B 域 ────允许────▶ 共享内核 K（shared/ui、api/*、core/*）
A 域 ──────────禁止────▶ B 域私有目录（反之亦然；只允许经 K）
共享内核 K ─────禁止────▶ 任何 feature（防反向依赖与 public 初始化期 TDZ）
装配层 ─────────允许────▶ 各域入口（且只经声明式清单）
```

已知必须消除的违规边：`src/api/detail-studio.js:7 → features/detail/detail-image-form.js`（跨子域）、`detail-image-form.js:3,28 → detail-studio source 白名单`（K 反向依赖 feature）、`analyze-strategy.js:32 → prompts/server/detail-skills.js`（归属待裁决）、`VersionPanel.jsx:35` 直拼 URL（出口非唯一）、`use-detail-studio-state.js:6` 与 `detail-studio-generate.js:13` 旁路直连 `api/config.js` / `api/images.js`（须收进出口或登记为例外）。

### 3.4 可插拔契约：注册点与剔除流程

**契约**：任一子域的启用/停用，只允许通过一张声明式清单完成；装配层不得再出现域名硬编码。清单至少包含：视图 id、导航项、lazy 组件工厂、渲染分支、App 级状态适配器、服务端路由注册器、API 前缀、存储键前缀、数据目录、专属 verify 脚本与基线条目。

**剔除一个子域的标准动作**（以 A 域为例）：

1. 按附录 A 的「专属可删」清单删除目录；
2. 在清单中把该子域标为 disabled（**装配层零改动**）；
3. 同步移除该子域专属 verify 脚本在 `run-all.mjs` ORDER / FAST_ORDER 的登记，并刷新 3 份基线 JSON；
4. 跑 `check-syntax` + `run-all --fast` + `vite build`；
5. 跑**其他板块冒烟**：快捷生成、批量换装/改色、参考生图、AI 无限画布、视频、提示词助手，目视 + 关键交互；
6. 跑 public 生产构建首启动冒烟（静态门禁抓不到初始化期 TDZ 白屏）。

**影子摘除演练**（阶段 2 / 4 的验收手段）：在临时沙盒副本里执行上述 1–4 步并跑门禁，主工作区不动；用「删除后仍全绿」证明零外溢。演练脚本只读源码、输出报告，不修改仓库。

**业务语义的「删除」另有一条红线**：客户自行删/改详情页面时，以用户当前状态为准，不强改、不恢复默认；删除留痕按项目既有机制（留痕键 + 跨家族才 forget）处理，不因工程重构被清空。工程剔除 ≠ 用户页面状态清理，两者不得混为一谈。

### 3.5 视觉统一规范（不破坏原本视觉）

1. **唯一令牌源**：`src/styles/tokens.css` 是唯一 `:root`。颜色 / 间距 / 圆角 / 层级一律用 `var(--…)`；已有 `hardcoded-color-check` + `theme-token-parity-check` 兜底。
2. **唯一组件源**：按钮、弹窗、面板、分区标题一律用 `src/shared/ui/`；`legacy-button-ratchet` 已把旧类归零，不得回潮。
3. **共用类冻结登记**：`src/styles.css` 的 `.detail*` 段被 `ReferenceRemixView` 与 `DetailUploadZone` 复用，**不改名、不迁移、不删**。登记进附录 A「共享不可删」，详情迭代只准新增、不准修改这些选择器；若将来真要剔除 A 域，共用类保留并下沉到形态层。
4. **新增样式前缀**：A 域新增类用 `.dm-*`，B 域继续 `.detailStudio*`；禁止跨子域复用对方前缀，禁止用无前缀通用类名（如 `.panel`、`.row`）。
5. **每次迭代的视觉验收**：旧「一键详情/主图」目视零回归 + 其他板块冒烟；涉及 CSS 的改动必须附改动前后对照说明，禁止「顺手统一一下样式」式的扩大范围。

| 级别 | 场景 | 手段 | 风险 |
|---|---|---|---|
| L0 整仓 | 整条迭代线废弃 | 在专用分支上 `git revert <阶段 commit 区间>`（推荐，保留历史）；或 `git reset --hard detail-domain-baseline-20261114` | `reset --hard` 会一并抹掉同期其他板块改动，**只允许在专用分支 / 确认无其他改动时用** |

| L3 单文件 | 局部回退 | `git checkout <tag> -- <单文件>` | 需重跑 `check-syntax` + `--fast` + `vite build` |

### 4.3 每阶段打点规范

- 一阶段一执行单、一 commit 一 tag；tag 名 `detail-domain-phase<N>-<YYYYMMDD>`，message 必含：阶段号、HEAD、改动文件数、门禁实测数字、真机补验状态、关联执行单路径。

- 基线 tag **永不移动、永不 force 更新**；需要新基线时另建新 tag。

### 4.4 回退前检查清单（缺一不可）

1. `git status --short` 干净；若有其他板块未提交改动，先 `git stash push -- <文件>` 隔离，回退后 `pop`。
2. 先建 `backup/pre-rollback-<YYYYMMDD>` 指向当前 HEAD。
3. 确认 `data/`、`logs/`、`tmp/` 不在回退范围；确认没有未审批的 `schemaVersion` / 项目 JSON 迁移。
4. 回退后按 §6.3 分层验收，至少跑 `check-syntax` + `run-all --fast` + `vite build` + 其他板块冒烟。
5. 涉及 public 生产构建的，必须补一次首启动冒烟（初始化期 TDZ 静态门禁抓不到）。
6. 回退后同步 `docs/规划/README.md` 索引与三处状态字段，防止文档停留在旧状态。

### 4.5 禁止项

- 禁止在含其他板块未提交改动的工作区直接 `git reset --hard`。
- 禁止用 `--no-verify` 绕过 pre-commit。

## 5. 文档归置与变更秩序（本轮重点）

### 5.1 落点表：不搬迁存量，只补规则

| 文档类型 | 唯一落点 | 命名规则 | 归档 / 回填义务 |
|---|---|---|---|
| 执行单 | `docs/执行单/进行中/` → 交付当天 `docs/执行单/已完成/<YYYY-MM>/` | `V4.0-执行单-Vxxx-详情域-<主题>.md` | 移单 + 回填 `docs/执行单/README.md` 总表 + 回填域索引 |
| 方案 / 规划 / 架构契约 | `docs/规划/` | `V4.0-详情域-<类型>-<主题>-YYYY-MM-DD.md` | 域索引登记一行 |
| 设计 | `docs/设计/` | `V4.0-详情域-设计-<主题>-YYYY-MM-DD.md` | 域索引登记一行 |
| 验收 / 复盘 / 阶段报告 | `docs/复盘/` | `V4.0-详情域-<阶段>-验收报告-YYYY-MM-DD.md` | 域索引登记一行 |
| 状态快照 / 索引 | `docs/规划/README.md` | 单文件，原地更新 | **不另建第二份状态表** |
| 契约台账（历史、只读） | `docs/存档-台账/` | 沿用既有 | 冻结后只读，不改 |

三条铁律：

1. **不搬迁、不改名存量文档**。历史上已多次因搬迁/改名造成指针失效与文档漂移；本轮用「索引指向原位置」解决散落，不制造新的迁移风险。
2. **不新建平行索引**。详情域唯一指针总表就是 `docs/规划/README.md`；执行单总表、NEXT 指针各司其职，不复制彼此内容。
3. **根目录不新增 md**（AGENTS.md 限定 5 份常设），md 全部纳入 git 跟踪；仓库相对路径，禁止写死本机绝对路径（`docs-path-check`）。

### 5.2 唯一索引与同批回填

`docs/规划/README.md` 至少维护三张表：① 详情域文档登记表（编号 / 类型 / 路径 / 阶段 / 状态 / 关联 commit / 更新日期）；② 阶段状态表（阶段 0–6 唯一状态真相源）；③ 待裁决事项表。

**同批回填义务**：任何详情域文档的新建、移动、归档、状态变更，必须与触发它的代码/文档改动在**同一个 commit** 里回填索引；未回填视为该阶段未完成，不得打阶段 tag。三处状态字段（域索引阶段状态表 / 执行单抬头 / `docs/ai-tryon/NEXT.md` 在跑单指针）必须逐字一致——项目已三次因口径漂移返工。

### 5.3 任何需求都走同一条管道（七步）

> Owner 后续给出的任何调整优化方向，无论大小，都不改变这条管道；只改变「执行单里的需求内容」。

| 步 | 动作 | 产出 / 门禁 |
|---|---|---|
| 1 需求登记 | 写进域索引「需求池」，一句话 + 提出时间 | 不新建文档 |
| 2 归属判定 | 判定落在 A 域 / B 域 / 共享内核 K / 装配层；判定文档类型与落点 | 执行单首屏「归属与落点声明」 |
| 3 影响面声明 | 列出会碰的注册点、共用类、共享内核、门禁基线、真机项；明确零改动清单 | 影响面表（含「不影响哪些板块」的反向声明） |

**规模护栏**：单张执行单只做一个逻辑改动；一个阶段一张单；禁止把「顺手改一下样式 / 顺手整理文档」夹带进功能单；禁止在功能高峰期启动状态分层等架构级重构。
