## 1. 目标与四条硬约束

Owner 诉求可归为四条硬约束，后续任何功能方向都不得绕过：

1. **可回退**：A 域改出问题时，能按「整仓 / 域 / 阶段 / 单文件」四级回退，且回退不带走其他板块的改动、不破坏用户数据。这是本轮最直接的诉求。
2. **归置分类有序**：文件按域、按层、按职责落位；同类文件不散落；命名统一；新增文件有唯一允许落点。
3. **视觉统一不破坏**：沿用既有设计令牌与共享组件，不改名、不迁移既有样式类，新增内容不得引入第二套视觉体系。
4. **零外溢、可剔除**：A 域改动不得影响快捷生成、批量换装/改色、参考生图、AI 无限画布、视频、提示词助手；**将来整体删除 B 域时，A 域与其他板块零改动即可继续运行**。

第五条是元约束：**文档与流程本身也必须有序**。Owner 明确「不管给出什么调整优化方案，都不能随便让文档归置混乱，修改调整必须有序规范」。本规划把「变更秩序」写成可执行管道（§5）与可验证门禁（§6），不是一句口号。

**范围边界（v1.1 新增）**：

- 施工对象只有 A 域。B 域本轮**只读、不改、不修、不补**，它已经「开发出一些问题」，不为它投入任何修复成本。
- B 域的价值是**参考**：页面框架、分区组织、组件拆分思路可供 A 域借鉴，借鉴方式受 §3.3 约束。
- B 域的终态是**整体删除**，不是继续迭代、不是与 A 域合并、不是双轨并存。

**本规划不做什么**：不定义任何具体功能优化内容（方向由 Owner 后续给出）；不在本轮改业务代码；不做全仓级架构重构（v1.0 的装配注册化、目录归置、双域解耦等阶段全部取消）；不调整门禁判据；不搬迁或改名任何存量文档。

## 3. 目标架构

### 3.1 域边界定义（v1.1 重写）

```
detail-domain（详情域）
├── 子域 A：一键详情/主图  detail-main    ← 唯一迭代对象，长期保留
├── 子域 B：详情创作      detail-studio   ← 冻结参考实现，终态整体删除
└── 共享内核 K（A 域依赖；B 域只读借用，随 B 删除而消失）
    ├── 形态层：src/shared/ui/**、src/styles/tokens.css
    ├── 能力层：src/api/client.js、images.js、config.js、server/core/**
    └── 契约层：buildDetailImageForm 等 A 域自有、被 B 域借用的纯函数 / 常量
```

**核心裁决（与 v1.0 相反）**：因为保留 A、删除 B，**不做对称解耦、不做去归属化**。

- `detail-image-form.js` 继续留在 `src/features/detail/`，归属正确，无需提升到 `src/shared/`，无需改 `source` 白名单为参数注入。
- B→A 的两条引用（`src/api/detail-studio.js:7`、`analyze-strategy.js:32`）随 B 域一起删除，A 不受影响。
- A→B 的唯一残留是 `detail-image-form.js:3,28` 的 `detail-studio` 字符串白名单，删 B 时清除即可（那时 V213 已冻结，零改动清单自然解除）。
- `prompts/server/detail-skills.js` 与三个活壳继续服务 A 域，**不随 B 域删除**。
- 结论：**终态摘除 B 域时，A 域业务代码零改动**；要动的只有装配层、质量网与文档。

### 3.2 目录归置与命名分类规范

|---|---|---|---|
| A 域视图 / 状态 | `src/features/detail/` | `detail-*.jsx` / `detail-*.js` | 新增非 `detail-` 前缀文件、把 A 域 JSX 放到其它 feature |
| A 域样式 | `src/styles.css` 的 `.detail*` 段 | 新增类用 `.dm-*` 前缀 | 改 / 删既有共用选择器、新建 `:root` |

| A 域前端出口 | `src/api/prompts.js`、`images.js`、`save.js` | 沿用现有出口 | 组件直拼 `/api/...` URL、feature 内裸 fetch |
| A 域服务端 | `server/detail-ai.js`、`detail-middleware.js`、`routes/detail.routes.js` | 沿用现有 | 在路由内写业务、第二次 `express()` |

**新增文件三问**（写进执行单首屏）：是否属于 A 域？属于 A 域哪一层？是否应放共享内核？三问答不出 → 不得新建文件。**B 域不参与判定，因为它不再接收新文件。**

**单文件体量**：B 域超标的 `state 724` / `CSS 1898` / `VersionPanel 374` / `PlanningPanel 311` 等**不再拆分**（要删的代码不投入）。A 域 `DetailView.jsx` 616 / `detail-state.js` 654 若迭代中明显膨胀，按「先区内拆、再谈归位」处理，不与功能改动混在同一 commit。

### 3.3 依赖方向与借鉴纪律（v1.1 重写）

```
其它 feature ────禁止────▶ A 域 / B 域 私有目录（现状已满足）
A 域 ──────────禁止────▶ B 域私有目录（借鉴纪律，硬红线）
B 域 ──────────允许────▶ A 域共享件（现状，随 B 删除而消失，不再治理）
A 域 ──────────允许────▶ 共享内核 K（shared/ui、api/*、core/*）
共享内核 K ─────禁止────▶ 任何 feature（防反向依赖与 public 初始化期 TDZ）
装配层 ─────────允许────▶ A 域 / B 域入口（B 的入口在阶段 3 摘除）
```

**借鉴纪律（本轮最重要的一条新规矩）**：B 域的页面框架逻辑可以借鉴，但**A 域不得 import B 域任何文件、不得复制一段仍依赖 B 域 state / api / 组件的代码进来**。否则等阶段 3 删 B 时，A 域会一起断掉——这正是「后期删除不影响」最容易踩的坑。

允许的三种借鉴方式：

| 方式 | 做法 | 落点 |
|---|---|---|
| ① 复制思路 | 看懂分区 / 交互 / 状态组织后，在 A 域用 A 域自己的状态与 api 重写 | `src/features/detail/` |
| ② 沉淀共享 | 确实与域无关的纯函数 / 常量，抽到共享层，A 域引用；B 域现状引用随它一起删 | `src/shared/` |
| ③ 人工参考 | 只看不改，不落代码 | 无需落点 |

每次借鉴必须在 `docs/规划/README.md` 需求池登记「来源文件 → 借鉴方式 → 目标落点」，并在执行单首屏声明；由 `detail-domain-borrow-check.mjs` 机器校验 A 域零 B 域 import。

### 3.4 终态摘除 B 域的标准流程（阶段 3）

## 5. 文档归置与变更秩序（Owner 元约束）

### 5.1 落点表：不搬迁存量，只补规则

| 文档类型 | 唯一落点 | 命名规则 | 归档 / 回填义务 |

3. **根目录不新增 md**（AGENTS.md 限定 5 份常设），md 全部纳入 git 跟踪；仓库相对路径，禁止写死本机绝对路径（`docs-path-check`）。

**同批回填义务**：任何详情域文档的新建、移动、归档、状态变更，必须与触发它的代码/文档改动在**同一个 commit** 里回填索引；未回填视为该阶段未完成，不得打阶段 tag。三处状态字段（域索引阶段状态表 / 执行单抬头 / `docs/ai-tryon/NEXT.md` 在跑单指针）必须逐字一致——项目已三次因口径漂移返工。
