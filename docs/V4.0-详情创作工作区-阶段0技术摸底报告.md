## 0. 结论摘要

1. **最重要的发现：JY-Canvas 已有统一的文本大模型调用能力。** `server/core/ai-chat-shared.js:151 postChatCompletion({baseUrl, apiKey, body, signal})` → `${baseUrl}/chat/completions`，已被 7 个现有 LLM 入口复用（`detail-ai.js`、`quick-prompt-ai.js`、`reference-ai.js`、`outfit-pose-ai.js`、`outfit-master-fit-ai.js`、`outfit-quality-ai.js`、`ai-canvas-agent.js`）。KEY 统一 `resolveApiKey(payload.apiKey)`，网关统一 `channelBaseCandidates()`。**因此三种创作模式的「AI 策划」可以完全复用现有模型体系，不需要、也不允许引入第二套 Provider / API Key。**
2. **五个开源项目没有一个是可直接整体复用的。** 全部是 MIT，但技术栈与 JY-Canvas（React 19 + Vite 7 + Express 4 + 纯 JSON 文件存储 + 无数据库 + Node 24）全线不兼容：MxPage / banana-mall 是 Next 14 + Prisma/SQLite + Electron + LangGraph 重栈；product-shots / ecommerce-skills / Gayaya999 是 Agent Skill 文本资产或 Python 脚本原型。
3. **MxPage 与 banana-mall 是同一代码库的两个时间快照**，不能当成两套独立资产重复计入。MxPage 是超集与演进版，工作流与数据建模以其为准；banana-mall 仅作精简版对照。
4. **推荐路线：借流程与数据结构，不借技术栈。** 以 MxPage V4 确定性工作流为流程蓝本（状态机 / 请求账本 / 租约 / 提示词冻结），以 product-shots + ecommerce-skills + Gayaya999 的结构化规则表为内容蓝本，在 JY-Canvas 现有 Express + JSON 文件存储之上自建轻量工作区。**不移植 Prisma / Next / LangGraph / Electron / Python / 任何 Provider 适配层。**
5. **现有详情模块的选项不是 UI 摆设。** `server/detail-middleware.js` 已把 `richness / copywriting / fontStyle / modelMode / modelUsage / reverseScreens / workflow / stylePackId` 逐字段注入服务端提示词（如 `:289 richnessPolicy`、`:299` 「本屏无模特，禁止出现真人」硬约束、`:405 buildGlobalLock`），并在 `:590-610` 回写结构化字段。这恰好是任务书 §七「结构化参数传递机制」的现成范式，可直接提炼，不必从零设计。
6. **需先补齐三个公共能力缺口才能开工**：通用持久化任务存储层、通用文本规划端点、独立的项目/版本资产目录。其中「抽取通用任务存储层」属于新增公共模块，按任务书 §十七 必须提前上报。
7. **发现一处任务书与现有架构的口径冲突**：任务书 §十 要求「初期不人为设置固定并发数量上限」，但现有 `server/core/image-concurrency.js` 对全部图片请求施加进程级 `IMAGE_CONCURRENCY_LIMIT=5` 全局闸门。需 Owner 裁决。

- `references/platform-profiles.json`：12 平台结构化规则，含 `schema_version / researched_at / reverify_after_days:90 / evidence_levels` 与每项 `export{canvas_width,...} / image_text_policy / ai_visual_policy / information_density / module_preferences / hard_rules[{rule,evidence,verified_at}] / sources[]`。

### 3.2 三种模式的硬隔离（任务书 §四 / 禁止事项 5、6）

`mode` 为项目创建时确定、**不可变**字段：`guided` / `assisted` / `direct`。

| 模式 | 允许的 AI 处理 | 明确禁止 | 技术保障 |
|---|---|---|---|
| A `guided` | 4 阶段主动追问（借 product-shots `BriefState` / completeness / suggestion chips）→ 商品分析 → 策划 → 分屏 | 不得虚构功效、参数、认证 | 服务端 `planner/` 专属；事实分级 `user / visible / inferred / unconfirmed` |
| B `assisted` | 理解原意 → 找缺失 → 补购买逻辑 → 优化叙事 → 规划分屏 | **不得覆盖 `userIntentRaw`** | 每次产出都存 `rawIntent` 与 `diff`；AI 建议作为 `assistPatch` 独立保存，用户逐条采纳 |
| C `direct` | **仅**识别分屏边界、切分独立生成任务 | 不调 `planner/`、不调行业 Skill、不增删改卖点与画面要求、不自动覆盖原文 | 路由层 `resolveModeHandler(mode)` 白名单，`direct` handler **根本不 import planner 模块**；`rawPrompt` 字段 immutable；新增 `mode-c-purity-check.mjs` 断言（须注册 `run-all.mjs`） |

模式 C 的「智能整理」：`rawPrompt` 保持不变 → 生成独立 `tidyVersion` → 并排展示整理前后差异 → 用户可编辑 → **用户显式确认后**才把 `tidyVersion` 设为 `frozenPrompt`。任何情况下自动整理都不写回 `rawPrompt`。

### 3.3 结构化参数链与功能验证（任务书 §七）

```
用户选项 → ProjectConfig（schema 校验、全字段落库）
         → PlanningContext（三处注入，而非末尾追加一句）
              ① platformProfile（比例 / 内容组织 / 文字布局 / 平台规则）
              ② buildGlobalLock（copywriting / fontStyle / richness / modelMode / lang）
              ③ screenVisualPolicy（每屏构图 / 信息密度 / 人物约束）

每层保留 `appliedOptions[]` 溯源，最终提示词带 `optionTrace` 便于核对。借鉴现有 `detail-middleware.js:289/299/405` 已验证的写法（`richness` 真正改变信息密度、`no-model` 硬禁人物、平台影响比例与内容组织）。

**验证设计**：新增 `option-effect-check.mjs`，对每个重要选项做**负向对照**——固定其他字段，只改一个选项，断言策划输出或 `frozenPrompt` 中对应约束确实变化；再往真源塞入「选项未参与编译」的违法内容，确认门禁判红。这沿用本仓「改验证脚本必做负向对照 + `indexOf` 切片配 `>=0` 守卫」的既有纪律。

### 3.4 用户确认权：提示词冻结（任务书 §八）

直接采用 MxPage 已验证的 "never compile over user edits"：
1. `materializePrompts()` 产出 `promptReview.screens[].frozenPrompt`，连同商品分析、目标消费者、痛点、购买理由、叙事逻辑、视觉方向、每屏标题/内容/构图一并展示；
2. 用户可改整体方案 / 单屏 / 屏数 / 顺序 / 提示词 / 删屏 / 加屏（≤20）；编辑**只写 `frozenPrompt`**；
3. `confirm({confirmationId, revision})` CAS 提交，`workers.has(runId)` + live lease 防重复派发；
4. 生成阶段**只读 `frozenPrompt`**，禁止再经任何 Skill / 行业策略 / 智能整理编译；
5. 新增门禁断言：生成请求体 `prompt` 与 `frozenPrompt` 字节一致，不一致判红。

### 3.5 逐屏上下文与商品一致性（任务书 §六 / §九）

`ScreenContext` 结构含：`productFacts[]`（分级）、`identityAnchor`（商品参考图 → `mainAssetId`，约束外观/包装/颜色/标签）、`visualDNA`（整体色系/字体/光影/构图族）、`planSummary`、`screenRole / goal / copy`、`compositionSpec`、`prevScreenId / nextScreenId` 关系、`globalConfig`、`screenOverrides`、`referenceAssets[]`（按 `role: product | visual | structure` 分类，互不串用）。参考图职责在上传时由用户明确指定并落库，商品图只进身份锚、风格图只进视觉 DNA、结构图只进内容组织，避免相互干扰。单屏生成只读本屏 context + 只读共享锚，不重建策划。

### 3.6 质量检查（任务书 §十二）

- **规则代码优先**：借 `check_listing.py` 的四态 `verdict = pass|warn|reject-risk|error` 与 `run_loop.mjs` 的 `RISK_ORDER`，客观检查全部由 Node 代码实现；主观检查才用 `postChatCompletion` 且固定检查项。
- 六类检查：商品事实（`unconfirmed` 不得 publish、禁功效/认证/参数虚构）、购买逻辑、内容完整性（重复卖点 / 凑屏 / 逻辑断裂）、视觉设计（统一性 / 构图变化 / 重复模板 / 信息密度）、提示词（含身份锚、继承 visualDNA、继承全局选项、单屏专属、冲突检测）、用户选项（`appliedOptions` 传递链完整性）。
- **不合格自动修正恰好一次并重检；仍不合格明确列出问题交用户，禁止无限循环**（对齐禁止事项 12）。检查发生在正式生成图片之前。

                imageAssetId, isActive, createdAt, fromUserRequest }
GenerationTask{ taskId, screenId, idempotencyKey,
                state:waiting|running|success|failed|uncertain|canceled,
                attempts, requestId, retryAuthorized, lastError, timing }
PlanRun       { id, projectId, stage, checkpoint, leaseToken, leaseUntil,
                idempotencyKey, confirmationId, revision, error }
```

存储：`data/detail-studio/projects/<id>/project.json` + `screens/` + `versions/` + 顶层 `index.json`。**沿用 `server/ai-tryon/task-store.js` 的原子写（tmp + rename）、`.bak` 回退、每任务/全局索引单写入器串行链**；不引入数据库。

### 4.2 任务状态机与失败策略（任务书 §十）

- 每屏一个独立 `GenerationTask`；状态 `waiting / running / success / failed / uncertain / canceled`；`uncertain`（超时/断网/上游 5xx/429 拿到但结果未知）**绝不自动重试**，须先查询原 `requestId`、用户显式 `retryAuthorized` 才可重提（防重复扣费，借 MxPage `queryImageTask`）。
- 请求账本：key = `PLAN` / `GENERATE:${screenId}` / `REVIEW:${start}`，记 `state / requestId / upstreamTask`。租约 60s + 心跳 15s，`assertActive()` 防多执行者覆盖；`idempotencyKey` + CAS `updateMany({where:{id,status,updatedAt}})` 防重复提交。
- 启动恢复 `recoverInterruptedRuns()`：过期租约 → INTERRUPTED，**只恢复状态不盲目重跑**（沿用本仓 `startup-recovery-no-auto-regenerate` 与 MxPage 同口径）；假 COMPLETED 降级 PARTIAL。
- 退避：`min(2**i*1000, 30000)`，仅对 `429 / 5xx / timeout / ECONNRESET`；`retryBudget` 上限；`budget/halted` 熔断。**不人为设固定并发数上限**（按任务书），但复用现有 `acquireImageSlot` 做进程级异常保护与超时保护。
- 失败隔离：单屏失败不影响其他已成功屏；已落盘的图片与版本永久保留（独立目录，不受 `cleanupResultCache` 的 7 天 TTL 影响）。

### 4.3 单屏编辑与版本（任务书 §十一）

`versionNumber` 单调递增 + `isActive` 互斥 + `Screen.currentVersionId` 指针，切换版本只改指针。单屏修改只创建该 `screenId` 的 `GenerationTask`，**不重建 `PlanRun`、不触碰其他屏**；`userIntentDiff` 记录连续对话式修改的上下文，基于上一版 `imageAssetId` 继续。若用户明确提出调整整套视觉方向，先列出受影响屏清单，**由用户确认后**才批量处理。

### 4.4 项目保存、预览与导出（任务书 §十三）

项目全量落服务端 `data/`（原因见 §2.4）；重新打开按 `index.json` 恢复。整体预览按 `Screen.order` 竖排，复用 banana-mall 的 396px 手机外壳思路（用 `src/shared/ui/CachedImage`）。导出分步：单屏图片 → 多屏 ZIP（借 `export-manifest.json` 命名约定）→ 长图预览（前端 Canvas 拼接，或后续引入 sharp 需另评估原生依赖）→ 项目资料与提示词 JSON。**项目数据含生成图片，绝不能进入 `seed/manifest.json` 的 `SEED_ENTRY_IDS` 白名单**（封装红线②「封装包不能有生图信息记录」），`/api/seed-sync` 需显式拒收 detail-studio 相关键。

## 6. 推荐实施路线与理由

### 6.1 为什么选「借流程与数据结构，不借技术栈」

1. **技术栈全线不兼容**：五个项目没有一个能直接集成——Next 14 App Router / Prisma+SQLite / Electron / LangGraph / Python+Pillow / Claude Code Skills 运行时，与 React 19 + Vite + Express 4 + JSON 文件 + Node 24 的现有体系冲突；整体移植成本高于按蓝图自建，且必然带来原生 ABI、体积与启动链路 TDZ 风险（MxPage 的 sharp/Prisma/Electron 尤其明显）。
2. **但流程与数据建模的价值极高且许可证宽松**：MxPage V4 的「检查点 + 请求账本 + 租约 + 幂等 + 不确定请求不自动重试 + 生成前提示词冻结」几乎逐条对应任务书 §八/§十/§十一；Gayaya999 的 `facts.source` 分级对应 §四.1；product-shots 的结构化行业 DNA 对应 §四/§十一；ecommerce-skills 的确定性脚本对应 §十二/禁止事项 10。**这些是「思路 + 规则数据」，移植成本极低。**
3. **模型体系已统一**：`postChatCompletion` + `/api/images` + 客户 KEY + 单网关已经齐备，引入任何第二套 Provider 不仅违反红线，还会被 `routing-check` 判红。工作区只需新增薄封装与端点。
4. **参数链有现成范式**：现有 `detail-middleware.js` 已证明「选项 → 服务端策略函数 → 全局锁/单屏策略 → 提示词」可行，直接提炼并补 `appliedOptions` 溯源与负向对照门禁即可，无需从零设计。
5. **渐进式、每阶段审核**：按任务书 §十六 的阶段 1–6 推进，每阶段结束统一汇报，阶段内部任务由统筹 AI 自主拆解，不逐任务打扰 Owner。
