## 一、取证结论（源码直证）
### 1. 数量有三套互不等价的来源（当前无联动）
| 层 | 真实来源 | 代码 |
|---|---|---|
| 分屏框数 | `activeDetailGroup.prompts.length`（批量任务数实为 `enabledPrompts.length`） | `detail-state.js:606-608,623-625` |
| 基础参数数量 | `detailSettings.count`（全局单例，UI 下拉） | `DetailView.jsx:225` → `detail-state.js:276-280` |
| 每屏出图数 n | `generateDetailPrompt` 第4参数，默认 1 | `detail-state.js:461,511` |

**当前缺口**：手动增删屏不回写 `detailSettings.count`（`detail-group.js:286-315`、`detail-state.js:719-730`）；改 `detailSettings.count` 只影响下次 AI 规划、不改已存在组的 prompts；`detailSettings.count` 全局共享、切组不变（`detail-state.js:155,161,236-252`）。

### 2. 生图链路关键事实
- 批量提交数 = `enabledPrompts.length`（过滤 `enabled && status!=="running" && shouldGenerate!==false && !isEmptyScreen`），**每屏 n=1**（批量调用只传 3 参，count 默认 1）。
- 手动空白屏是 `shouldGenerate:true / isEmptyScreen:false`，会进入 enabledPrompts，靠 `generateDetailPrompt:468` 的逐屏空 text 校验落 `failed` 后 return —— **不是"批量前统一检查并阻止"**，需补。
- AI 规划组 prompts 由服务端返回，前端不按 count 截断；`countMode:"fixed"` 硬编码（`detail-state.js:412`）、门禁 AE10 锁定，**禁改**。

### 3. 持久化约束
- group 白名单 `DETAIL_GROUP_STORAGE_KEYS`（`detail-group.js:14-21`）、prompt 白名单 `DETAIL_PROMPT_STORAGE_KEYS`（:25-34）；新字段不进白名单会在 `sanitizeDetailGroupsForStorage`（:383-406）写盘时被剥离。

## 二、最小修复设计

### 核心：统一状态更新函数 `applyDetailCountSync(groupId, targetCount, origin)`
- `origin` 取值 `"prompts"`（手动增删屏触发）或 `"setting"`（基础参数修改触发），**只作语义记录，不参与判定**。
- 函数内部**一次性**写出两个 state：① 当前组 prompts（含可恢复暂存区）② `detailSettings.count`。同一次事件里用同一个确定值 targetCount，杜绝 React 异步更新/旧分组参数/缓存值竞争。
- **不再反向调用**增删屏函数或 `updateDetailSetting`，避免循环同步。所有数量入口（下拉 onChange、新增分屏、删除分屏）都改为调用本函数。

### 数量减少的数据保护（重点）
- 在 **group 级**新增 `parkedPrompts: []`（暂存数组），加入 `DETAIL_GROUP_STORAGE_KEYS` 白名单，跨刷新保留。
- 缩减时：把超出新数量的 prompts **原样移入** `parkedPrompts`（完整保留 text / results / 稳定 screen ID / 所有字段），不永久删除、不 retire ID。
- 扩容时：**优先从 `parkedPrompts` 按原稳定 ID 放回**（恢复提示词与生成结果），不足部分才补真正空白新屏（走 `nextDetailScreenId`，不复用）。
- **用户明确点 X 删除单屏**（`removeDetailScreen`）仍走现有语义：永久删除 + `retireDetailScreenId`，**不进暂存区**——与"数量缩减"严格区分。
- 暂存区只在数量操作里搬运；切组、刷新、预设加载均不丢失（白名单保证）。

### 数量入口改造
1. **基础参数改数量**：`updateDetailSetting("count", v)` → `clampDetailCount` 后调用 `applyDetailCountSync(activeGroupId, n, "setting")`；仍置 `countTouched=true`（不改 AI 规划 fixed 语义）。
2. **手动新增屏**：`addManualDetailScreen` 追加空白屏后 → `applyDetailCountSync(groupId, 新prompts.length, "prompts")`。
3. **手动删除屏**：`removeDetailScreen` 删除后 → `applyDetailCountSync(groupId, 新prompts.length, "prompts")`；被删屏不再进入后续任务（现有 retire + prune 机制保留）。
4. **拖拽排序**：完全不碰数量，也不调同步函数。
5. **切换分组**：切组 effect 中用 `activeGroup.prompts.length` 同步 `detailSettings.count`，保证"切组读本组数量"，不同组不污染。

### 生图规则
- 批量入口 `generateDetailGroup`：在提交前统一扫描 enabledPrompts 的 `text`，存在空白则**阻止整批**并明确列出"第N屏"（按当前顺序编号），不提交任何任务。
- 每屏 n 保持 1（不改 `generateDetailPrompt` 的 n 语义）；"5 个有效框提交 5 个任务、每任务 n=1"由 `enabledPrompts.length` + 默认 count=1 天然满足。
- 单屏生成仍只提交当前屏 1 张。
- AI 规划模式全程不改（禁改点见一节）。

### 界面
- DetailView 在手动模式下同时显示"基础数量"和"实际活动分屏数"，两者由同一同步函数驱动、始终一致；不同步完成不提前显示。

## 三、需顾问确认的一个边界
**基础参数改数量作用于哪个组？** 取证显示 `detailSettings.count` 是全局单例，而 AI 规划组的 prompts 是服务端规划产物。
- 设计建议：**数量联动只作用于"手动组"**（含 `source:"manual"` 分屏的组，或新建的手动空组）；若当前活动组是纯 AI 规划组，改基础数量只更新设置值供下次 AI 规划使用，**不直接增删该组 prompts**（否则会破坏已验收的 AI 规划结果）。
- 若顾问要求"AI 规划组也随基础数量增删屏"，需另行明确对服务端规划结果的改写边界（会触及 AI 规划语义，需单独授权）。
