## 0. 结论先行（给决策者的一屏）

**一句话判断**：V212 复用的是「生图入口、出图 FormData、结果可见性和部分布局外观」，**不是产品流程**。当前新版详情创作仍是「先建项目 → 选模式 → 13 个前置/管理步骤 → 出图」的开发者工作台，与客户已习惯的旧版一键详情操作框架相反。按最高产品原则，本轮**不建议继续加功能，建议先做流程归位**。

**三条最重要的诊断**：

1. **该必选的没必选，不该必选的全必选。** 旧版唯一硬校验是「至少一张产品图」（`src/features/detail/detail-state.js:343-346`）；新版把产品图降级成一句 UI 文案（「必传」只是样式，`src/features/detail-studio/components/FlowGuidanceBar.jsx:23,55`；上传块明写「建议至少上传一张，不传也可继续」，`src/features/detail-studio/intake/ReferenceImageDropzone.jsx:102-107`），服务端全链路**没有产品图校验**；却把「项目名称」做成硬必填（`server/features/detail-studio/store/project-store.js:240-242`）、把「创作模式 A/B/C」做成创建时必选且创建后不可变（`workspace-contract.js:7-20`、`project-store.js:287-288`）。这与「产品图片上传是唯一必选项」正好反过来。
2. **新版最值钱的东西是后端策划大脑，最该换掉的是前台流程。** `analyzeProductStrategy` + `directVisualPlan` + `compileScreenPrompt` 已能产出结构化 `ScreenSpec[]`、事实分级、全局一致性锁、行业策略注入，明显强于旧版「按平台节奏自动排标题」。而 `PlanningPanel` 冻结区提示词 `readOnly`（`src/features/detail-studio/planning/PlanningPanel.jsx:223`）、分屏不支持勾选/排序/删除/新增、没有与 AI 沟通改词的入口 —— 客户反而比旧版更难干预结果。**方案 = 保留新大脑，把前台换回旧骨架。**
3. **不需要重建 Agent 架构。** 《状态快照》§0/§4 已实证：无 Agent 运行时、无 Skill 执行注册表、`dispatchTool` 在 `server/**` 与 `src/**` 生产代码零调用，V207 七层架构除 P1 外壳外全是设计。「整套/单屏沟通改词」只需复用现有 `postChatCompletion` 加两个薄端点 + 一层手动覆盖，**不需要** V207 P2–P8、不需要 Tool 执行层、不需要上下文/长期记忆管理。建议**冻结该路线图**并清理口径（理由见 §6）。

**本轮对应的 8 项任务**：① 读状态报告 → §2；② 旧版页面 → §3；③ 新版页面 → §4；④ 最小改造方案 → §5；⑤ 必选/可选/后台自动 → §5.2；⑥ 板块库与沟通入口 → §5.3 / §5.4；⑦ Agent 架构评估 → §6；⑧ 提交审核 → 本文件 + §8 待拍板事项。

## 1. 判断依据（最高产品原则如何落到代码）

本方案对每项改造只问四个问题，答不上来就不做：

- 客户为什么需要它？→ 是否减少从「上传图」到「拿到可用分段提示词」的操作步数。
- 能否利用已有成熟功能实现？→ 优先复用旧版 UI 范式、新版后端策划链、`SCREEN_MODULES` 词表、共享生图 form。
- 是否影响旧功能？→ 旧 `detail-main` 运行时零回归是硬红线。
- 是否增加无价值复杂度？→ 凡「客户不可见、系统能自动做」的一律沉到后台，不新增可见面板。

### 3.2 唯一必选、默认值、零管理概念

- **唯一硬必选 = 产品图**：`detail-state.js:343-346`（无图 → `addEvent("请至少上传一张产品图")` 并 return）。第二个阻断是全局 API KEY（`detail-state.js:347-353`），在设置页，不属于页面输入。生成图片还有一条 `enabledPrompts.length === 0` 的常识校验（`:502-506`）。
- **可选设置全部有默认值**：真相源 `src/shared/app-defaults.js:67-90`（平台 `taobao-detail`、比例 `9:16`、分辨率 `2K`、数量 `10`、文案 `need`、画面 `simple`、字体 `heiti`、模特 `use-model`、反转屏 `2`、Skill 版本 `v1`、风格包 `auto`、语种 `中文`）；「内容输入（可选）」4 字段默认空串（`DetailView.jsx:274`）；参考图默认空。**客户一个字不填也能出提示词。**
- **零管理概念**：在 `src/features/detail/**` 全量搜索「项目 / 项目组 / 能力自检 / 选择 Agent / 配置 Skill / 上下文管理」，只有注释里的普通词，无任何 UI 控件。旧版的「分组 #N」是每次生成提示词产生的记录，不是项目；「预设」是参数快照，不是项目。
- **缺信息时不虚构**：旧版靠用户指令 + 平台/行业规则；新版的事实分级更严格（见 §4.4），这项能力应保留并前移。

### 3.3 分屏能力：旧版有什么、缺什么

| 能力 | 旧版 | 证据 |
|---|---|---|
| 每屏启用/停用 | ✅ checkbox | `detail-group.js:221-231` |

### 4.3 明确回答「哪些旧版交互已复用，哪些仍是不合理的新流程」

**已复用（V211/V212 的真实成果，保留）**：

- 分析 / 分屏 / 编译 / 冻结 / 质检五个客户按钮（§4.1 #9–#13）。

### 5.4 AI 全局 / 单屏沟通入口设计

**入口位置**：右栏「分段提示词」卡片区，两级、视觉上明确区分作用域：

- **整套**：卡片区顶部一条输入「对整套方案说一句…」+ 发送 → `scope="all"`。
- **单屏**：每屏卡片内一条输入「只改这一屏…」+ 发送 → `scope="screen"`, `screenId`。
- **手动编辑**：每屏 textarea 可直接编辑完整提示词（复用旧版 `updateDetailPrompt` 交互，替代当前 `readOnly` 的 `PlanningPanel.jsx:223`）。

**严格的作用域隔离（对应 4.4「不得因为修改一个分屏而破坏其他已经确认的内容」）**：

| 操作 | 允许改动 | 禁止改动 |
|---|---|---|
| 整套沟通 | `planning.screens` 全量（用户显式要求时）、`narrativeSummary` | 不得静默改 `globalLock` / `analyze` / `visualDNA`；须先展示受影响屏清单 |
| 单屏沟通 | 仅目标屏的 `ScreenSpec` | 其它屏的 `ScreenSpec` / 文案 / 冻结值**字节不变**；前后屏上下文只读带入（`version-routes.js:9` 已有此纪律） |
| 单屏手动编辑 | 仅 `planning.manualOverrides[screenId]` | 不改 `planning.frozenPrompts`、不改其它屏 |
| 删除 / 新增 / 重排分屏 | 仅 `screens` 数组结构与 `id/index/prevScreenId/nextScreenId` 链 | 不重跑整套策划、不自动重生成其它屏（沿用 V204 裁决） |

**后端最小增量（不建 Agent 运行时）**：新增一个薄端点 `POST /projects/:id/planning/revise`，body `{ scope, screenId?, instruction, target: "plan" | "prompt" }`；复用现有单网关 `postChatCompletion`：
- `scope=all` → 复用 `buildDirectorUserPrompt` 变体，把当前 `screens` + `instruction` + 选定板块注入，要求返回同 schema 的 `ScreenSpec[]`，经 `normalizeDirectorResult` 规范化后落库。
- `scope=screen` → 只把目标屏 `ScreenSpec` + `instruction` + 前后屏摘要（只读）发给模型，返回**单个** `ScreenSpec`，patch 回 `screens[index]`。
- `target="prompt"` → 直接返回改写后的提示词文本，写入 `manualOverrides[screenId]`（供不想改结构、只想改措辞的客户）。

**⚠️ 必须裁决的架构冲突：手动编辑 vs 冻结重编译。** 当前 `compile-screen.js:8` 与 `detail-studio.routes.js:392` 明确「冻结时服务端重编译，不信任客户端字符串」，以保证「展示 == 实际发送 == 落库」三同源。若允许客户直接编辑 `frozenPrompt`，重编译会把编辑覆盖；若放弃重编译，则失去三同源这一已交付的质量保证。

**建议解法（推荐，待拍板）**：引入 `manualOverrides` 覆盖层，`frozenPrompts` 仍由服务端重编译产出且**不被改写**；生成端读取优先级 = `manualOverrides[screenId]` > `frozenPrompts[screenId]`，前端展示时用同一优先级函数，从而「展示 == 实际发送」仍成立，且客户编辑只影响该屏。配套门禁：单屏编辑后断言其它屏的 `frozenPrompts` 与 `screens` 字节不变；负向对照「去掉 override 层 → 判红」。

**「确认提示词」语义**：客户确认时后台一次性做「服务端重编译 + 落库 + 标记 confirmed」，客户不接触编译/冻结字样；确认前不触发任何生图请求、不产生费用。

| 手动编辑完整提示词 | 覆盖层 + 生成端优先级 | ❌ 与冻结重编译冲突 | `manualOverrides` 层（§5.4） |
| 删 / 增 / 排序分屏 | 逐屏 patch 端点 | ❌ 只有整体替换 | 1 个端点 |
| 用户确认后生成图片 | 已有冻结 + 批量出图 | ✅ V212-R1 已交付 | 把「确认」做成后台动作 |
| 版本 / 任务 / 数据持久化 | 已有 | ✅ `version-store` / `orchestrator` / `project-store` | 无 |

**结论**：8 项产品能力中 4 项现有已够，4 项只需「2 个薄端点 + 1 个覆盖层 + 1 层板块扩展」。全部可复用现有单网关 `postChatCompletion` 与确定性编译器，**不需要 Agent 运行时、不需要 Tool 执行、不需要上下文/长期记忆框架**。

### 6.3 明确建议：冻结 V207 P2–P8，清理 V208 Tool 层口径

- V207 的「对现有架构进行较大改造」结论形成于 V212 **之前**（当时主路径是服务端内部自调用）；V212 后 `submitBatch` / `runTask` 在用户态退役，`create-task.tool.js` 事实上失去落地对象（《状态快照》§2.2）。**继续按 P2–P8 重建 Agent/Skill/Context 层，是为一个已不存在的调用链服务**，会产出客户看不见的复杂度，违反最高产品原则。建议冻结该路线图，并把 V207 设计文档标注为「历史设计，非现行架构」。
- V208 的 7 个 Tool 适配器建议**保留但明确定位为「只读元数据 / 未来可选」**，不作为本方案的依赖；不新增 `dispatchTool` 生产调用点。若 Owner 同意，后续单独出单评估是否清理死资产（不作为本方案范围）。
- 「Agent 沟通改词」在客户侧应表现为**一个输入框 + 明确的作用域**，而不是一个可选择的 Agent、一套 Skill 配置或一段能力自检。后台可以复杂，前台必须简单。

## 7. 风险、证据缺口与验收口径

**证据缺口（不得高估当前可用度）**：E4 Owner 带 KEY 的 8 屏全链路出图、长图下载、真机 director 成功出屏、`logs/planning-calls.jsonl` 真机值至今未回填；public 生产构建（`dist` + `.release-mode`）首启未单独验证。V210 / V212 的故障现场是触发证据，**不等于修复验证**。

**回归风险**：① 旧 `detail-main` 零回归（改板块词表必须走扩展层，不动 `prompts/server/detail-skills.js`）；② `frozenPrompt` 三同源（引入 override 层后由「展示优先级函数」保证，需门禁锁死）；③ 数据边界（`deferAutoSave=1`、结果图不进 seed / `data/results` / 全局 history）；④ 单网关与 KEY 口径；⑤ 打包运行期 TDZ（public 生产构建启动链路只准 import 零依赖叶子）。

**验收口径（不以门禁全绿代替真实使用验证）**：
1. 新客户不看说明，能否在「上传图 → 点生成 → 看分段 → 确认 → 出图」5 步内完成；**只传 1 张图、其余一个字不填**必须能生成分段提示词。
2. 不上传产品图时，「生成分段提示词」在前端与服务端**都被拦住**，且不产生任何上游调用 / 扣费。
3. 客户全程看不到「项目 / 模式 / 自检 / 编译 / 冻结 / 质检 / Agent / Skill」字样。
4. 改第 N 屏后，其它 N-1 屏的 `ScreenSpec` / `frozenPrompt` **字节一致**（自动断言 + 负向对照）。
5. 面板里选的比例 / 分辨率 / 模型，与真实生图 FormData 一致（修掉硬编码覆盖）。
6. 门禁：`run-all.mjs --fast`、`check-syntax`、`vite build`、旧页零回归浏览器冒烟、public 生产构建首启；新增 verify 注册双数组、带负向对照、按基线棘轮上线。

**与既有缺陷的关系**：《状态快照》§6 的 #1（终态大小写）、#2（run-all 重复登记）、#3（VersionPanel `screenIndex` → `NaN`）、#5（总表漂移）建议随改造一并修，均为独立缺陷，不构成本方案前置，也不因本方案而自动消失。
