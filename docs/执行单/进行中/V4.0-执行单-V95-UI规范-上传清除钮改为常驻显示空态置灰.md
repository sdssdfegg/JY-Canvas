## 0. 先读：这不是"漏做"，是规格分歧，本单修正规格

统筹 2026-10-18 探针实测（`tmp/clear-empty-state-probe.mjs`）：批量生成 图1/图2/图3 **上传后全部有**清除钮（h=28、非置灰）——V82/V92 的覆盖没有漏。用户圈出的是**空态**：三个图区空态时右上角都**没有**按钮。

根因：V82 起草时统筹把用户"每个上传图片的模块右上角**都有一个**"解读成了"有图才渲染"（`file &&` 条件渲染），并写成了规格"空态不渲染"。**这个解读从未与用户确认，且与用户字面意图相悖**——用户要的是按钮**常驻**在右上角那个位置，界面可预测。本单把规格改为：

> **清除钮常驻显示于上传模块右上角；空态时置灰（disabled），有内容时可点。**

这样做的好处：① 满足用户字面要求；② 位置不随内容跳动（上传前后按钮位置稳定）；③ 空态置灰语义清晰（没东西可清）。

### 1.1 执行注意

- **保持各处 onClick 逻辑一字不改**，本单只动"渲染条件 → disabled"。
- `UploadZone`（#1）与 `DetailUploadZone`（#6）原条件里的 `onClear &&` 是防御性的：统筹探针证实所有调用点都已传 `onClear`，但保守写法保留 `!onClear ||` 前缀置灰。**若执行日发现某调用点确实没传 `onClear` → 停下回报**，不得静默补传。
- #3/#4 的"有内容"判定包含 URL 输入框（`settings.imageUrl` 非空也算有内容可清），与原条件一致，勿改语义。
- 各调用点外层容器（`uploadHeaderActions` / `detailUploadHeaderActions` / `.videoReferenceLine` / `.imageEditorSlot header` / `.batchResizeActions`）**不动**——按钮常驻后占位即可，无需改布局。
- 执行日先 `git grep -n "UploadClearButton" -- src` 复查是否出现**新的**调用点（V92 之后可能新增），新调用点同规则处理并写进回执。

### 1.2 不要顺手做的

- 不改 `UploadClearButton` 组件本身、不改 `Button`、不碰 `.ui-button:disabled` 样式。
- 不做任何其它 UI 规范化改动。
- 空态置灰是否够醒目（opacity 0.55）由探针判定即可，**不得**自行调样式值。
