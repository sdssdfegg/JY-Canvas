## 1. 诊断结论：不是渠道问题，是结构问题（当前代码取证）

### 1.1 渠道可排除

- `/api/health`：`gatewayBaseUrl = https://api.jingyin.online/v1`、`imageConcurrency.limit=5`、服务 200。
- 商品分析（批次①）**真机成功返回完整结果**（截图有信息完整度 5%、事实缺口、确认信息、14 条补充缺口）⇒ **同一网关、同一把 KEY、同一模型 `gpt-5.6-luna`、同一个 `postChatCompletion`、同样 `response_format: json_object`** 全链路是通的。
- 因此 KEY / 网关 / 渠道 / 模型可用性 / 上游鉴权都不是本次故障原因。

### 1.2 结构错配：小输出能回，大输出回不来

| | analyze（成功） | director（卡住） |
|---|---|---|
| 路由超时 | `setTimeout(..., 60000)`（`:258`） | `setTimeout(..., 90000)`（`:300`） |
| `max_tokens` | `2000`（`analyze-strategy.js:183`） | `3000`（`director-visual.js:190`） |
| 输出 | 一份商品分析 JSON | **最多 20 屏 ScreenSpec[]** + `narrativeSummary` + `visualDNA`；每屏 schema 约 10 类字段（`prompts/detail-studio/prompts/director-visual.js:38-56`） |
| 输入实测（统筹构造近似项目） | — | `system 611` + `user ~2025` 字符 ⇒ **输入不是瓶颈** |

上游生成 20 屏结构化中文 JSON 天然慢且耗 token，90s / 3000 token 是紧约束。

### 1.3 两条高概率失败路径（**因零日志无法区分，这正是 P0 要先补日志的原因**）

- **路径 A（超时 / 截断）**：90s abort → `directVisualPlan` catch 返回 `504`；或 3000 token 截断 → `extractJsonObject` 抛错 → `502 parse_failed`。前端 `setError` 只在**页面顶部** `detailStudioBannerError`（`DetailStudioView.jsx:37`）显示，截图视口已滚到中部 ⇒ 用户感知「转圈后没反应」。
- **路径 B（静默空结果）**：模型返回合法 JSON 但 `screens` 缺失/结构不符 → `normalizeDirectorResult` 得到 `[]` → `directVisualPlan` 仍返回 **`ok:true, screens:[]`** → 路由落库 `planning.screens=[]` → 前端 `setNotice("分屏方案已生成（0 屏）")` 只是一条普通 banner，界面停在 `0 屏` 与空状态文案「先完成商品分析…」。**完全匹配截图**。

### 1.4 可观测性缺口（本次无法定性的根因）

- `grep -c planning logs/generation.jsonl` = **0**；`logs/launcher-diagnostic.log` 无 planning 事件。
- `src/api/client.js:22` 的 `shouldTraceGeneration` 只覆盖 `/api/images` 等出图端点，不覆盖 `/api/detail-studio/*/planning/*`。
- `server/features/detail-studio/planning/` 与 `server/core/ai-chat-shared.js` **零日志埋点** ⇒ 文本模型三个批次（analyze / director / quality）的耗时、上游状态码、返回长度、解析结果全部无记录。

> **Owner 可立刻自查（不依赖本单）**：浏览器 DevTools → Network → 点「生成分屏方案」→ 看 `/planning/director`：`504` = 90s 超时；`502` = 上游错误或 JSON 解析失败；`200` 但响应 `screens: []` = 静默空结果；一直 pending = 请求仍挂着。把状态码告诉执行 AI 可直接锁定路径 A/B。

## 2. 修复口径（参数分档，不拍脑袋）

- 超时与 `max_tokens` 抽为**按目标屏数分档**的常量（如 `screenCount ≤ 8 / 9-14 / 15-20` 三档），从 `planning.screens` 目标或 `context.screenCount` 取值；20 屏档必须给足输出空间。`analyze` 的 60s / 2000 **保持不变**。
- 错误类别枚举固定：`timeout` / `upstream_error` / `parse_failed` / `empty_screens` / `no_content`；返回给前端的是**类别 + 人话建议**，不是上游正文。
- `normalizeDirectorResult` 增加屏数校验；`screens` 为空或字段结构不符 → 抛明确错误，禁止静默 `ok:true`。
- 前端反馈：`已等待 N 秒`、错误类别、建议动作（重试 / 减少屏数 / 检查网络）、重试按钮；错误 banner 置顶且滚动可见。
- **保持**：A/B 各 3 次 `postChatCompletion` 上限、C 模式 0 次、`frozenPrompt` 字节一致、后台零改写。
