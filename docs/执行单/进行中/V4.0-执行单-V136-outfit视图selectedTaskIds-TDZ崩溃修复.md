# V4.0 执行单 V136 —— outfit 视图 selectedTaskIds TDZ 崩溃修复（v4.0.13 二进制实测必崩）

## 背景（用户实测）

用户报告：打包二进制 v4.0.13（端口 8788）中 批量生成 / 图片编辑 / 批量改尺寸 三视图全部显示
「{label}这块界面出错了 | Cannot access 'selectedTaskIds' before initialization」。
本单定位为**真实代码缺陷**（并修正 2026-10-23 早晨"纯 HMR 假阳性"的错误结论——那是空状态探针造成的迷惑，见根因③）。

## 根因（三层，均已实证）

1. **责任 commit**：`687ddee`（V135 落地的 V133 累积态）把 `selectedTaskIds` 状态+4 函数从组件内联
   `useState`（V131 之前声明于 **318 行**、使用于 516 行，顺序正确）搬入 `useOutfitSelectionHandlers`，
   调用点落在 **~1227 行**；而消费点 `selectedCount`/`selectedCompletedCount`（V68 起）位于 **~497 行**，
   从此落在声明前的暂时性死区。
2. **为何此前全绿**：`tasks.reduce(...)` 的回调**惰性执行**——`tasks` 为空数组时回调一次都不跑，
   不触发 TDZ。全新实例/CI 探针（空状态）全过；用户本地有任务历史（`TASK_HISTORY_KEY` 恢复）→ 必崩。
3. **为何三个视图同报错**：ErrorBoundary 捕获后跨视图保持 error 态（同一 boundary 实例记住首个错误，
   label 随视图换、message 不换）；图片编辑自身 import 图与 outfit 零交集，是被传播波及。

## 改动（最小外科手术）

- `src/outfit-workflow.jsx`：仅把 `selectedCount` / `selectedCompletedCount` 两个纯派生 const
  从 ~497 行**下移**到 `useOutfitSelectionHandlers` 调用点之后；两侧各留注释说明约束与迷惑点。
  **hook 执行顺序零变动**；两值消费点全在 JSX（~1658/1661），无中位消费。
- 排查另两刀（V132 result-drag / V134 split-halves）：`resultReplaceTargetId`、`splitHalves*`
  均无"声明前渲染期早读"，全文件仅此一处。
