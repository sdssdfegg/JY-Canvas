## 1. 第 ④ 项（下载域）—— **已施工并回滚，判定不拆**

- 域 = `downloadFeedbackIds` 状态 + `downloadSelected` / `downloadAll`（5 符号，13 行逻辑）；
- 实测：组件 1977 → **1979（+2）**，新模块 38 行 → 净 **+40**；
- 技术阻断：`setDownloadFeedbackIds` 被 `useOutfitSaveHandlers` 的 ctx **立即求值**消费（1347 行），
  故新 hook 必须早于 1333 调用；但 hook 需要 `downloadTask`（1335 才返回）→ 只能引入
  `getDownloadTask: () => downloadTask` 延迟取值。这是**下游反向取上游**的坏味道，
  且给未来"谁把 useOutfitSaveHandlers 挪到前面"埋一个 TDZ 雷（V121-R2 同族：lint/build 都不报，运行时整页崩）。
- **裁决：回滚**。理由 = 收益为负（+40 行）+ 引入反向依赖 + 域太小。已删 `handlers/outfit-download.js`，
  组件恢复至 1976 行，lint 0 / build EXIT=0 / size-ratchet failureCount=0 复绿。

## 2. 第 ⑤ 项（页面切换域）—— **评估后判定不拆**

域 = `buildCurrentOutfitPageSnapshot`(1103) / `resetOutfitPageTransients`(1124) / `loadOutfitPage`(1137)，共 55 行。
- 顺序死结：这三个函数被 `useOutfitPages` ctx **立即求值**消费（1180 行）→ hook 必须早于 1161；
  但 `resetOutfitPageTransients` 需要 `clearSelection`，而它来自 selection hook（1227，晚于 1161）
  → 同样要 getter 延迟取值。让 selection hook 提前也解不开：它依赖 `addEvent`，而 `addEvent`
  又来自 `useOutfitPages`（1161）→ **环**。
- 收益估算：55 行域 − hook 样板 ≈ 净 +20，还要背 1 个 getter。
- **裁决：不拆**。

## 3. 第 ⑥ 项（effect 四簇）—— **评估可执行，但排单不现做**

现状取证：28 个 `useEffect` 连续分布在 629–1008（380 行，占组件 22%），是剩余最大的单块。
- 反向依赖扫描：effect 块内命中的下游 hook 返回值**只有 `clearAll` 一处**（来自 useOutfitRefHandlers）
  —— 表面上"只差一个"，但要消掉它得把 useOutfitRefHandlers 提前，而它又依赖 clearSelection（selection hook），
  selection hook 又依赖 addEvent（useOutfitPages）→ **牵一发动全身的重排**。
- 真实风险不在依赖数量，而在 **28 个 effect 的执行顺序**：React 按声明顺序跑 effect，
  搬进 hook 后顺序 = hook 调用点顺序 × hook 内声明顺序。整块搬、调用点放回 629 原位可保序；
  分簇搬则每一步都在增加错序面。ctx 预计 40+ 项，漏注入会**静默改行为**（V132 已踩过一次漏注入 preview，
  那次还是 lint 抓到的；effect 漏项 lint 未必抓得到）。
- **裁决：可行但属高风险，另排 V136 单，不在本轮顺手做。**
  建议方案（供 V136 采纳）：**整块单 hook、逐字迁移、一次性注入**——
  ① 新 `handlers/outfit-effects.js` 只 export 一个 `useOutfitEffects(ctx)`，28 个 effect 按原顺序逐字搬；
  ② 调用点放回 629 原址（保证早于其余 hook，顺序不变）；
  ③ `clearAll` 用 `getClearAll: () => clearAll` 或在 hook 内改为接收 ref（二选一，单内定）；
  ④ 验收必须附 effect 顺序对照表（原行号 → 新行号一一对应）+ outfit 页面冷启动手动冒烟。
