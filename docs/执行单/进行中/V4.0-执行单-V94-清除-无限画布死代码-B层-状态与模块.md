## 0. 为什么还要一单（先读）

V93 把**看得见的**无限画布清掉了：导航入口、`SHOW_INFINITE_CANVAS` flag、`.infiniteCanvasView` 渲染分支、390 行死 CSS。但**整条支撑链路还在**：

```
main.jsx  infiniteCanvasState ──┬─> createCanvasActions / createCanvasInteractions（canvas-actions.js 313 行）
                                ├─> canvas-graph.js（102 行）
                                └─> main-handlers.js（4 处 infinite + sendResultToCanvas 孤儿）
                                     └─> canvas-generation-handlers.js（731 行，共用 hook）
```

这些现在**没有任何用户可达路径**（视图已删、导航已关），但仍然：占 size-ratchet 的账（约 1150 行）、占 dependency-direction 的依赖图、让 dead-export 挂孤儿条目、让 `localStorage` 继续读写一份永不展示的数据（`INFINITE_CANVAS_KEY`）。

**本单把这整条链路拆掉，做到"无限画布"四个字在代码里彻底消失。**

### 2.2 B7 的处置：共用 hook 怎么剥（重要，先判断再动手）

`useCanvasGenerationHandlers` 的 ctx **同时**注入了快捷生成与无限画布的东西。执行日必须先分清哪些 handler 归谁：

- **判定方法**：对每个 handler 追它的调用点——若只被 `activeView === "infinite-canvas"` 路径（已删）或被无限画布节点逻辑调用 → 删；若被快捷生成的生成按钮 / 任务流调用 → **留**。
- **两选项**（默认走 ①，改动大且需说明时才走 ②）：
  - ① **原地剥离**：文件保留在 `src/features/canvas/`，剥掉 infinite 部分。**代价**：§1.2 的"目录整个消失"不达成，验收改为"目录内仅剩 1 个不含 infinite 的共用 hook"。
  - ② **搬出目录**：若剥离后该文件已与"画布/无限画布"无关，可搬至更合适的位置（如 `src/features/quickgen/`）—— 需**停下回报等统筹裁决**，不得自行决定位置。
- **`source: "infinite-canvas"` 三处**：这是提交生成任务时打的来源标记。删之前确认 `source` 字段本身是否还有其它取值在用（如 `"quickgen"`）—— 只删 infinite 那一支，字段与 dict 结构保留。

### 2.3 不要顺手做的（记录即可）

- 换装旧令牌注入 / hardcoded-color 存量收口（另一条线）。
- UI 规范化的任何视觉改动。
- `main.jsx` 里与无限画布无关的其它瘦身（本单只删 infinite 链路）。
