# V4.0 执行单 V143 — AI 无限画布 MVP-1（独立画布工作空间）

> 关联审计：`AI无限画布集成审计/`（任务单 V1.0 全套交付物）。
> 推荐架构（审计结论，doc 03 / doc 07）：方案 B 独立子应用/服务；Agent 驱动层走 JY 现有 GPT API 渠道（doc 07）。
> 本单落地 **MVP 第一阶段（独立画布工作空间）+ MVP 第二阶段（打通一条真实生图链路）+ MVP 第三阶段（Agent 自然语言操作画布）+ MVP 第四阶段（画布自动工作流引擎）+ MVP 第五阶段（多 Agent 编排）**。

## 目标

在 JY-Canvas 现有 React19+Vite 栈内，新增一个**隔离**的「AI 无限画布」工作空间，复用现有导航与存储机制，不改动任何现有业务页面。

验收标准（对应审计 MVP-1）：
1. 左侧导航新增「无限画布」入口，点击进入独立工作空间。
2. 可创建 / 保存 / 重新打开画布项目（刷新后保留，复用隔离存储键）。
3. 画布支持平移、缩放、节点拖动。
4. 可添加「图片节点」与「提示词节点」。
5. 可在节点间建立基础连线（端口拖拽）。
6. 提供小地图用于定位。
7. 提供撤销 / 重做（基础操作）。

## 设计要点

- **隔离存储键**：`jingyin-ai-canvases-v1`（与休眠的 `jingyin-infinite-canvases-v1` 完全独立，不读取/不迁移它）。
- **零侵入**：新视图自带工具栏，从 `MainTopBar` 排除列表移除；现有页面逻辑、模型调用、API Key、提示词模板一律不动。
- **复用机制**：导航走 `navItems` + `activeView`；持久化走 `src/lib/storage/json-storage.js` 的 `writeJsonStorage`/`readJsonStorage`（与现有设置存储同款）。
- **渲染层现实**：沙箱无法克隆 infinite-canvas（github.com 阻断），本阶段在 JY 自有栈原生实现画布；待候选源码在本机可用后，可再评估替换渲染层（不影响本阶段隔离设计）。
- **图片节点**：MVP-1 以 dataURL 存入项目（小图可行）；大图配额风险已在审计 doc 05 标注，MVP-2 接通生图时改为引用现有图片存储。

## MVP-2：打通一条真实生图链路（已落地）

**目标**：模特图 + 服装图 + 提示词 → 生成节点 → 生成结果 → 结果节点，尽可能调用 JY 现有模型服务，不改变现有快捷/批量生成流程。

**源码核实的生图调用链（非推测）**：
- 前端入口：`src/api/images.js` 的 `generateImages(form)` → `postForm("/api/images", form)`，其中 `apiJson` 对 `FormData` 不自设 `Content-Type`（浏览器补 multipart boundary），且 `readJsonResponse` 在 `ok:false` 时抛 `ApiError`（错误文案即上游返回）。
- 服务端：`server/routes/images.routes.js:116` `POST /api/images`，multipart `image` 文件（上限 `IMAGE_UPLOAD_PARSE_CEILING`）+ 表单字段（`prompt` / `model` / `apiKey` / `channelId` / `aspectRatio` / `imageSize` / `n` / `deferAutoSave`）。含图时 `server/channel.js:57` 路由到 `/images/edits`（图生图/换装编辑路径）。
- API Key：`resolveApiKey(req.body.apiKey)` = `normalizeApiKeyInput`；空且无服务端 key 时路由返回 400 `missing_api_key`。前端 key 来源 = 设置存储键 `jingyin-internal-settings-v3`（`STORAGE_KEY`，`src/shared/app-defaults.js`），字段 `apiKey`；`config.hasServerKey`（默认 false）来自 `GET /api/config`。
- 成功返回：`{ ok:true, images:[{url,...}], usedModel, ... }`。

**实现要点**：
- 生成节点收集上游「图片/结果节点」（多张，作为编辑输入）与「提示词节点」（单条）；读设置取 `apiKey` + 默认 `model`（`tt-image-2`）；构造与现有 `postForm` 一致的 `FormData`（`prompt` / `model` / `n=1` / `deferAutoSave=1` / `apiKey` / 图片），调用 `generateImages`。
- `deferAutoSave=1` ⇒ 画布生成结果**不污染主画廊历史**（与现有业务隔离，满足审计 doc 05/07 数据隔离要求）。
- 成功：生成节点内显示结果预览，并自动在下游创建一个「结果节点」+ 连线，形成「生成 → 结果」链路；结果节点可继续作为下一轮生成的输入（连续编辑）。
- 失败：节点内红字显示明确错误（含上游 4xx/5xx 文案），不崩画布。
- 安全：API Key 复用现有设置存储键读取，**不新增任何第三方/日志暴露**；`normalizeApiKeyInput` 内联为零依赖叶子（避免跨特性依赖，通过 `dependency-direction-check`）。

**验收标准（对应审计 MVP-2）**：
1. 工具栏「添加生成节点」可建生成节点。
2. 连 2 张图片节点 + 1 个提示词节点到生成节点，点击「执行生成」，走现有 `/api/images` 出图。
3. 生成成功后自动出现结果节点并连线，结果图可在画布中查看、可继续连入下一轮生成。
4. 生成失败（如无 Key / 上游报错）在节点内显示明确错误。
5. 刷新后画布项目（含生成节点配置）仍在。
6. 不改变现有快捷生成 / 批量生成 / 历史记录。

## MVP-3：Agent 自然语言操作画布（已落地）

**目标**：用户在画布里用一句自然语言下指令（如「把这两张图连到生成节点，提示词写成换成红色连衣裙」），由 Agent 翻译成结构化的画布动作并落到画布上。

**前置结论（源码核实，非推测）—— 闭合 doc 07 标红的未实测项**：
- 全仓检索 `tool_calls` / `function_call` / `tools:` **零命中**；JY 现有 chat 客户端是**纯 `chat/completions`**（`server/core/ai-chat-shared.js` 的 `postChatCompletion`，只接受调用方组装好的 body，不认识任何业务字段）。
- 结论：**不走 OpenAI 式 function calling**，改为沿用本项目既有 AI 文本族范式（与 `server/outfit-quality-ai.js` 同构）：`response_format: json_object` → `extractJsonObject` 解析 → 结构化规整；上游不支持 JSON 约束时由 `shouldRetryWithoutJsonFormat` 剥掉约束重试一次。
- 收益：不新增任何 SDK / 客户端能力，与现有质检、母版分析、提示词改写共用同一条调用链与同一套日志/错误口径。

| 文件 | 作用 | 是否新增 |

| `server/ai-canvas-agent.js` | Agent 规划器：指令 + 画布快照 → 动作清单（零依赖叶子，只 import core 叶子） | 新增 |
| `server/routes/ai-canvas-agent.routes.js` | `POST /api/ai-canvas-agent`（resolveApiKey→401、channelBaseCandidates、日志、publicImageErrorPayload） | 新增 |
| `server/app.js` | 注册新路由（2 行，纯新增） | 改动（最小） |
| `src/api/ai-canvas-agent.js` | 前端 `postJson` 封装 | 新增 |
| `src/features/ai-canvas/ai-canvas-agent.js` | 快照构建（节点→稳定代号 n1/n2）+ 动作 fail-closed 校验与应用（零 import 纯函数叶子） | 新增 |
| `src/features/ai-canvas/ai-canvas-view.jsx` | 左侧栏「画布 Agent」面板（指令输入 / 执行 / 回复 / 已应用 / 已跳过） | 改动 |
| `src/features/ai-canvas/ai-canvas.css` | Agent 面板样式（全令牌化） | 改动 |

**设计要点**
- **动作白名单（fail-closed）**：只允许 `add_prompt_node` / `add_generation_node` / `set_prompt_text` / `connect` / `rename_node` / `delete_node`。服务端只产出建议、前端再校验一次；白名单外或代号解析不到的动作一律不落画布，并在面板给出可读的跳过原因（不静默乱改）。
- **稳定代号（ref）机制**：快照把真实节点映射成 `n1`、`n2`…，模型只引用代号、不知道内部 id；新建节点由模型自取代号（如 `p1`、`g1`），前端维护「代号→id」映射供后续 `connect` 复用。
- **不自动触发生成**：Agent 只负责搭图和写提示词，真正的出图仍由用户在生成节点点「执行生成」——避免一句话就产生意外调用与配额消耗。
- **Key / 渠道 / 日志 / 错误口径全部复用现有**：`resolveApiKey` → 缺 Key 401；`channelBaseCandidates()` 取渠道候选；成功/失败都写 `writeGenerationLog`（stage `ai-canvas-agent`）；对外错误统一 `publicImageErrorPayload`。
- **模型**：默认 `gpt-5.4-mini`（与现有 AI 文本族同一口径；settings 只有图片模型字段，不为 Agent 新增设置项）。温度 0.2 保证同一指令动作稳定；单次动作上限 12 条。

**验收标准（对应审计 MVP-3）**
1. 左侧栏「画布 Agent」可输入指令并执行（Ctrl/Cmd+Enter 快捷执行）。
2. 指令「加一个提示词节点，内容是 XXX」→ 画布出现新提示词节点且内容正确。
3. 指令「把 n1、n2 连到生成节点」→ 生成新节点并完成连线；代号解析失败时面板显示跳过原因，不静默乱连。
4. 无 API Key 时面板显示「请先在设置里填写 API Key」（服务端 401 文案）。
5. 不改变现有快捷生成 / 批量生成 / 历史记录与任何现有页面。

## MVP-4：画布自动工作流引擎（一键跑通整张图，已落地）

**目标**：画布上搭好链路后，一键按顺序自动执行所有生成节点——不必逐个点「执行生成」，且支持 `生成节点 → 生成节点` 的**链式多轮**（连续编辑）。

**设计取舍**
- **拓扑排序决定顺序**（Kahn）：保证上游先跑、下游后跑；同层按画布节点原序出队，结果稳定可复现。重复边只算一次入度、悬空边忽略，都不会把顺序算歪。
- **有环直接拒绝执行**：环里的节点**以及被环堵住的下游**都标为不可排定，`runnable` 为空并给出中文原因——绝不猜顺序、绝不无限循环。
- **链式多轮怎么打通（关键）**：原 `collectGenerationInputs` 只认直接上游的 `image`/`result` 节点。为支持 `生成 → 生成` 的边，**不改动原函数语义**，新增 `collectWorkflowInputs` 在其结果之上叠加「上游已生成成功的生成节点（取其 `resultUrl`）」。单节点「执行生成」仍走原口径，两者互不影响。
- **失败即停**：某节点报错立刻停止；错误同时写在该节点（节点内红字）与画布状态条上，已完成的部分结果保留。
- **解析逻辑放零 import 的纯模块**：`ai-canvas-workflow.js` 不 import 任何东西，这样能被无头脚本直接断言（`ai-canvas-generation.js` 因要读设置、会连带 `import.meta.env`，纯 node 下导不进来）。

**模块与文件**

| 文件 | 作用 | 是否新增 |
|---|---|---|
| `src/features/ai-canvas/ai-canvas-workflow.js` | 拓扑排序 / 环检测 / 运行计划 / 链式输入解析（**零 import 纯逻辑**） | 新增 |
| `src/features/ai-canvas/ai-canvas-generation.js` | 新增 `collectWorkflowInputs`（委托纯模块，不改原 `collectGenerationInputs` 语义） | 改动 |
| `src/features/ai-canvas/ai-canvas-store.js` | 工作流状态 reducer（`WORKFLOW_START/STEP/DONE/FAIL/RESET`，**不入撤销栈**） | 改动 |
| `src/features/ai-canvas/ai-canvas-view.jsx` | 工具栏「运行画布」按钮 + 运行状态条（运行中 i/n、已完成、失败原因） | 改动 |
| `src/features/ai-canvas/ai-canvas.css` | 状态条样式（令牌化） | 改动 |
| `scripts/verify/ai-canvas-workflow-check.mjs` | 无头验收 19 项（已登记进 run-all 顺序表与 `--fast`） | 新增 |

**验收标准**
1. 工具栏「运行画布」按连线顺序依次执行生成节点，状态条显示「运行中 i/n」。
2. `图片 → 生成1 → 生成2` 链式：生成2 会把生成1 的结果当输入（连续编辑跑通）。
3. 存在循环连线时拒绝执行并提示「画布里有循环连线」，不会卡死。
4. 某节点失败时立即停止，节点内与状态条都显示错误，已完成结果保留。
5. 不改变单节点「执行生成」的原有口径，也不改变现有快捷 / 批量生成与历史记录。

## MVP-5：多 Agent 编排（Planner 搭图 → Prompter 写提示词，已落地）

**目标**：一条指令下去，不只搭出画布链路，还要把节点上的**生图提示词**写好 —— 把「搭图」和「写词」交给两个专业角色**串行**完成。

**为什么拆成两个角色**（而不是让一个 Agent 顺手都干）
- 项目实测（P0-B / E5）：**结构化提示词对出图质量提升最大**（均分 9.30 → 10.58）。让专门的提示词角色只干这一件事，比让规划角色顺手写更稳。
- 职责隔离后：prompter **不产出任何图结构动作**，planner 也不写提示词，两边契约都更窄、更好守。

**为什么串行而不是并发**
第二个角色必须在「搭完图之后」的画布上工作 —— 它得看到 planner 刚建出来的节点，才能给它们写提示词。并发会让第二阶段读到旧画布，写出来的提示词落不到新节点上。所以是**有顺序的两跳**。

**模块与文件**

| 文件 | 作用 | 是否新增 |
|---|---|---|
| `server/ai-canvas-agent.js` | 角色分工（planner / prompter）：各自的 system 提示词、输出契约与归一化；**默认仍是 planner，MVP-3 行为逐项不变** | 改动 |
| `server/routes/ai-canvas-agent.routes.js` | 响应补传 `role` 与 `prompts` | 改动 |
| `src/features/ai-canvas/ai-canvas-orchestrator.js` | 编排器：按模式串行跑两个阶段，第二跳在「搭完图之后」的画布上跑 | 新增 |
| `src/features/ai-canvas/ai-canvas-agent.js` | `applyCanvasAgentPlan` 额外带出 `createdNodes`；新增 `applyPromptPatches` 落盘提示词 | 改动 |
| `ai-canvas-view.jsx` / `ai-canvas-panels.jsx` / `ai-canvas.css` | 改调编排器；面板加「编排方式」下拉（自动编排 / 只搭图 / 只写提示词） | 改动 |
| `scripts/verify/ai-canvas-agent-check.mjs` | 断言 30 → **43 项** | 改动 |

**验收标准**
1. 面板默认「自动编排」：一次执行后画布既被搭好、提示词也被写好，并按阶段分别展示各自做了什么。
2. 可只搭图、或只写提示词。
3. prompter 不产生任何增删节点 / 连线的动作。
4. 无 Key / 空指令仍按原样拒绝；默认角色行为与 MVP-3 完全一致。

**🔴 测试抓出的真 bug（记录以警）**：第一版我给编排器测试写的桩，返回的是**上游 `chat/completions` 的 choices 形状**，而前端实际调的是**我们自己的路由** —— 结果掩盖了「路由响应没传 `prompts` / `role`」这个真 bug（prompter 的产出根本到不了前端）。**桩必须与真实调用面的形状一致，否则测的是假链路。**

## 补漏：Agent 路由级验收（2026-10-29）

**为什么补**：此前所有 Agent 断言都直接调模块函数，**测不到两层** —— ① 路由有没有真的挂到 express 上（`server/app.js` 漏注册的话，那 43 项照样全绿）；② 路由响应的字段是否传全（prompter 的 `prompts` 漏传就栽在这一层，且当时确实没被抓到，是靠改桩形状才发现的）。

**做法**：新增 `scripts/verify/ai-canvas-agent-route-check.mjs` —— 起一个最小 express 实例、**只挂本路由**，用**真实 HTTP** 打进去，按真实响应断言。

**覆盖 11 项**：缺 Key → 401 且不碰上游 / 空指令 → 400 / planner 走通且回传 `actions` + `role` + `dropped`（白名单外的已被服务端滤掉）/ **prompter 的 `prompts` 必须原样回传** / 上游失败 → 非 2xx + `ok:false` + 中文可读文案。
