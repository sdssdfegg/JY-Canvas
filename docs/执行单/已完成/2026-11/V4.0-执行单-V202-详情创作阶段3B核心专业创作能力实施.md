## 1. 本阶段目标与「框架优先」编排原则

Owner 明确本阶段价值排序：**框架与契约 > 内容质量调优 > UI / 视觉细节**。故五批之内，先做扎实可单测、可回归的框架主体，能力插件后置：

| 优先级 | 批次 | 性质 |
|---|---|---|
| **P0 框架主体** | **B1 规划底座 → B2 导演与分屏 → B3 提示词编译与冻结** | 事实分级、结构化 schema、选项参数链、逐屏上下文、`frozenPrompt` 编译与冻结。这三批是「展示提示词 == 实际生成提示词」的架构保证，必须先稳、纯函数可单测 |
| P1 能力插件 | B4 质量审查 | 六类检查 + 一次定向修正 + 再审查（`MAX_AUTO_FIX=1`），框架稳后再挂 |
| P2 增量内容 | B5 行业策略包 | 先 `generic` + `apparel` + `cleaning` 三包跑通机制，其余行业留后续增量，**不一次做满 6 类** |

**三类商品测试是验证框架是否通用的手段，不是调提示词大赛**（清洁日化 / 服装 / 食品或 3C，覆盖不同购买决策逻辑）。不出图、不比美观，验的是同一套框架在不同品类下是否都能产出合规、不套模板、参数生效的结构化结果。

**明确不做**（防止范围漂移）：批量生成与任务队列（阶段 4）、单屏版本管理与连续编辑（阶段 5）、长图预览与导出（阶段 6）、任何全局视觉系统 / 主题研究、旧详情模块改造、模型选择与渠道配置扩展（阶段 2 已定稿）。

## 3. 五批实施内容（对照 3A §3.8.1）

### B1 规划底座（P0 框架主体）
- 落 `prompts/detail-studio/core/*` 与 `server/features/detail-studio/planning/analyze-strategy.js`；批次① 1 次 `postChatCompletion`，结构化 JSON 含**事实分级**、消费者购买逻辑、信息缺口。
  > 🔧 **统筹修订（2026-11-10，B1 完工复核后）**：事实分级四类的**唯一真相源 = 3A 报告 §3.6.1**：`user`（用户明确提供）/ `visible`（商品图可见、可合理推断）/ `inferred`（合理推断、需标注来源）/ `unconfirmed`（待用户确认，禁止擅自编造）。程序强制 `unconfirmed` 不得 `publish`。本行原写的 `user / inferred / needConfirm / forbidden` 把「分级枚举」与「程序规则」混写，属发单笔误，**即日起作废**，B2/B3/B4 一律按上述四类实现；执行方按真相源落地且未私自改契约，处理正确（见 §9 B1 记录）。
- 选项结构化参数链：旧详情选项**只读盘点 → 逐项迁入结论 → 在新工作区重新结构化**，链路 `选项 → ProjectConfig → PlanningContext → ScreenSpec → frozenPrompt`；`appliedOptions` 溯源字段落库。
- A 模式引导：按 `completeness > 0.8` 停止追问，不一次性抛全部问题、不追问已知信息；B 模式保留用户原始意图字段，AI 补强不得静默改写。
- **B1 范围归属（统筹补充）**：B1 本批只交付**后端编排 + 提示词分层包 + 路由 + 落库**；前端 `analyze` 结果展示与 A 模式 `completeness > 0.8` 停追问的交互，**并入 B2 批次一并交付**，且必须在 P3 阶段验收前补齐。前端 API 薄封装须等有真实消费方后再加，避免 `dead-export-check` / `size-ratchet` 双红（执行方规避正确）。
- 验收：批次① 1 次调用返回结构化 JSON；`appliedOptions` 完整；事实分级四类（`user`/`visible`/`inferred`/`unconfirmed`）可枚举。

### B2 导演与分屏（P0）
- `director-visual.js` + `screen-composition.js` + `ScreenSpec[]` + 逐屏上下文（商品事实 / 身份锚点 / 视觉 DNA / 前后屏关系 / 全局选项 / 单屏专属要求 / 三类参考图职责）。
- 先定整套叙事再定单屏；屏数、顺序、构图由内容与品类驱动，**不套「痛点—卖点—参数—总结」固定模板**；≤20 屏；避免连续多屏「产品居中 + 标题在上 + 卖点在下」。
- 验收：批次② 1 次调用产出 `ScreenSpec[]`；屏数/顺序/构图随选项变化；逐屏上下文结构落库。

### B3 提示词编译与冻结（P0 · 红线所在）
- `prompt-compiler.js` 为**确定性纯函数**（照 `detail-middleware.js:531-550` 的 `text[]` 拼接范式），主路径零模型调用；`option-trace.js` 记录每个选项影响了哪句约束。
- 用户确认后写 `frozenPrompt`；**生成端只读它**，用户看到的提示词 == 实际发送提示词，后台不得再经任何 Skill / Agent 改写（MxPage 的 `never compile over user edits` 口径）。
- 模式 C 四份边界不变：`rawPrompt` 永久只读、`tidyVersion` 可选默认关、`diff` 可核对、`frozenPrompt` 仅确认后写。
- 验收：`frozenPrompt` 与生成请求体 `prompt` **字节一致**；C 路径 purity 门禁绿。

### B4 质量审查（P1）
- `quality/checklist.js`（确定性规则）+ `quality/qc-prompt.js`（LLM 主观），六类：商品事实 / 购买逻辑 / 内容完整性 / 视觉设计 / 提示词 / 用户选项。
- 独立 1 次调用，`MAX_AUTO_FIX=1`：**一次定向修正 + 再审查**封顶，仍不合格就明确告知用户、交回人工，禁止无限循环。
- 验收：六类检查可定位到具体屏/字段；上限常量生效；修正后再审查不触发第三次调用。

### B5 行业策略包（P2）
- `prompts/detail-studio/industry/*.js` + `getIndustryStrategy` 覆盖加载，只覆盖「决策逻辑 / 内容规划 / 视觉表达 / 事实边界」四字段，**不覆盖 BASE 事实锁与平台规则**；`generic` 兜底。
- 先 3 包：`generic` / `apparel` / `cleaning`（对应三类测试）；`cleaning` 必须遵守 3A 报告 §3.2 已补的三条冲突消解规则（显式 `industryId` 优先 / 同分专属词 tie-break / 新包不复用 `home` 已有「清洁」等泛词），否则清洁日化会误判为家居。
- 验收：加载机制就位、6 类扩展位清晰、三类商品均命中预期包。

## 4. 三种模式的能力调用流程（硬隔离）

| 模式 | 调用链 | 上限 |

## 7. 阶段验收（§十七 / 3A §3.8.3 口径）
