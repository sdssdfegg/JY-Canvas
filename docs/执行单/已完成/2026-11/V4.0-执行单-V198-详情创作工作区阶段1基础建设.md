## 1. 目标与边界

在 JY-Canvas 中新增**独立**的「详情创作」工作区：独立导航入口、独立 `React.lazy` 视图分支、独立业务状态、独立服务端路由与项目数据目录，并接通现有统一文本模型与 `/api/images` 图片生成能力。

**阶段 1 只做基础建设**，不实现三种创作模式的业务逻辑、不实现分屏生成与质检。旧 `detail-main` 保持原状；新功能未经完整验收前，不得为统一代码而重构旧详情模块。

允许实施（封闭集合见 §3）：新增 detail-studio 独立工作区目录（按 §2 分类）、独立导航入口、`main.jsx` 的一个 lazy 分支、`src/api/detail-studio.js`、Express 服务端路由、项目基础数据结构与服务端持久化目录、接通现有统一文本模型调用能力、接通现有 `/api/images`、复用现有设计系统的基础 UI、必要的工程门禁基线刷新。

不允许顺手实施：完整三种 AI 策划模式、复杂分屏生成与质检系统、修改旧详情模块、修改模型 Provider / KEY / 网关体系、引入新数据库或第三方任务框架、擅自修改公共并发机制。

## 2. 目录分类规范（🔴 Owner 追加要求 · 本单硬约束）

> 目的：让后续阶段可以**按业务区切割**、**按目录定位问题**、**按区域独立修改**，避免在单个目录里堆出下一个 5000 行巨石。

### 2.1 分类原则

1. **一级目录沿用项目惯例**：`src/features/<feature>/`、`server/features/<feature>/`、`src/api/`、`server/routes/`。不新造顶层目录，不把工作区文件塞进 `src/` 根目录。
2. **二级目录按「技术底座 + 业务区域」分类**：技术底座（constants / state / components / styles / store / model / probe）承载跨阶段复用件；业务区域按任务书七个业务区命名，承载阶段专属实现。
3. **一个业务区一个目录**：后续阶段新增能力必须进对应业务区目录，禁止把新能力继续堆进 feature 根目录或塞进别的业务区。
4. **跨区通信只经统一出口**：前端业务区之间不直接 import，一律经 `state/` 与 `src/api/detail-studio.js`；服务端经 `server/routes/detail-studio.routes.js` 装配，业务区之间不互相 import。
5. **单文件体量**：区内单文件建议 ≤300 行；超出时先在**本区内**拆小文件，不新开业务区、不把职责外溢到别的目录。
6. **每个 feature 根必须有 `README.md` 目录契约**：写清分类规则、各目录职责、后续阶段归属表、排查顺序。
7. **启动链路零依赖叶子**：`server/features/detail-studio/store/` 与 `model/` 只依赖 Node 内置模块与 `app-paths.js`，禁止引入特性模块群（public 打包初始化期 TDZ 白屏，本仓已咬三次）。
8. **建目录必须同步登记**：新目录须在当阶段执行单与 `README.md` 目录契约里各补一行，禁止先斩后奏新增未登记目录。
