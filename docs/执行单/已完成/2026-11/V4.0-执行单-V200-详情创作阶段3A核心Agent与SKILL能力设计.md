## 1. 目标与边界

**核心创作能力优先。** 画布、项目、参数、模型调用、图片生成与任务管理只是执行容器；决定产品价值的是容器内的专业创作能力。当前风险：基础结构与执行能力已具备，但若只靠一个通用模型 Prompt，商品分析、消费者策划、详情叙事、视觉设计与生图提示词会模板化、套路化、缺乏专业判断。

3A 交付的是**能真正影响详情创作质量的 Agent / SKILL 专业能力体系设计方案**，并用真实商品创作思路验证其价值。

🔴 边界：
- 本阶段**只做必要的架构与能力设计 + 阶段级报告**，不做大规模代码修改、不做 UI、不实现批量生成。
- **不为追求 Agent 数量而过度架构化**；逻辑角色不等于独立模型调用次数。
- 不做视觉系统研究或基础设计规范建设（视觉系统已关闭，见 §2 第 6 条）。
- 阶段 3B 的商品分析 / 策划 / 导演 / 视觉 / Prompt / 质检实施，等 3A 报告审核通过后另出单。

## 2. 八条既有决策（红线，逐条照抄 Owner 原文）

1. 详情创作是独立工作区，不受旧详情模块的布局结构限制。
2. 继续复用 JY-Canvas 自有模型 API、模型配置、渠道配置、API Key、图片生成和相关基础能力。
3. **全应用只有 Settings 中的统一 API Key 配置入口，禁止在详情创作工作区新增 API Key 输入。**
4. 模式 C 必须保护用户原始 Prompt，不允许 Agent 或 SKILL 自动改写已确认的原文。
5. 模式 C 的真实生成内容必须来自用户确认冻结的 Prompt。
6. **现有视觉系统已关闭，不重新开展视觉系统研究或基础设计规范建设。**
7. 不修改旧详情模块，不重写项目，不另建一套模型 Provider / API Key 体系。
8. 不因本阶段需要而修改已有模型网关、渠道配置和 API Key 管理。

> 阶段 1、2 的真实上游模型与图片生成仍未完整验证，后续需用用户现有配置实际验证，**但不因此阻塞专业创作能力设计**。

## 3. 阶段 3A 八项交付要求

### 3.1 Agent 角色与职责设计

设计以下**逻辑角色**的职责、输入、输出、调用条件与协作方式：

| 角色 | 核心职责 |
|---|---|
| 详情创作总控 Agent | 任务理解、能力调度、流程管理、结果整合 |
| 商品分析 Agent | 商品理解、事实识别、卖点、差异化、信息缺口 |
| 电商策划 Agent | 消费者需求、痛点、购买动机、购买疑虑、转化逻辑 |
| 详情导演 Agent | 整套详情叙事、内容顺序、分屏规划、信息节奏 |
| 视觉设计 Agent | 每屏视觉任务、构图、场景、色彩、视觉层级、差异化 |
| 生图 Prompt Agent | 把策划与视觉方案转成可执行生图提示词 |
| 质量审查 Agent | 独立审查事实、策划、分屏、视觉、Prompt 与参数执行情况 |

🔴 **必须给出「哪些独立 Agent、哪些用角色 Prompt / SKILL / 内部流程实现」的判断与理由**（质量、稳定性、可维护性、成本四维），并明确**避免无意义的多 Agent 串行调用**。7 个逻辑角色 ≠ 7 次模型调用。

### 3.2 SKILL 目录与能力设计

至少评估以下 10 项是否需要独立 SKILL：商品分析与事实识别 / 电商消费者与转化策划 / 详情页叙事与内容规划 / 详情页视觉导演 / 单屏设计与信息层级 / 电商生图 Prompt 工程 / 参考图分析与用途识别 / 电商文案与消费者语言 / 详情创作质量审查 / 行业专属策划策略。

**SKILL 不能只是几句角色描述**，须考虑沉淀：专业方法论、工作流程、结构化输出规范、行业知识与参考资料、优秀与失败案例、质量检查清单、必要的确定性脚本或规则。并**明确区分哪些由模型判断、哪些由程序严格执行**（参考 ecommerce-skills 的 `batch.mjs` / `check_listing.py` 边界，只借思路不搬其 Provider）。

### 3.3 Agent / SKILL / 确定性程序的职责边界

给出一张职责矩阵：谁负责事实分级、谁负责流程编排、谁负责重试/幂等/参数校验、谁负责最终提示词冻结。确定性操作（任务状态、重试、参数校验、结构校验、幂等）必须由程序承担，不得塞进长提示词。

### 3.4 A/B/C 三种模式的能力调用流程

- **A 专业引导策划**：主动发现信息缺口并引导完善；不把所有问题一次性抛给用户、不过度追问已知信息；体现专业判断而非单纯收集表单。
- **B Agent 协同策划**：保留用户原始意图，AI 做专业分析、补强与规划；不只复述输入，也不能未经解释推翻用户创意。
- **C 完整提示词直通**：沿用阶段 2 规则 —— 原文优先、不调用策划 Agent 隐式改写、原文与整理版分离、整理默认关闭、显示差异由用户确认、确认后冻结、生成只用冻结版。**不得因新增 SKILL / Agent 改变上述行为**，须在调用图上证明 C 路径不经过任何策划 / 质检 / 改写节点。

### 3.5 现有模型 API 与上下文承载

说明单网关 `postChatCompletion` + 现有 `modelName` 适配点如何承载这些能力：一次/多次调用的划分、结构化 JSON 输出规范（`extractJsonObject`）、上下文窗口与分段策略、失败与降级、成本控制。**不新增任何 Provider / baseUrl / apiKey 配置 / 网关**。

### 3.6 商品事实、用户选项、参考图与创作上下文传递

- **商品事实分级**：用户明确提供 / 可合理推断 / 待用户确认 / 禁止擅自编造（不许把推断或未确认的功效、参数、认证、材料、性能包装成事实）。
- **用户选项结构化参数链**：见 §4 的盘点要求，必须给出「选项 → 结构化项目配置 → AI 策划上下文 → 分屏方案 → 最终提示词」的完整链路与逐项验证方法。
- **参考图三角色**：商品身份参考 / 视觉风格参考 / 内容结构参考，必须区分用途，不能全当风格图；商品身份锚点约束后续每屏一致性。
- **逐屏上下文**：商品事实、身份锚点、整体视觉 DNA、整体策划、当前屏定位与信息、专属构图、前后屏关系、全局选项、单屏专属要求、参考图。

### 3.7 质量审查与定向修正机制

审查不能只打分，须针对实际问题给修改建议：事实错误或编造 / 消费者逻辑不成立 / 策划缺购买价值 / 内容重复或顺序不合理 / 视觉模板化 / Prompt 不可执行或冲突 / 用户参数未生效 / 参考图未发挥作用。采用**一次定向修正 + 再审查**机制；仍不合格就明确提示用户，**禁止无限自动修正**（任务书 §十二）。

### 3.8 实施顺序、风险与验收标准

给出 3B 的分批实施顺序、每批验收点、架构与成本风险、以及可量化的能力验收口径（含 §5 的三类商品测试设计）。

## 4. 统筹 AI 的关键判断提示（执行 AI 少走弯路）

1. **7 角色 ≠ 7 次调用**：单网关 + 一次 `postChatCompletion` 可用结构化 JSON 分段 schema 承载多角色产出。建议按「阶段批次」合并（如分析+策划一次、导演+视觉一次、质检独立一次），并从延迟、失败面、成本、可调试性给理由。质量审查建议保持**独立一次调用**（避免自审自话）。
2. **§六 的选项目前并不在阶段 2**：Owner 列出的平台 / 模特或人物 / 翻屏 / 画面丰富度 / 画面比例 / 视觉风格 / 自定义要求 / 文案与商品信息，**阶段 2 实际只建了 `modelConfig`（模型渠道）、`productData`、`referenceImages`**。这些选项现存于**旧详情模块** `server/detail-middleware.js`。3A 必须先**只读盘点旧模块全部选项**（含存储键与变量名），逐项给「迁入新工作区 / 不迁入」结论与结构化字段设计 —— 🔴 **只读盘点，绝不修改旧详情模块**（§2 第 7 条），在新工作区重新实现结构化参数链。
3. **质量审查防循环**：一次定向修正 + 再审查，之后交用户；与任务书 §十二「自动修正一次」一致。
4. **模式 C 调用图隔离**：设计文档里必须有一张调用图或依赖表，证明 C 路径不 import 任何 planner / skill / 策划 / 质检节点；`frozenPrompt` 只读，`rawPrompt` 永久只读。
5. **行业策略先做加载机制**：服装 / 美妆护肤 / 清洁日化 / 家居 / 食品 / 3C 六类不要求一次做满；先设计「通用能力 + 行业策略包」的加载与覆盖机制。行业策略要体现**不同的消费者决策逻辑、内容规划、视觉表达、产品事实与宣传边界**，不是替换行业词汇。
6. **目录契约**：阶段 3 业务区 = `planning/`（前后端同名，两份 README 归属表已登记）。3A 是设计阶段不建代码目录；3B 实施时新增目录须在**执行单 + 两份 README** 三处登记。跨区通信只经 state / api 出口。
7. **视觉系统已关闭**：不要产出新的 token / 主题 / 设计规范研究；复用 `src/shared/ui/` 与既有 `tokens.css` 即可。
8. **门禁**：3A 不改业务代码 ⇒ **不刷任何基线、不必跑 `vite build`、不改 `run-all.mjs`**。若确需交付少量设计探针脚本，须按 R6 注册 `ORDER` / `FAST_ORDER`；否则只交文档，提交时 pre-commit 的 `--fast` 59/59 即够。
