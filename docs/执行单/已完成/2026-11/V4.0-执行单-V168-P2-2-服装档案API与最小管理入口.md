## 1. 需求与裁定

### 1.1 为什么是这单

V167（P2-1）已落地 `server/ai-tryon/garment-profile-store.js`（7 个纯数据层导出：创建 / 查询（含指定版本快照）/ 改版 / 列表 / 设基准 / 存资产 / 重建索引），`garment-profile-check` 41/41 全绿。**但它明确「不接路由、不接 UI」⇒ 当前数据层完全不可达，用户在界面上看不到任何东西**。战略 P2 的交付标准是「用户可以在同一张图片上连续修改多次，并且系统能够追踪每一轮修改对应的版本」，契约 §4 也把「档案管理模态 + composer 关联选择」列为 P2 范围内的 UI 最小入口。

**故本单取 P2 的第二个最小可独立交付切片：把档案数据层接成「可调用的服务端 API + 独立的前端管理模态」**，让用户能看见并管理自己的服装档案、查看版本快照、确认基准资产。这是后续「连续编辑 / 版本比较 / 回退 / 提示词档案层」的地基。

### 1.2 范围裁定（专业判断，留档可复核）

| 候选 | 是否纳入 | 理由 |

## 4. 实现规格

### 4.1 服务端 API（建议路径，可微调但须被验收覆盖）

| 方法 | 路径 | 数据层调用 | 返回 |
|---|---|---|---|
| GET | `/api/garment-profiles` | `listGarmentProfiles({status})` | `{ok:true, profiles:[summary]}` |
| GET | `/api/garment-profiles/:id?version=n` | `readGarmentProfile(id, version)` | `{ok:true, profile}`；不存在 404 `{ok:false,message}` |
| POST | `/api/garment-profiles` | `createGarmentProfile(body)` | `{ok:true, profile}`（version=1, status=draft） |
| POST | `/api/garment-profiles/:id/revision` | `updateGarmentProfile(id, body)` | `{ok:true, profile}`（旧版逐字不变） |
| POST | `/api/garment-profiles/:id/baseline` | `setApprovedBaseline(id, assetId)` | `{ok:true, profile}`；缺 assetId 400 |
| POST | `/api/garment-profiles/:id/assets` | `saveGarmentAsset(id, buffer, mimeType, meta)` | `{ok:true, asset_id, file}`（FormData 上传） |

- 🔴 **不提供 DELETE / 清空 / 批量清理**。
- 所有 `req.body` 字段须白名单校验（只收契约 §1 字段；`garment_profile_id` / `version` / `created_at` / `approved_baseline_asset_id` 不接受客户端直接指定，基准只能走 `/baseline`）。
- `id` 须过 `safeFileName` 等价规则（拒绝 `/`、`..`、绝对路径、空字节），防路径穿越；参考 `server/core/asset-urls.js:25-26` 的 resolved 前缀校验。
- 错误统一 `try/catch` 包 `await`，不泄漏堆栈与绝对路径到前端。
