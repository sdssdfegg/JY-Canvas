## 1. 目标与交付

单个详情项目最多 **20 屏**，每屏是一个独立生成任务。交付：

1. 批量图片生成（复用现有 `/api/images`，不新建图片体系）。
2. 任务状态管理：等待 / 处理中 / 成功 / 失败可见，整体进度 + 单屏进度。
3. 失败隔离：某屏失败不能导致其他成功屏丢失。
4. 失败任务可**单独重试**；中断后可恢复；任务状态持久化。
5. 幂等：避免重复提交导致重复扣费 / 重复生成。
6. 异常保护：请求超时、限流 / 临时错误、合理退避、**有限重试**（禁止无限重试）。
7. R2 授权的通用持久化任务层抽取落地，并验证旧换装任务完整兼容。

## 4. 任务模型与状态机

- 每屏 1 个独立任务，1:1 对应 V202 的 `ScreenSpec[]`；模式 C 直接消费 `mode-c.js#splitIntoScreens` 产出的 `screens[]`（原文不改、不调 AI、不 import planner）。
- 状态：`queued` → `running` → `success | failed`；可加 `cancelled`（用户主动中断）。状态迁移由**程序**判定，不交模型自由发挥。
- **幂等**：每任务带 `idempotencyKey`（项目 id + 屏 index + `frozenPrompt` 内容指纹），重复提交走 CAS 或请求账本直接复用已有任务，绝不二次扣费 / 二次生成。借鉴 MxPage `requestOnce` 思路，**不搬其代码 / Provider / 数据库**。
- **失败隔离**：单屏失败只写该任务状态，其余任务与已成功结果原样保留；成功图片落盘后不因后续失败被清理。
- **重试**：`maxAttempts` 上限（建议 2–3，写进常量）；**「不确定请求」不自动重试**（上游可能已生成但响应丢失），交用户手动点重试；退避用指数 + 抖动；区分可重试错误（超时 / 429 / 5xx / 临时网络）与不可重试（401 / 413 / 参数错误 / 内容违规）。
- **超时**：复用现有 `IMAGE_REQUEST_TIMEOUT_MS`（画板 15min）与单渠道 6min 口径，任务级另设更短的看门狗；超时后可查询再决定是否重试，避免盲重。
- **断点恢复**：服务重启后从持久化任务重建内存队列；`running` 且无结果的任务标记为「待确认」而非直接重跑，防重复扣费。
- **进度**：整体（成功/失败/总数/百分比）+ 单屏（状态、耗时、错误信息人话化、重试次数）。

## 8. 阶段验收（来源：总任务书 §十 + §十六 阶段 4 + 3A §3.8）

1. 单个项目最多 20 屏，一次性可排满 20 个独立任务；**详情队列本身不设数量上限**。
2. 每屏状态可见（等待 / 处理中 / 成功 / 失败），整体进度 + 单屏进度可查。
3. 某屏失败时其他成功屏与已落盘图片**全部保留**，不被清理。
4. 失败任务可**单独重试**，且不触发其他屏重新生成。
5. 服务中断 / 重启后可从持久化状态恢复，`running` 无结果任务不盲目重跑。
6. 任务状态持久化，重新打开项目能看到历史任务与结果。
7. 幂等：重复提交同一屏不产生第二次上游请求 / 扣费（负向对照验证）。
8. 超时、429 / 5xx、临时错误有分类处理 + 退避 + **有限重试**；「不确定请求」不自动重试；无无限循环。
9. 生成请求体 `prompt` 与 `frozenPrompt` 字节一致；模式 C 走 `screens[]` 且不经过任何策划 / 质检节点。
10. **R2 抽取后旧 AI 换装任务完整兼容**：存储 / 读取 / `.bak` 回退 / 断点恢复逐项实测，不得改坏稳定运行的换装任务管理。

## 10.2 §8 十四项验收实测结论

1. **20 屏上限 + 队列无上限**：`MAX_SCREENS=20`；`submitBatch` 全量建任务、全量入队可见（core 冒烟并发写入 20 任务无丢失，total=23 实测）。详情队列不另设并发上限。
