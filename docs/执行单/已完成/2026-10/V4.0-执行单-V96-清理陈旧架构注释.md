## 0. 为什么先做这一单（决策依据，留档）

用户 2026-10-18 授权统筹排序。候选三件：① 本单（陈旧注释）② 孤儿服务端端点 `POST /api/canvas-assets`（含 `canvasAssetDir` 两个消费点）③ UI 规范线的 AppSidebar。统筹排序 **① → ② → ③**，依据：

1. **技术债利息率最高**：V93/V94 刚删完无限画布，注释里仍写着 `createCanvasActions` / `addCanvasFiles` / `handleCanvasDrop` / `canvasCenterPoint` 等**已删符号**。将来人或 AI grep 这些名字会命中注释、误判其仍存在——**这正是用户最初抱怨的"总是打架"**。现在上下文最新、清理成本最低；拖越久，将来要重新查证"这符号到底删没删"，利息随时间上升（趁热打铁）。
2. **风险最低**：纯注释、零逻辑改动，不可能引入功能回归，可独立快速交付。
3. **diff 干净**：`main.jsx` / `main-handlers.js` / `canvas-generation-handlers.js` 三个文件实测索引已是 **LF**（`git ls-files --eol` = `i/lf w/lf`），改注释**不会**触发 V93 那种全文件 CRLF 归一化（那次 4118 增/4508 删的惊悚 diff），语义 diff 会很小。
4. **② 排后**：孤儿端点牵连**用户可见功能**——`canvasAssetDir` 被 `storage-usage.js` 用于设置页「画布资源」磁盘用量统计，是否连这一项一起下掉需要单独裁决，不该与纯注释清理混一单。
5. **③ 排后**：AppSidebar 属"新价值"而非"还债"，先清干净认知债再推进更稳。
