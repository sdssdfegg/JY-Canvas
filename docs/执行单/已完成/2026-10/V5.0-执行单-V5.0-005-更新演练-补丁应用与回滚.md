# V5.0-005 · v5.0.0 增量更新演练（补丁应用 + 回滚）

- **类型**：发布里程碑 / 更新演练
- **日期**：2026-10-23（承接 V5.0-004）
- **前置**：V5.0-004 交付时把「④ 更新演练」记为未做（`④—`），用户要求补做：验证 `patch-from-v4.0.16` 能正确应用到已装 v4.0.16 的机器上（→v5.0.0），且能回滚（→v4.0.16）。
- **结论**：**演练全绿（5/5 阶段通过）**，但过程中**查出并修掉 3 个会让客户「应用更新.bat 必然失败」的阻断缺陷**——它们不是演练环境差异，是真实的发货缺陷。

## 一、为什么必须单独建单

V5.0-004 只验证了整包能起。增量升级是**另一条链路**：客户拿着旧安装，用「旧安装里那份更新器」去消费新补丁。
这条链路此前**从未被真实验证过**——历史演练（v4.0.0→v4.0.1 等）全部**显式传了 `-PackageDir`**，
而客户的「应用更新.bat」不会传，所以缺陷一直被掩盖。

## 二、查出并修掉的 3 个阻断缺陷（本单核心价值）

### BUG-A · 补丁清单写在补丁根，更新器去 `updates\` 里找

- **现象**：`apply-update.ps1 -From updates` 恒报「补丁目录里既没有 patch-manifest.json 也没有 build-manifest.json」。
- **根因**：`build.mjs` 的 `makePatch()` 把 `patch-manifest.json` 写到**补丁包根目录**；而更新器按 `$fromDir = $PackageDir/updates` 找清单。
  客户按说明把 `updates\` 放进安装目录后，根目录那份清单**根本不会被带走**。
- **修法**：清单改写到 `patchDir/updates/patch-manifest.json`；同时把 `updater/` 排除出「待应用清单」
  （它已由自包含拷贝交付，否则更新器会试图覆盖正在运行的自身，且清单里列了却不在 `updates\` 中会触发「缺失」而整体放弃）。
- **影响面**：**v4.0.0 以来的所有补丁包都带这个缺陷**（历史目录里 `patch-manifest.json` 全在补丁根）。

### BUG-B · 旧更新器在 `param()` 缺省值里算 PackageDir → 一跑就崩

- **现象**：跑 v4.0.16 那份更新器（走真实 `-File` 入口）报
  `Split-Path : ParameterArgumentValidationErrorNullNotAllowed`。
- **根因**：
  ```powershell
  param([string]$PackageDir = (Split-Path -Parent $MyInvocation.MyCommand.Path))  # ← param 绑定期
  ```
  此时 `$MyInvocation` 还指向 `powershell.exe` 的调用，`MyCommand.Path` 为 **null** ⇒ `Split-Path -Parent $null` 直接抛错。
  （即便算出值，它也是脚本所在目录 = `updater\`，而补丁 `updates\` 在**安装根**，仍然对不上。）
- **修法**：`PackageDir` 缺省改成空串，挪到**脚本体**里算（此时 `$MyInvocation.MyCommand.Path` 才是脚本自己），
  并加 **grandparent 兜底**（`updater\` 的父目录 = 安装根）。
- **关键约束**：修正后的更新器**只存在于 `tools/`，历史已发版（v4.0.0–v4.0.16）里全是旧版**。
  旧安装不会自动获得它 ⇒ **补丁包必须自带这份修正后的更新器**，见 BUG-A 后的「自包含」改造。

### BUG-C · `apply-update.ps1` 是「双 BOM」，PowerShell 直接解析失败

- **现象**：双 BOM 文件跑 `-File` 报「意外的属性 CmdletBinding」；
  但如果把 BOM **去光**，PS5.1 会按系统 ANSI 解码中文 → 报语法错（实测 L146「意外的标记 }」/ L229 / L242「字符串缺少终止符」）。
  **两种极端都会让更新器不可用。**
- **根因**：`tools/apply-update.ps1` 头部是 `EF BB BF EF BB BF`（两个 BOM），是唯一一个双 BOM 的 ps1
  （`verify-package.ps1` / `make-shortcut.ps1` 都是正常的单 BOM）。
- **修法**：**归一为「恰好一个 BOM」**——源码文件已修正；并在 `build.mjs` 的 `shipTools()` 里加 `normalizePs1Bom()`，
  每次构建自动归一（不是手工改产物，防复发）。
- **教训固化**：第一轮排查用「去 BOM」绕开双 BOM 问题，结果 Phase D 又被去掉最后一个 BOM 而崩。正解是归一成 1 个，不是去掉。

## 三、配套改造：补丁包「自包含」

因 BUG-B（旧安装里的更新器是坏的），`makePatch()` 额外把以下内容从发布包拷进**补丁根**：

| 随补丁交付 | 作用 |
|---|---|
| `updater/`（修正后的更新器） | 覆盖旧安装的坏更新器——**这是补丁能被应用的先决条件** |
| `应用更新.bat` / `回滚更新.bat` / `校验安装.bat` | 入口齐备，客户无需依赖旧安装里的旧 bat |
| `更新与校验说明.txt` | 文案同步为「把补丁包里的**所有内容**解压到软件目录（覆盖同名文件）」 |

> 旧文案「解压出 `updates\` 放到本目录」已不可用（旧更新器必崩），已在 `build.mjs` 的 `更新与校验说明.txt` 模板里同步改掉。

## 五、演练踩坑（口径固化，防后人重复踩）

1. **node 的 `fs.cpSync` 拷贝大目录会静默 exit=127**：本环境 node 走 `node-brokered-fs-shim`，
   拷 95 MB 级目录直接 127 且**无任何输出**（`rmSync` 不受影响）。
   ⇒ 重活改用原生 `robocopy`（实测 95 MB 仅 184 ms）；`robocopy` 退出码 **0–7 都是成功**，只有 ≥8 才是失败。
2. **SEA 单文件 exe 运行期会锁住自身文件**：冒烟后没彻底杀掉 exe 就回滚 → `Copy-Item` 覆盖 exe 报「系统错误。」
   ⇒ 冒烟后要 `kill` + 等 `exit` 事件 + `taskkill /F /IM` 兜底 + 等待后再回滚。
3. **回滚分支用 `exit` 而非 `Finish()` ⇒ `Stop-Transcript` 跑不到**，日志会残留上一轮内容 ⇒ 跑前先清日志。
4. **`cd` 在本工具里不跨调用保持**：一律用绝对路径，别依赖上一次的 `cd`。
