# V4.0 执行单 V144 — AI 画布节点生态扩展（强类型 outfit 节点 + 节点间图像数据总线）

> 前置依赖：V143（AI 无限画布 MVP1-6 + 加固 + 导入导出 + 出图参数）已落地并合入 `main`，`run-all --fast` 49/49、`vite build` EXIT=0。本单在 V143 引擎之上扩展**节点生态**，不重写画布引擎、不动 outfit 业务页面。
> 方向裁定：P2 服装档案仍卡 E6（需用户本机直播抽查，用户侧阻塞，未定稿 ADR-001）；AI 画布为无阻塞独立 track，故 V144 选「AI 画布节点生态扩展」（用户 2026-10-29 委派「你定」）。

## 目标

把 outfit 既有 5 类生图能力（**换装 / 改色 / 精修 / 局部编辑 / 参考生图**）封装为画布**强类型节点**，并建立「上游节点选中版图像 → 下游节点输入图」的**图像数据总线**，使画布从「通用生图」升级为「可编排的成套出图工作流」。

验收标准：
1. 画布支持新增 5 类强类型节点，每类有专属参数面板（复用 outfit 现有设置 schema，不另写一套）。
2. 节点间可传递图像：上游结果节点的「当前选中版」作为下游节点的输入图，链式多轮连续编辑（换装→改色→精修→出多版）。
3. 类型不匹配（如把不支持图像输入的端口接图像输出）**fail-closed**：拒绝执行 + 工具栏告警，不静默出错、不污染下游。
4. 多 Agent（planner）能规划包含 typed 节点的图；动作白名单扩展覆盖新节点类型（自然语言操作可用）。
5. 无头验收脚本覆盖：5 类节点构造、数据总线传递、类型不匹配拒绝（fail-closed 断言）。

## 设计要点

- **复用而非重写**：typed 节点 = V143 通用生成节点的「强类型特化」。节点适配层只负责（a）把画布输入图 + 参数翻译为 outfit 端点 payload；（b）把返回图写回数据总线。生图链路、模型选择、配额全部复用既有。
- **数据总线契约**：在 `ai-canvas-store` 增 `outputImage: { nodeId, versionId, ref, dataUrl? }`；下游节点 input 解析「上游结果节点当前选中版」。v143 已有结果版本管理（每节点 12 版），本单复用其选中版作为数据总线上游源。
- **fail-closed 双校验**：① 连接时（UI 层）按端口 `acceptedKinds` 拒绝非法连线；② 运行时（workflow 引擎 topo 执行前）二次校验，防止经导入/脚本构造的非法图偷偷执行。
- **隔离纪律**：不动 outfit 页面、不改 outfit schema 语义、不新建服务端接口；只新增画布侧节点适配层。outfit 存储键、提示词模板一律不动。
- **搬运丢参防护**：节点适配层 payload 构造必须逐项比对 `outfit-batch-execution.js` 与页面请求的全部入参（历史已踩两次坑），由 `ai-canvas-node-outfit-check.mjs` 做结构断言。

## 复现 / 验收方式

1. `runtime/node/node.exe node_modules/vite/bin/vite.js build`（或 `npm run build`）通过。
2. `runtime/node/node.exe scripts/verify/run-all.mjs --fast`（或 `npm run check`）全绿（含新增 `ai-canvas-nodes-check` / `ai-canvas-node-outfit-check`，--fast 计数 49→51）。
3. 浏览器进「无限画布」：加换装节点（输入图 + 提示词）→ 执行 → 其输出连改色节点 → 改色节点自动吃上游选中版 → 执行出图 → 再连精修节点，验证链式多轮。
4. 类型不匹配冒烟：把不支持图像输入的端口接图像输出 → 工具栏告警、执行被拒。

## MVP-1：节点类型体系 + 端口/数据总线契约（待落地）

定义 `ai-canvas-nodes.js` 节点注册表：5 类 `kind`（`outfit-tryon` / `outfit-recolor` / `outfit-retouch` / `outfit-local-edit` / `outfit-reference`）+ 每类 input/output 端口与 `acceptedKinds`。落地 `ai-canvas-data-bus.js` 输出图像契约 + 下游解析。 store/workflow 加类型校验骨架（先 fail-closed 拒绝，MVP-2 起接线真生成）。

## MVP-2：换装节点 + 改色节点（待落地）

最高频两类优先。实现 `ai-canvas-node-outfit.js` 的 tryon/recolor 适配：输入图取自数据总线上游（或节点自带上传）、参数面板复用 outfit 设置 schema、调 `POST /api/generate-outfit`、返回图写回数据总线。 `ai-canvas-panels.jsx` 加两类参数面板。

## MVP-3：精修 / 局部编辑 / 参考生图节点（待落地）

补齐 retouch / local-edit / reference 三类适配（复用对应 outfit 端点）。局部编辑需把上游图像 + 蒙版区传入；参考生图需参考图 + 提示词。

## MVP-4：多 Agent prompt 扩展 + 动作白名单扩展（待落地）

`ai-canvas-orchestrator.js` 的 planner prompt 扩展：能规划含 typed 节点的图（描述 5 类能力 + 数据流向）。动作白名单（`ai-canvas-view.jsx` 自然语言操作解析）扩展覆盖新增节点类型的增/改参/连线/执行。

## MVP-5：无头验收全量 + 真机冒烟指引（待落地）

`ai-canvas-nodes-check.mjs` + `ai-canvas-node-outfit-check.mjs` 全量覆盖（5 类构造、数据总线传递、类型不匹配 fail-closed、payload 对齐防丢参）。补执行单「本机真机冒烟」章节（用户 Key + 中转站）。 `run-all --fast` 计数 49→51。

## 回滚

- 本单为**纯增量**（新增节点适配层 + 数据总线 + 验收脚本），不动 outfit 引擎核心与生图链路语义。
- 回滚方式：特性分支整体 revert / 丢弃；画布旧通用生成节点保留，typed 节点移除后不影响 V143 既有能力。
- 数据总线契约仅在画布隔离存储键 `jingyin-ai-canvases-v1` 内增字段，回滚后旧画布项目忽略未知 `kind`（前向兼容）。

### 实施范围与原始方案差异（留痕）
- 原方案列 5 类强类型节点；实际落 **3 类可执行**（outfit-tryon / outfit-recolor / outfit-retouch），outfit-local-edit / outfit-reference 仍注册进注册表但 `runnable:false`（暂未开放）。
  理由：local-edit 需画布内裁剪/涂抹交互、reference 需服务端参考图路由对齐；为守住「搬运不丢参」硬保证（历史已踩两次），不发出会 400 的请求，故标为 deferred 而非半成品。后续 MVP 再开放。
- 数据总线未新增 `outputImage` 存储字段：复用 V143 既有的 `node.data.src`（图片/结果节点）与 `node.data.resultUrl`（生成/outfit 节点选中版）作为上游输出源，`collectNodeInputs(current, node)` 按 `toPort` 归集上游端口图 + 提示词。存储键 `jingyin-ai-canvases-v1` 仅增节点 `type` 取值，前向兼容。
- 服务端零新增端点：复用 `POST /api/generate-outfit`（同名字段 `image` 按序 图1=model、图2=服装/颜色参考），结果在 `res.payload.image`。
- 多 Agent 白名单：`server/ai-canvas-agent.js` 的 `ACTION_CONTRACT` 与 `src/features/ai-canvas/ai-canvas-agent.js` 的 `CANVAS_AGENT_ACTION_TYPES` 同步扩展 `add_outfit_tryon_node` / `add_outfit_recolor_node` / `add_outfit_retouch_node`（顺序逐项一致，ai-canvas-agent-check.mjs:171 断言）。
