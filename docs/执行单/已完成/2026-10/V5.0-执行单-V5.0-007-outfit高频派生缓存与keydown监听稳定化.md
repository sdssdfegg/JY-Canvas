# V5.0-007 · outfit 高频派生缓存（7 次 O(n) → 1 次）与 keydown 监听稳定化

- **类型**：性能优化（R1 派生收口 / 引用稳定）
- **日期**：2026-10-24
- **前置**：V5.0-006（批量结果卡 memo）已归档
- **裁定依据**：`docs/规划/V4.0-全局架构与性能规划-2026-10-13.md` R1「状态就近」精神 +
  R2「父组件传稳定引用」。本单不是再加一层 memo，而是**把卡 bail 也省不掉的父层开销收口**。

## 一、为什么做这一单

V5.0-002/006 让两张卡真正 bail 了，但**父层每次渲染的 O(n) 派生仍在**——卡 bail 只省了
「渲染卡」，省不掉「算要不要渲染卡」。`outfit-workflow.jsx` 顶层有一段每次渲染都跑的派生：

```js
const completedCount = tasks.filter((t) => t.status === "success").length;  // O(n)
const failedCount    = tasks.filter((t) => t.status === "failed").length;   // O(n)
const runningCount   = tasks.filter((t) => t.status === "running").length;  // O(n)
const detachedCount  = tasks.filter((t) => t.status === "detached").length; // O(n)
const imageCount     = completedCount;
const visibleTasks   = resultFilter === "video" ? [] : resultFilter === "image" ? tasks.filter((t) => t.result) : tasks; // O(n)
const resultPreviewTasks = visibleTasks.filter((t) => t.result);            // O(n)
```

**每次渲染 7 次 O(n) 遍历 + 6 个临时数组分配**。批量任务几十条时，这段是纯浪费。

## 二、现状核查（派单前实测，不臆断）

| 核查项 | 结论 |
|---|---|
| 派生位置 | `outfit-workflow.jsx:490-496` |
| 计数方式 | 4 次**独立** `filter().length` ⇒ 4 次 O(n) |
| 是否缓存 | ❌ 全部无 useMemo；文件里 31 行含 `.filter/.map/.sort`，仅 4 处 useMemo |
| **连带伤害（本单关键发现）** | `resultPreviewTasks` 是 `:1022` **useEffect（keydown 监听）的依赖** ⇒ 每次渲染都是新数组 ⇒ **每次重渲染都要解绑再重绑一次全局 keydown 监听器** |
| `resultPreviewTasks` 其它用途 | `:1022`（effect 依赖）、`:1449-1453`（预览左右翻页）、`:1940`（传下游） |
| 4 个计数的引用点 | `494 / 518-524 / 1572 / 1574 / 1575 / 1653` —— **全部晚于声明 490**，无 TDZ 风险 |
| 依赖变量声明位置 | `tasks` **:308**、`resultFilter` **:310** —— 均早于 490 ⇒ 此处加 useMemo **不会 TDZ**（V136 教训已复核） |
| `useMemo` 是否已 import | ✅ `:1` 已导入 |

> ⚠️ 本单特意复核了 V136 的 TDZ 坑：V136 就是因为「派生消费了后面才声明的 `selectedTaskIds`」而崩。
> 本单依赖的 `tasks`/`resultFilter` 声明均早于派生点，且 4 个计数的引用点全部晚于 490。

## 三、方案（纯加法，零语义变更）

### 3.1 四个计数合并为**一次遍历** + useMemo

```js
const taskCounts = useMemo(() => {
  let completed = 0, failed = 0, running = 0, detached = 0;
  for (const task of tasks) {
    if (task.status === "success") completed += 1;
    else if (task.status === "failed") failed += 1;
    else if (task.status === "running") running += 1;
    else if (task.status === "detached") detached += 1;
  }
  return { completed, failed, running, detached };
}, [tasks]);
const completedCount = taskCounts.completed;
const failedCount = taskCounts.failed;
const runningCount = taskCounts.running;
const detachedCount = taskCounts.detached;
```

**语义等价论证（必须成立才可合）**：`task.status` 是**单值字符串**，一个任务不可能同时
命中两个分支；原代码 4 次独立 filter 亦各自只统计一种状态 ⇒ `else if` 链与 4 次 filter
**逐状态完全等价**（含 `pending` 等其它状态：两边都 +0）。

### 3.2 `visibleTasks` / `resultPreviewTasks` 用 useMemo 稳定引用

```js
const visibleTasks = useMemo(
  () => (resultFilter === "video" ? [] : resultFilter === "image" ? tasks.filter((task) => task.result) : tasks),
  [tasks, resultFilter]
);
const resultPreviewTasks = useMemo(() => visibleTasks.filter((task) => task.result), [visibleTasks]);
```

- 依赖数组必须**完整**：`[tasks, resultFilter]` / `[visibleTasks]`（漏依赖会出陈旧值，比性能问题更糟）。
- 附带收益：`resultFilter === "video"` 分支原本每次新建 `[]`，缓存后复用同一引用，
  ⇒ `:1022` 的 keydown effect 不再每次重渲染都解绑/重绑。

### 3.3 不动的事

- 不改任何 JSX、不改变量名与类型（下游无感）；
- 不改 `imageCount`（仍是 `completedCount`）；
- 不把 `tasks` 本身换数据结构；
- 不引新依赖。

### 探针时序缺陷修复（`composer-stable-height-check` 假红）

首轮 run-all 该项失败（`foundEmbed=false`、`tops=[]`）。按纪律做 base 对照：base 内容 +
**仅 touch mtime**（不改内容）同样失败 ⇒ 非本单回归，是探针自身时序缺陷——
outfit 视图懒加载，dev 下**任何**对 `outfit-workflow.jsx` 的改动都会触发 Vite 重编译，
而探针固定 `wait(900)` 常在 embed 挂载前就判定（「不动就过、一动就红」）。
修法：`composer-stable-height-page.jsx` 的固定等待改为**轮询等待**（`waitForEmbed`，
最多 10s，200ms 间隔），**断言逻辑与阈值一律不变**。修复后带本单改动复跑全绿
（`tops=[1128×5] spread=0`、`count=4`、临时页 top=1128）。

## 五、风险与边界

- **陈旧值风险（最高）**：useMemo 依赖漏写 ⇒ 计数不更新。对策：依赖数组只写 `tasks`/`resultFilter`
  这两个 useState 源，且二者声明早于派生点；验收加「计数正确性」专项断言。
- **TDZ 风险**：已复核（见 §二），依赖与引用点顺序均安全。
- **过度 memo 反噬**：本单只对 **O(n) 且依赖稳定** 的派生加缓存；计数合并后遍历 7→1，
  即便 useMemo 本身有开销也是净收益。
- 不动 P0 生命线业务语义（批量生成/批量换装/局部回贴）。

## 六、结论（归档时回填）

- **父层 O(n) 派生 7 次 → 1 次**（4 计数合并为一次遍历 + useMemo；`visibleTasks` /
  `resultPreviewTasks` 缓存后 `tasks`/`resultFilter` 不变即零开销），临时数组分配 6 → 1。
- **附带收益（关键发现落地）**：`resultPreviewTasks` 引用稳定 ⇒ `:1045` 那个以它为依赖的
  全局 keydown effect 不再每次重渲染解绑/重绑（改前每次 render 都重绑一次）。
- 语义零变更：算法等价性 fuzz 20000 例零漂移 + 三组计数运行期断言 + 预览环形翻页实测。
- 净行数：`outfit-workflow.jsx` −101 行（注释增、代码减）；size-ratchet 体量下降 7 处。
- 探针文件 `composer-stable-height-page.jsx` 的时序修复属**修真实缺陷**（非掩盖）：
  固定 900ms 盲等改轮询，断言不变；已由 base+touch 对照证实是探针自身缺陷。
