# V5.0-006 · 批量结果卡 memo 化（R2 收官：批量结果卡 / 状态卡）

- **类型**：性能优化（R2 重渲染隔离，第二弹）
- **日期**：2026-10-24
- **前置**：V5.0-001（主画廊卡抽取）+ V5.0-002（memo 真正生效）已归档
- **裁定依据**：`docs/规划/V4.0-全局架构与性能规划-2026-10-13.md` R2 原文——
  「列表项必须是独立 `memo` 组件；父组件传稳定引用。**重点对象：批量结果卡、参考图缩略条、任务行**。
  判定方法：改一个任务的状态，只应重渲染那一张卡。」

## 一、为什么做这一单

V5.0-001/002 只覆盖了**主画廊**（`quick-gallery-card.jsx`）。R2 明列的三类重点对象里，
**批量结果卡仍未 memo**：`src/features/outfit/panels/ResultQueue.jsx` 的 `visibleTasks.map(...)`
是**整段内联**，`OutfitWorkbench` 把 16 个 handler 直接透传下来。

批量生成是高频重灾区：

- 同屏可达 **50+ 张卡**，每卡含 `CachedImage` + `ReferenceThumbTray` + 4 个操作按钮 + 提示词按钮 + meta；
- 生成/轮询期间任务状态**频繁翻转**（running → success / failed），每次上游重渲染都会**重建全部卡**；
- 上游 16 个 handler 来自普通工厂、每次 render 重建闭包 ⇒ 即使把卡 `memo` 也会被绕过（与 V5.0-001 同病）。

方向 = 用户已肯定的体感（「变丝滑」：视图壳拆分 + TDZ 修复 + memo），且**不依赖样本、不烧额度**。

## 二、现状核查（派单前实测，不臆断）

| 核查项 | 结论 |
|---|---|
| 卡是否 memo | ❌ 否，`ResultQueue.jsx:63` 起整段 `visibleTasks.map(...)` 内联 |
| 分支数 | 2：**非 success**（loading/failed 状态卡，`:74-108`）+ **success**（结果卡，`:120-237`） |
| 上游 handler | 16 个，均由 `OutfitWorkbench`（`OutfitWorkbench.jsx:174-189`）透传，来自上游普通工厂 |
| 整包透传的集合 | `selectedTaskIds`（Set）、`downloadFeedbackIds`（Set）、`brokenTaskImages`（对象） |
| `settings` 引用 | ✅ 稳定 —— `outfit-workflow.jsx:303` `useState(() => mergeOutfitPageSettings(...))` |
| `activeOutfitPage` 引用 | ✅ 通常稳定 —— `outfit-workflow.jsx:390` `outfitPages.find(...)` 返回数组元素（仅 fallback 分支会新建） |
| `resultReplaceTargetId` | 字符串（标量） |
| 每卡已派生的布尔 | 仅 `selected`（`:64`）；`isDownloaded`/`isReplaceTarget` 仍是**卡内**查集合 |

结论：与 V5.0-001 完全同构，可直接复用 V5.0-002 的成熟手法。

## 三、方案（复用 V5.0-002，零陈旧闭包、零触及上游工厂）

### 3.1 新建 `src/features/outfit/panels/result-card.jsx`

两个 `React.memo` 组件，JSX **逐字搬运**（行为零改）：

- **`ResultCard`**（success 分支，搬 `ResultQueue.jsx:120-237`）
- **`TaskStatusCard`**（非 success 分支，搬 `:74-108`）

### 3.2 `ResultQueue.jsx` 内做「晚期绑定委托」

沿用 V5.0-002 的 `handlerLateRef` 同款手法（本仓既有模式）：

```js
const handlersRef = useRef(null);
handlersRef.current = { toggleTaskSelected, retryTask, downloadTask, …共 16 个 };   // 每渲染刷新
const cardHandlers = useMemo(() => ({
  toggleTaskSelected: (id) => handlersRef.current.toggleTaskSelected(id),
  …                                        // 稳定引用，调用时经 ref 转发到最新实现
}), []);
```

**不在上游 `outfit-workflow.jsx` / handler 工厂里加 `useCallback`/`useMemo`**（陈旧闭包风险，且触 P0 生命线）。

### 3.3 集合改「每卡派生布尔」（map 内派生，卡只收标量）

| 原来（卡内查整包） | 改为（map 内派生，传入卡） |
|---|---|
| `selectedTaskIds.has(task.id)` | `selected`（已有，保留） |
| `downloadFeedbackIds.has(task.id)` | `isDownloaded` |
| `resultReplaceTargetId === task.id` | `isReplaceTarget` |
| `brokenTaskImages[task.id] \|\| task.resultMissing` | `brokenEntry`（单条；多为 `undefined`，引用天然稳定） |

对象型 props 保留整包但**已核实引用稳定**：`settings`（useState）、
`activeOutfitPage` 卡内只用 `.workflowMode` ⇒ **派生成标量 `workflowMode`** 传入（彻底规避 fallback 分支新建对象的风险）。

### 3.4 卡的 props 清单（防漏项）

**ResultCard**：`task` `taskIndex` `selected` `isDownloaded` `isReplaceTarget` `brokenEntry`
`settings` `workflowMode` `handlers`（稳定委托对象）

**TaskStatusCard**：`task` `selected` `settings` `handlers`

> ⚠️ props 漏项 = 运行期 undefined（vite build 验不出）——沿用 V65/V68 的负向对照兜底。

### 探针已知限制（如实标注）

- `rerunSkipped=true`：注入的探针任务无原始上传图 ⇒ `canRerunTask(task)` 为 false ⇒
  重刷按钮 `disabled`（UI 提示"历史结果缺少原始上传图，不能重刷"）。**数据限制，非代码回归。**
- `retrySkipped=true`：同理，failed 卡的 `.assetRetryButton` 受 `canRetry = failed && canRerunTask(task)` 约束未渲染。
- 拖拽替换高亮 / 参考图右键未纳入本次探针自动化（需多元素拖拽序列），其 handler 与派生布尔
  `isReplaceTarget` 的接线已由静态搬运 + 探针其余项间接覆盖。

## 五、风险与边界

- **批量生成是 P0 生命线**：本单为**纯搬运 + 引用稳定化**，不改任何业务判断与 JSX 结构；
  两个分支的卡都要覆盖，避免只搬 success 分支导致 failed/running 卡行为丢失。
- **`brokenTaskImages` 是会话内失败标记**：只在加载失败时变更，常态下 `brokenEntry` 为 `undefined`，不破 memo。
- **不追求 DevTools 打点**：memo 生效由架构保证（同 V5.0-002），实时打点验证按先例挂起待用户本地。
