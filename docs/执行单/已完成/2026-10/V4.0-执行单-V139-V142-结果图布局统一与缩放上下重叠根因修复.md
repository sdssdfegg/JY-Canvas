## 0. 背景与结论

用户需求：① 快捷生成与批量生成的结果图布局不一致；② 结果图多排时纵向间距逐渐缩小/出现视觉重叠；
③ 右上角「结果图显示百分比」放大后图片上下重叠（**百分比越大叠加越厉害**）；④ 缩放默认要为 75%。

**结论：四条全部解决，且"重叠"的真根因与前两轮的归因完全不同**（见 §8 错误归因时间线）。

真·根因（V142，浏览器探针实测坐实）：
结果画廊的 grid **行轨道被锁死**——探针读到 `grid-template-rows: 96.25px 96.25px 96.25px 96.25px`，
而这个值与卡片真实高度（`轨道宽 × 4/3`，75% 缩放时 176px）**无关**。于是每张卡溢出本行约 80px、
压住下一行 = 用户看到的上下重叠；并且缩放只放大卡片高（176→340px）、被锁的行高不变 ⇒
**唯一解释了「百分比越大叠加越厉害」**。

修复：两边共用的网格合并规则加两行——

```css
grid-template-rows: none;      /* 置空被锁死的显式行轨道 */
grid-auto-rows: max-content;   /* 隐式行按卡片真实高自动撑开 */
```

随后用探针实测确认：行高恒 = 卡片真实高，行步进恒 = 行高 + 12px gap，缩放 75%→145% 全档位**重叠恒 0**。

## 2. 实现要点

- **V140（两边口径统一）**：快捷 `.galleryStrip.galleryStripColumns` 与批量 `.outfitWorkflowEmbedded .taskGrid`
  合并为同一条规则，列模板/间距/对齐完全一致，间距统一走尺寸令牌 `--space-3`（=12px = `GALLERY_GAP_PX`）。
  另删除 `@media(max-width:760px)` 里把快捷卡片压成 `calc((100%-12px)/2)≈82px` 的覆盖——
  快捷键结果画廊已是 grid，`100%` 指向 176px 轨道 ⇒ 卡片被压到 82px 而轨道仍 176px，与批量的 176px 明显不一致。
- **V141（列数脱节加固）**：列数由 JS 注入 `--gallery-columns` 改为纯 CSS
  `repeat(auto-fit, min(var(--asset-card-min), 100%))`：浏览器按「当前缩放后的轨道宽」原子式算列数，
  杜绝缩放瞬间「列数用旧卡片宽、轨道已用新卡片宽」的脱节；`min(...,100%)` 防窄容器溢出。
  同时把基类 `.assetCard` 的 CSS 级虚拟化关掉（参考/视频画廊用 `.referenceAssetCard`/`.videoAssetCard`，不受影响）。
- **V142（真根因）**：见 §0。探针通过三个对照实验坐实——
  ① 移除 grid 类退回 flex ⇒ 重叠 0；② 保留 grid 但强制 `grid-template-rows:none` + `grid-auto-rows:max-content` ⇒ 重叠 0；
  ③ 默认态（锁死 96.25px×4）⇒ 重叠 28 处。**且普通 CSS 规则（无需 `!important`）即可覆盖该行高。**
- **默认 75%**：两侧 `galleryZoom` 初值改 `0.75`；`changeGalleryZoom` 的 clamp 范围是 `max(0.75, min(1.45, …))`，
  75% 是允许下界 ⇒ 不会被夹回 1；该状态**不持久化**（纯 useState，不进 localStorage），刷新即回到默认 75%。

### 4.4 其它验收点

- **图片加载前/后**：卡片高由固定轨道宽 + `aspect-ratio: 3/4` 决定，与 `<img>` 是否加载无关 ⇒ 无布局跳动。
- **不同原始比例**：预览区盒模型固定（宽 → 高 = 4/3），比例差异仅由 `object-fit: cover` 吸收，不影响网格。
- **既有操作**：编辑/删除/下载/预览/重刷/标注编辑的卡组件**零改动**（仅 CSS），回调逐项透传不变。
- **截图目视**：145% 档位实拍 → 无重叠、卡片尺寸一致、右上角显示 145%。
- **harness 自测**：修复态 75%/145% 均 vGap=12px、重叠=否；破坏态 75%/100%/145% vGap = −67.8/−126.4/−232px、重叠=是
  ⇒ 精确复现了「缩放越大叠加越厉害」的规律（harness 已用真实浏览器交叉验证，且已修掉其自身的读数滞后与遗漏判重问题）。

## 8. 错误归因时间线（本单最重要的产出）

| 轮次 | 当时的归因 | 结果 |
|---|---|---|
| V139 | 结果卡 `content-visibility:auto` + `contain-intrinsic-size:auto 260px`（离屏卡按 260px 估计占位） | **错**。探针实测两边结果卡这两项都已是 `visible`/`none`，重叠依旧 |
| V141 | 再加一层：JS 注入 `--gallery-columns` 可能"列数用旧卡片宽、轨道用新卡片宽"而脱节 | **不足**。改成纯 CSS auto-fit 后 118% 仍重叠（用户第二张截图） |
| V142 | 上浏览器探针实测 DOM 几何 ⇒ **行轨道被锁死成 96.25px×4** | ✅ 三个对照实验坐实，改后全档位零重叠 |

教训（写给后来者）：

1. **CSS 归因必须由探针实测 computed 值坐实**，不能靠读源码/注释静态推断——本单曾把"自己写的注释文字"
   当成"服务器仍在吐旧 CSS"，闹出二次误判。
2. **先确认现象可复现再做归因**：三个对照实验（退 flex / 强制作废行高 / 默认态）才是定位布局问题的正确姿势，
   比"读 CSS 猜哪个属性可疑"可靠得多。
3. **用户报"设为 75%"这类明确要求要当场核对**：本单直到用户第二次追问才发现默认值根本没改。
4. **部署模型要先确认**：8787 实际是 `node server/index.js`（内挂 Vite 中间件 + 每次请求读磁盘），
   改源码刷新即生效；早前几轮误判为「需重建 dist / 二进制」，属多余动作。
5. **跑浏览器类脚本的正确方式**：需要在同一环境的 shell 里导出 `LOCALAPPDATA`，否则所有依赖浏览器的脚本会集体误报失败。
