### 1.2 根因链（统筹已实测闭环，非代码回归）

1. `server/index.js:13-21`：NODE_ENV 未显式设置时，**检测到 `dist/.release-mode`（或 exe 旁同名标记）即强制 `NODE_ENV=production`**；
2. production 下 `server/app.js:100-104` 走「磁盘前端」分支：`express.static(dist)` + `app.get("*") → sendFile(dist/index.html)`（SPA fallback），**不挂 Vite dev middleware**；
3. 6 个探针脚本的 program 都是 `page.evaluate(() => import("/scripts/verify/xxx-page.jsx"))`——dist 里没有 scripts/ 目录，请求被 SPA fallback 打进 index.html，浏览器报 `Failed to fetch dynamically imported module`（原始回执实测抓到）；
4. 污染源 = `dist/.release-mode` 文件：**V121 统筹复核时为模拟 release 模式 `touch` 后遗留**（10-19 23:36）；且 `scripts/secure-win-release.mjs:208` 构建发布包时**正式写入**该标记——即每次构建后跑验证都必然复发。
5. 统筹已删除遗留标记并重跑：**6/6 全部恢复 ok=true**（composer-stable-height 的 CSS 断言失败同为连带，非真回归）。

### 1.3 为什么以前没暴露

构建发布包与跑全量验证历史上不在同一工作流里串行发生；V121 首次「构建（public 冒烟）→ 遗留标记 → 用户全量验证」串成一线，触发。

### 2.2 辅修：污染检测警告（run-all 层）

### 2.3 门禁锁定：新增静态断言防新增脚本回归

新开 `scripts/verify/verify-dev-mode-check.mjs`（或并入既有静态 check，择简——**推荐新开**，语义独立）：

## 4. 易错点（凭历史教训预设）

1. **spawn env 形态不一**：19 个脚本是不同时期抄来改的，`env` 键位置/拼法可能有差异——逐个看准再改，`NODE_ENV` 必须放在 `...process.env` 之后；
2. **不许改 `server/index.js` 的发布模式语义**（marker→production 是发布链路的正常设计，见 index.js 注释与 secure-win-release.mjs:204/666）——本单修的是「测试实例免疫」，不是「取消发布模式」；
3. **不许自动删/移 `dist/.release-mode`**（用户可能有正在跑的 release 实例；且这是用户工作区状态，按用户态纪律不代管）；
4. composer-stable-height-check 历史上的 CSS 断言（36px vs 32px）本次为连带失败——修复后若仍失败才是真回归，需单独报统筹，不许顺手改断言迁就；
5. 新 check 的「反向断言」（index.js marker 逻辑仍在）要写稳：匹配注释或结构特征，别写成脆弱的全文本匹配。
