## 1. 问题陈述

`server/core/generation-logger.js:32`：

```js
await appendTaskTextLog(entry).catch(() => {});
```

`appendTaskTextLog` 写的是 `logs/tasks/<date>/<requestId>.txt`（单任务诊断日志）。
它失败时**完全静默**，导致：

- `scripts/verify/local-edit-base-file-check.mjs` 的端到端断言**间歇红**
  （事件进了 `logs/generation.jsonl`，但 txt 不生成）
- 出问题时**无法区分是哪一种原因**

### 1.1 已查明的**三条静默路径**（本单的核心：让它们各自可观测）

| # | 位置 | 静默方式 | 触发条件 |
|---|---|---|---|
| ① | `taskTextLogPath()` L57-62 | `return ""` | `requestId` 为空，或匹配 `/^client_load_\|^client_error_\|^client_rejection_/i` |
| ② | `appendTaskTextLog()` L196 | `if (lines.length === 0) return;` | `taskLogLines(entry)` 返回空数组 |
| ③ | `writeGenerationLog()` L32 | `.catch(() => {})` | `mkdir` / `appendFile` 真抛错（权限、磁盘满、路径非法、并发竞态） |

⚠️ **①②是"按设计不写"，③才是"想写没写成"。当前三者都不可观测，这才是病根。**
⇒ **本单的目标不是"让 txt 一定生成"，而是"没生成时留下可追溯的信号"。**

## 2. 🔴 第一步：先定性，不要盲目改代码

台账已记录一条**高度可疑的干扰因素**：

> 🔴 **含 `spawn` / 自建实例的验证脚本不能并发跑**（各占 `127.0.0.1` 端口）⇒
> 批处理时报**假 FAIL**，且两次跑的失败名单不重叠；**单跑全绿**。
> 批处理 FAIL **必须先单跑定性**。

`local-edit-base-file-check.mjs` 正是**自建实例 + 用 `APP_PORT`** 的脚本（见其 L221
`fetch(http://127.0.0.1:${APP_PORT}/api/client-diagnostic-event)`），且它轮询
**20 次 × 150ms = 3 秒**等文件出现。

⇒ **间歇红很可能是端口冲突 / 实例启动慢，而不是 `appendTaskTextLog` 有 bug。**

**执行动作（必做，结果写进回报）**：


| 观察结果 | 结论 | 后续 |
|---|---|---|
| 5/5 全绿 | **纯环境干扰（端口/时序）**，代码无缺陷 | 只做 §3 的**可观测性**改造，**不动写入逻辑** |
| 有红且**总是同一条断言** | 真缺陷 | 按 §3 改，并定位到 ①②③ 中哪一条 |
| 随机红、无固定断言 | 竞态/时序 | 优先排查 §3.3 的节流与轮询窗口 |

## 3. 改造方案（按顺序做，做完一节验一节）

### 3.1 让 ③（真抛错）可见 —— 核心改造

`writeGenerationLog` L32 改为把错误落到 `runtime-errors.log`：

```js
await appendTaskTextLog(entry).catch((error) => {
  writeRuntimeFaultLog({
    time: new Date().toISOString(),
    ok: false,
    stage: "task-text-log-write-failed",
    requestId: entry?.requestId || null,
    endpoint: entry?.endpoint || null,
    error: String(error?.message || error)
  }).catch(() => {});
});
```

🔴 **四条硬约束**：

1. **绝不让 txt 失败影响主流程** —— `writeGenerationLog` 在关键路径上，
   诊断日志挂掉**绝不能**连带 `/api/generate-outfit` 失败。必须保持 `.catch()` 兜底。
2. `writeRuntimeFaultLog` 定义在**同文件 L211**（`export function` 声明，有提升，无 TDZ）⇒ 可直接调用。
3. **内层也要 `.catch(() => {})`** —— 它自己也写文件，也可能失败，不能制造新的未捕获拒绝。
4. **无循环风险**：`writeRuntimeFaultLog` 不调用 `appendTaskTextLog`（已核对 L211-217）⇒ 不会自激。

### 3.2 让 ①（按设计跳过）可计数 —— 低风险，可选

若 §2 定性为"真缺陷且命中 ①"，在 `taskTextLogPath` 的 `return ""` 前加一个
**一次性聚合计数**（不要每条日志都写文件）：

- 用模块级 `Map` 按 `reason`（`empty-requestId` / `client-prefix`）累加
- 仅在 `process.env.JINGYIN_DEBUG_TASKLOG === "1"` 时 `console.warn` 汇总
- 🔴 **不要在正常路径上写日志文件或抛错** —— ①②是合法设计，改造只为排查

### 3.3 防止故障放大（若 §2 判定为竞态/时序）

若 txt 持续写失败（如磁盘满），§3.1 会疯狂刷 `runtime-errors.log`。
⇒ 加**节流**：模块级计数器，同类错误**最多每 60 秒记 1 条**，超出只累加计数。

同时评估把验证脚本轮询窗口从 `20 × 150ms` 放宽（若 §2 定性为纯慢，而非缺陷）。
