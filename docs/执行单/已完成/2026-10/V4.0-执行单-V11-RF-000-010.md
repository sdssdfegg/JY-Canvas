## 0. 开工前准备（两单共用，必须全部完成）

### P1 · 终端与运行时就位
- **做什么**：在一个终端里把工作目录落在项目根，然后用仓库自带的 Node 运行时执行验证脚本。
- **人工操作要点**：
  - 工作目录必须是项目根 `D:\源码开发\静音AI画板v4.0源码`。**大多数验证脚本用"当前工作目录"当项目根**，在别的目录执行会读不到文件、报出一堆假失败。
  - 用仓库内的 `runtime\node\node.exe`，不依赖系统 PATH（目标机器没装 Node 也能跑，这正是自带运行时的意义）。
  - 不要同时开着占资源的其他程序（验证套件会起多个独立服务实例，资源紧张时进程起不来，表现成一片超时，**那不是真的有问题**）。
- **校验要点**：确认根目录下有 `package.json`（其中 `name` 为 `jingyin-internal-canvas`、`version` 为 `11.0.0`）与 `runtime\node\node.exe`。
- **不通过怎么办**：`node.exe` 缺失 → 先把运行时补回来再继续；否则依赖子进程的那批脚本会全红，本单后面的判定全部失真。

### P2 · 工作区干净度确认
- **做什么**：查看版本控制状态，确认当前没有与本轮无关的未提交改动。
- **人工操作要点**：确认当前分支、最近一次提交、以及待提交清单里有没有你解释不了的改动。
- **校验要点**：待提交清单里**不应**出现 `data/**`、`logs/**`、`tmp/**`、`.codex-artifacts/**`（它们是运行产物，应被忽略）；也不应出现别人正在做的改动。
- **不通过怎么办**：有无法解释的改动 → 先另存或另开分支，**不要在混杂的工作区上开工**（否则回退时不知道该退到哪）。

### P3 · ESLint 可用性（决定「lint 棘轮」是真检查还是空转）
- **做什么**：确认 `node_modules\eslint` 存在。
- **校验要点**：棘轮脚本在找不到 eslint 时会**跳过并报 ok=true**（输出里带 `skipped` 字样）。这种情况下「lint 棘轮不新增」等于**没有被验证**，不能当作通过。
- **不通过怎么办**：eslint 不在 → 先补齐依赖。**在 eslint 缺失的状态下，"AB-2 通过"的结论一律作废。**

### P4 · 浏览器探针可用性（决定 local-edit-base 是否可能因环境变红）
- **做什么**：确认 `%LOCALAPPDATA%\Tabbit\LocalAgent\bin\tabbit-cli.exe` 是否存在。
- **校验要点**：记住这个结论，它是后面区分「代码缺陷」与「环境限制」的唯一依据：
  - **存在** → 该脚本的浏览器段会真跑，它的红必须当成真问题看。
  - **不存在** → 输出里会出现一条名为「浏览器探针未执行」的失败项（脚本对拿不到浏览器回执的处理是**记失败**，不是跳过；这一点与其他脚本的"部分跳过"语义不同）。这条红属于环境，不属于 V11-RF-000 的修复范围。
- **不通过怎么办**：不确定就先跑一次 local-edit-base，直接看 JSON 输出里的 `browser` 字段（形如 `ran` 或 `skipped: 原因`）。

### P5 · 建立「改前基线」（两单共用，必须先做完）
- **做什么**：先完整跑一次验证套件主入口（全套，不加任何筛选），把输出留档；再单独跑一次 `local-edit-base-file-check`，把它的 JSON 留档。

  - 留档要包含完整输出，不要只截图结果行。
- **校验要点**（逐条记下，后面每一步都要跟它比）：
  1. 主入口末行的汇总：`[run-all] N 个脚本：通过 X，失败 Y，用时 Zs` → **N 应为 33**。（若 V11-RF-101 已经先行合入，N 会是 34 —— 该单会新增一个 `state-singleton-check` 脚本；此时以你实际看到的这个数字作为"改前基线"即可，本单不要求它是 33。）

- **不通过怎么办**：若失败脚本远多于预期（例如起服务那批全超时）→ 排查端口占用与内存占用后重跑一次再下结论。**不要在红得不清楚的基线上开工。**

## 2. V11-RF-010 · 统一「服务端源码真相源」

### 步骤 10-7 · 改造 `white-refine-split-check`（本单最关键的一步）
- **人工操作要点**：把这个脚本里"只读 `server\index.js`"的那个常量换成共享模块提供的整体文本；把那条断言从「在 index.js 里找 `/api/save-processed-image` 的注册」改成「在服务端**全部源码**里找」。正则里 `app.` 这个写法保持原样即可（搬家后注册仍形如 `app.post(...)`）。
- **校验要点**：改动**不许削弱**这条断言的判别力 —— 它的存在意义是"证明服务端确实有这个接口"，而不是"证明 index.js 里恰好有这么一行"。
- **不通过怎么办**：改完这条断言永远通过（例如不小心把正则放宽成了只要出现 `/api/save-processed-image` 字样）→ 立即收窄；然后用 10-10 的第 ① 条负向验证来确认判别力。

### 步骤 10-8 · 改造 `routing-check` 的扫描清单（保持逐文件粒度）
- **人工操作要点**：在它的逐文件扫描清单里，**追加** `server\core`、`server\routes`、`server\shared` 下的文件；追加时过滤存在性。**不要**把这份清单合并成一个字符串 —— 这条断言是**按文件**判定的，而且对 `server\channel-config.js` 与 `src\shared\routing.js` 有"旧 token 只允许出现在拒绝名单块内"的特例逻辑。

### 步骤 10-10 · 负向验证（三条，缺一不可）

- **校验要点**：② 的失败输出、①③ 复原后的绿，都要留档贴进提交。
- **不通过怎么办**：① 不通过 → 说明共享模块没被 `white-refine` 真正用上（或路径写错），回查 10-7；③ 崩溃 → 回查 10-2/10-4 的存在性过滤。
