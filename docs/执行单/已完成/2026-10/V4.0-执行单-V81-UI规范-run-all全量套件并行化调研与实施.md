## 1. 需求（背景）

`npm run check` 的全量口径（`run-all --skip-launcher`，50 条）目前**纯串行**执行（`run-all.mjs` 主循环 `for + await runOne`，注释自述"顺序执行便于定位失败点（且部分脚本要占用端口，不能并发）"）。实测参考：2026-10-17 统筹全量复跑总耗时 **739.9s（约 12.3 分钟）**；V79/V80 执行者跑到 30 分钟仍未结束即中止（浏览器类逐支起服务 + tabbit 冷启动）。

统筹复核的体感代价：每单复核都要付一次全量钱，慢到诱导"只跑 --fast 就归档"的侥幸——V70 的 modal-shell 锈蚀、V76 的 lint 欠账，都是这个侥幸的产物。本单目标：**在不放水、不改语义的前提下压短全量墙钟时间**，让"统筹复核跑全量"成为默认动作而不是奢侈动作。

## 3. 改动要求（调研先行，实施须统筹确认方案后落地）

### 3.1 调研（必做，回报附数据）

- 全量跑一次，导出**逐条墙钟耗时表**（run-all 已有 `ms`，`--json` 可直接取）；
- 按「纯源码/逻辑（无端口无浏览器）× 起服务/浏览器 × 撞车组」三分类清单，标出每条的资源占用（端口 / tabbit profile / `data/` 写 / vite cache dir）；
- 给出并行化收益估算：静态类并发（并发度 N=4 与 N=8 两档）× 浏览器类维持串行的总墙钟；以及浏览器类 profile 隔离后的进一步收益（仅估算，本期不实施）。

### 3.2 实施（二选一，回报注明选择与理由）

- **方案 A（保守，推荐默认）**：run-all 增加 `--jobs N` 参数，默认 `1`（行为与现在逐字节一致，CI/钩子零风险）；`N>1` 时仅对**静态类**建并发池，端口/浏览器类仍串行，且撞车组（8888 等）同组内串行。
- **方案 B（激进）**：连浏览器类也按「独立 profile + 独立端口」隔离后并入池。**本期禁止**——profile 隔离方案未经验证，留待后续单；如调研认为 A 已达标，明确建议不做 B。

### 3.3 硬约束

- **判定语义零变化**：任何 check 的通过/失败标准、输出格式、退出码不变；
- **失败归因不劣化**：并发时每条脚本的 stdout/stderr 仍按脚本分别捕获，失败时仍打印末 14 行详情；结果表仍按原 ORDER 顺序呈现（与现在一致）；
- **默认路径不变**：不带 `--jobs` 时与当前串行行为一致（含输出顺序）；
- 不引入新依赖（node 原生 child_process 够用）；不改 `--fast` 子集构成；
- 不碰任何 check 脚本本体（除 3.1 发现的 8888 撞车若在方案 A 内必须规避，也只许在 run-all 的调度层规避，不许改被调度脚本）。

### 3.4 附带的 flake 加固（run-all-check 套件内偶发失败）

调研中须一并定位 §2 末行 flaky 的根因（负载下 spawnSync 子进程异常），给出修法并实施：优先把 run-all-check 内的 `spawnSync` 改为与 run-one 一致的异步 spawn（消灭 EBUSY/信号类窗口），**不得**用"失败就重试" masks。修完后套件内连续两次全量 run-all-check 均一次通过。

## 4. 验收（缺一不可）

1. 不带参数全量跑：**50/50 通过**，且逐条结果顺序/摘要与串行版一致（对照改造前一次全量 JSON）。
2. `--jobs 4` 全量跑：**50/50 通过**，连续 **3 次**无 flaky（浏览器类串行 lane 不得互相污染——用 retouch-frontback 的开关态初值假设验证）。
2b. 串行全量（不带 `--jobs`）连续 **2 次** 50/50，且两次 run-all-check 均一次通过（flake 加固生效；改造前 2026-10-17 曾套件内偶发 1 次）。
3. 墙钟数据：`--jobs 4` 总耗时应显著低于串行（目标 ≤ 串行的 60%；未达标的回报实测分布，由统筹裁决是否接受）。
4. `--fast` 30/30、`check-syntax`、`vite build` EXIT=0、ESLint 0 errors 不受影响；`--jobs` 参数本身过 ESLint。
5. `git diff --stat` 仅 `scripts/verify/run-all.mjs`（+ 调研数据文件如留在 `tmp/` 不入库则不计）。

## 5. 删除与 `.lock` 纪律（硬性）

本单无删除。临时文件删除姿势：`/usr/bin/rm -rf`（绝对路径）｜node `spawnSync("/usr/bin/rm", ...)`｜`CODEBUDDY_SAFE_DELETE_ENABLED=0` 前缀｜PowerShell `Remove-Item -Recurse -Force`。禁止裸 `rm`/`rmdir`/`unlink`/裸 `fs.rmSync`。回报附 `.lock` 增量。

## 统筹修订注记（2026-10-17 上午，执行中修订——LhzhGZ 跑批期间发出，读毕再动后续步骤）

### 修订一：开窄例外，允许修 `scripts/verify/lib/sandbox.mjs` 的清理健壮性（解除 §3.3/§4.5 死锁）

**修订条款（替代 §3.3 末条与 §4.5 中与之冲突的部分）**：

1. **允许修改范围**：`scripts/verify/lib/sandbox.mjs` 一个文件，且仅限提升删除/清理健壮性（重试、退避、锁等待、句柄释放等待等）。**判定语义零变化**：所有 check 的通过标准、断言、输出格式、退出码一律不动；不得借机放宽任何判据。
2. **仍禁止**：改任何 `scripts/verify/*-check.mjs` 本体、改 tabbit profile 共享方式、改 `package.json` 旧 script 语义（§6 其余条款不变）。
3. **§4.5 diff 范围相应修订为**：`scripts/verify/run-all.mjs`（+ §3.4 已授权的 `run-all-check.mjs` spawnSync 加固）+ `scripts/verify/lib/sandbox.mjs`。
4. **验收加强（替代原验收 2 的"连续 3 次"口径）**：沙盒修复落地后，**不手动清 `.codex-artifacts/`**，连续 3 次 `--jobs 4` 全量 50/50——必须证明脆弱性被真正修好，而不是被"跑前清理" masks。若 3 次中仍有残留污染导致的失败，回报如实列出，由统筹裁决是再修还是接受"固定名沙盒改轮换名"方案（轮换名方案涉及各 check 的 SANDBOX_ROOT 常量，须另立专项，本单不实施）。
5. LhzhGZ（清场后的 `--jobs 4`）与随后的 cheap gates / §4.3 墙钟对比按原计划继续，作为修订前的基线数据保留。

### 修订二：验证路由纪律（本单合并后立即生效，后续所有单适用）

用户 2026-10-17 明确要求"发布任务还是要严谨一点，避免资源浪费每次都重复跑重复的验证"。以下纪律自本单合并起写入 `docs/执行单/README.md` 纪律块，V73-V75 及后续单的 §4 验收必须遵守：

1. **每单 §4 验收必须写明"门禁范围"**，按改动面声明跑哪些 check：UI/docs 单默认**不跑**请求级四重（`outfit-intent-request` / `retouch-intent-request` / `pro-wire` / `http-mock`——实测占全量耗时 83%），理由写入单子；全量 50 条仅在触及 `scripts/verify/run-all.mjs`、`lib/sandbox.mjs`、`package.json` 或 program 里程碑（V75 收官）时跑。
2. **统筹不复核全跑**：复核 = 采信执行者回报 + spot-verify（只跑本单触碰的 check 与回报数字有疑的条目）。全量从"每单一次"降为"里程碑一次"。
3. **债务打包立单**：门禁债/流程债同类项打成一单，不按个立；新立单须过"不能搭载进在途单"检验。
4. **base 写"派发日 main"**：不写死 commit hash，执行者免去反复重拉重测。
5. **禁止性条款必须带例外路径**：一刀切式禁令（如本单原 §3.3"不碰 check 脚本"）须写明"辅助库健壮性修复允许 + 条件"，否则迟早逼出额外单——本修订一即为此付的学费。

**起草者自省（记录在案）**：V81 立单的直接诱因之一是统筹复核习惯性全量复跑；若当初先立"验证路由"纪律，UI 单的全量成本早已消解，本单可能不必立。流程自肥的账，记在统筹侧。

### 8.2 实施（§3.2 / §3.3）

**方案 A（保守，已实施）**：`run-all.mjs` 新增 `--jobs N`（默认 1 = 与改造前纯串行逐字节一致，CI/钩子零风险）；N>1 时 `runPooled` 把互不踩共享资源的脚本放进并发池（全局并发度 = jobs），`rootdata` lane 与撞车组 `8888` 各自容量为 1 串行。结果表仍按原 `ORDER` 顺序呈现、失败尾 14 行、退出码、`--json` 格式全不变。未引入新依赖（node 原生 `child_process.spawn`），未改 `--fast` 子集、未改任何 `*‑check.mjs` 本体、`package.json` 旧 script 语义不变。

**本轮补的两处补丁（执行者定位的根因，均在允许范围内）**：

1. **`run-all.mjs` 撞车组未真正生效**（§3.3 要求 8888 必须在调度层规避）：原 `SCHED_RESOURCES = { rootdata: 1 }` 漏了 `group:8888`，导致 `outfit-intent-request`（不在 rootdata lane）可与 `outfit-defer-autosave` 同时占用 8888 → 偶发端口冲突双败。已补 `"group:8888": 1`，与 rootdata 共同兜底。
