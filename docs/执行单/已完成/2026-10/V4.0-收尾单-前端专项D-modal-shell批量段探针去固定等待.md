## 1. 已实锤现状

`scripts/verify/modal-shell-page.jsx` 批量入口段（统筹实测锚点）：

- `:201` `batch.navSwitched = navTo("批量生成");`
- `:202` **`await wait(900);`** ← 固定等待
- `:203` 立即查询 `[".outfitUploadBox", ".outfitUploadZone", ".uploadZone", "section.uploadBox", "section.detailUploadBox"]`
- 后续还有 `:209 wait(1200)`、`:215/222/227 wait(700)`、`:231 wait(1600)`

**问题**：批量生成页是**懒加载**的（vite 产出 `feat-outfit` 独立块）。固定 900ms 在正常机器够用，但在慢加载 / 冷缓存 / 并行会话占用资源时会不足，导致：

```
批量入口：切到批量页并找到上传区  →  foundUploadZone=false
批量入口：能再次打开并应用        →  reopened=undefined closedOnApply=undefined
```

即**"探针跑赢了页面"**，属验证脚本自身的时序脆弱性，不是产品 bug。BUG02 期间这三红正是这种外形，极易与真白屏混淆——**必须消除这种歧义**。

## 2. 目标

把「固定时长等待」改为「等目标就绪」，并在未就绪时给出**可区分的诊断**（而不是 `undefined`）。

## 3. 改动步骤

1. 在 `modal-shell-page.jsx` 内新增一个就绪等待 helper，语义为：轮询查询给定选择器数组，**命中即返回**；超时（建议 15s，与 error-boundary-check 的导航超时口径一致）后返回未命中，并把"等待耗时"和"最终 DOM 快照特征"写入 `facts`。
2. `:202` 的 `await wait(900)` 替换为「等待 §1 中 5 个上传区选择器任一出现」。
3. 后续 `:209 / :215 / :222 / :227 / :231` 同样改为等待**各自的目标条件**（上传后出裁剪按钮 → 等 `button[title="裁剪/补边"]`；打开 → 等 `.cropModal`；取消 → 等 `.cropModal` 消失；应用 → 等 `.cropModal` 消失）。
4. **保留**所有既有字段语义（`navSwitched` / `foundUploadZone` / `cropEntryFound` / `opened` / `layerIsSharedShell` / `closeButtonPresent` / `closedOnCancel` / `refReleasedOnCancel` / `reopened` / `closedOnApply` / 计数类字段）——**不得改名、不得增删断言**。
5. `scripts/verify/modal-shell-check.mjs` 的断言**一条都不许改**（R6：禁改判据/阈值/断言）。只在需要时把新带回的诊断信息拼进 `detail` 字符串（那是展示层，非判据）。
