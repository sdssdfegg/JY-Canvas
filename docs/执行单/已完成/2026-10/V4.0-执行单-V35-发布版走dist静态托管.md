# V4.0-执行单-V35 · 发布版运行时走 dist 静态托管（根除 vite dev server 启动慢）

> 类型：发布工程 / 运行时配置（非 src 重构）｜优先级：高（直接对应"启动进入慢"用户反馈）
> 统筹定案：让发布版启动时静态托管预构建的 `dist`，运行时**彻底不拉起 vite dev server**。

## 0. 背景（为什么做 / 已实证）

- `server/app.js:98-112` 的 `attachFrontend()`：仅当 `process.env.NODE_ENV === "production"` 且 `dist/index.html` 存在时，才走 `hasDiskFrontend` 分支**静态托管预构建产物**；否则走 `else` 分支 `await import("vite")` 拉起 **vite dev server（middleware 模式）**。
- 经全仓 grep 确认：**运行时从未把 `NODE_ENV` 设为 `production`**。`scripts/secure-win-release.mjs:119` 的 `NODE_ENV:"production"` 与 `:163` 的 `"process.env.NODE_ENV":"\"production\""` 都只作用于 **`vite build` 构建期 / 前端包内 define**，不传递给 `node server/index.js` 进程。
- 实证：统筹冒烟时直接 `node server/index.js`（未设 NODE_ENV），日志即出现 `Re-optimizing dependencies because vite config has changed` ⇒ 发布版 exe 走的是同一段代码，**发布产品里一直在跑 vite dev server**。
- `vite.config.js:4-5` 把 `PORT` / `VITE_HMR_PORT` 烤进配置对象 ⇒ 配置哈希随端口变 ⇒ vite 每次都重新预构建依赖 ⇒ 启动进入慢。这正是用户反馈的"启动进入慢"根因（与 verify 套件假失败同源）。

## 1. 目标

发布版启动 `node server/index.js` 时，命中 `hasDiskFrontend` 分支**静态托管 `dist`**，运行时**彻底不拉起 vite dev server** ⇒ 启动快、且端口变化不再触发重预构建。

## 2. 改动（执行者先 grep 确认最新行号，禁止扩大范围）

**核心：让"发布上下文"里的 `server/index.js` 在 `attachFrontend()` 之前把 `NODE_ENV` 设为 `production`，且不影响 `npm run dev`。**

推荐做法（marker 文件，最稳，不依赖 env 传递）：

1. `scripts/secure-win-release.mjs`：在 `vite build` 产出 `dist/` 之后、postject 打包之前，于 `dist/` 内写一个空标记文件（如 `dist/.release-mode`）。
2. `server/index.js` 顶部（`import` 区之后、`attachFrontend()` 调用之前）加：
   ```js
   import { existsSync } from "node:fs";
   import path from "node:path";
   // rootDir 推算：与 server/app.js 保持一致（app.js 里 rootDir 即仓库根）
   const __root = path.resolve(path.dirname(new URL(import.meta.url).pathname), "..");
   if (!process.env.NODE_ENV && existsSync(path.join(__root, "dist", ".release-mode"))) {
     process.env.NODE_ENV = "production";
   }
   ```
   若 `server/app.js` 已导出 `rootDir`，则直接 `import` 复用，不要重复推算。
3. 确认 `release` 包内 `dist/` 完整（`secure-win-release.mjs` 已 build 并拷贝）；`.release-mode` 标记随包发出。

备选（若 postject 入口可注入 env）：在打包入口 shim 里 `process.env.NODE_ENV = "production"` 后 `import("./index.js")`；同样需保证 dev 路径不触发。

## 3. 禁止 / 风险

- **不得为统一而改 `vite.config.js` 业务行为**（尤其不能删 PORT 读取导致 HMR 失效）；本单**零改 `vite.config.js` 与 `src/`**。
- **不得让 `npm run dev` 受影响**：dev 模式下 `dist/.release-mode` 不存在 ⇒ 不置 production ⇒ 仍走 vite dev server（HMR 正常）。执行者需实测确认 `npm run dev` 启动后日志仍有 vite、页面可热更。
- 先 `grep -rn "process.env.NODE_ENV\|NODE_ENV ===\|NODE_ENV ==" server/ scripts/` 确认：除 `server/app.js:99` 外，无其他代码依赖该值且会因置 production 而误伤；若有，先停手报统筹。
- 改动只限 `server/index.js`（+≤6 行）+ `scripts/secure-win-release.mjs`（写标记）；**零新建 src 文件** ⇒ 019 `fileCount` 不划账。

## 4. 验收（门禁，全绿才算数）

- 用**本次发布产物**启动：`netstat` 不应有 vite dev server 监听；日志**不得**出现 `Re-optimizing dependencies` / `VITE ready` / `vite v` 等字样；进程不应 `import("vite")`。
- `curl http://127.0.0.1:<port>/api/health` 返回 `ok:true`；浏览器打开首页，HTML 直接引用 `assets/index-<hash>.js`（非 vite 注入的 `@react-refresh` / `@vite/client`）。
- 启动耗时：同机同端口二次冷启，应**省去依赖预构建**（不再有 30s 级等待）。
- 六道门禁 + 环扫描全绿：019 `ok=true / duplicateCount=0`、`import-path` 0 违规、`check-syntax` 全过、`source-hygiene` dirtyFiles=0、ESLint 0 errors、`cycle-scan` 环=0；`vite build` 通过。
- 回归冒烟：上传 / 生成 / 历史 / 导出等既有功能正常（可交用户实测）。
