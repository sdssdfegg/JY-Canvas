# V4.0-修复单-BUG03：火山（HS）渠道图片编辑 502 与传参对齐

> 类型：修复单 · 分支 `feature/hs-volc-image-edit-fix` · 提交 `a6055ce` → `5452167` → `94e1c2e` → `b5f84c0` → `4862d95` → `ee127fb`
> 归档日期：2026-10-28 · 关联渠道：`hs-seedream-5-0-flash`（label `HS`，provider `volc`，上游模型 `doubao-seedream-5-0-flash-260915`）

## 0. 一句话结论

HS（火山方舟 Seedream 5.0 flash）做换装 / 图片编辑报 `模型或渠道不可用（HTTP 502）`。**502 的根因不在 154 中转站**，而是画板服务端对火山这条线的**请求构造有五处独立错误**；逐层剥开后全部修在画板侧，**154（nginx / new-api / ch30）零改动、计费 $0.12 保持不变**。

## 1. 现象

- 前端用 HS 渠道做图片编辑 / 换装：报 `模型或渠道不可用（HTTP 502）：图片编辑请求被…`。
- 纯文生图（不传图）**正常**；一传图就 502。
- 期间出现"改了代码、重启后端却毫无变化"的假象（见 §3.2/§3.3，两个失效点叠加）。

## 2. 影响面

| 项 | 结论 |
|---|---|
| 154 nginx / new-api / 渠道 ch30 | **未改动**（无路径重写、无渠道类型变更） |
| 计费 | 仍走 ch30 按 **$0.12/张** 扣额（实测 `used_quota` +60000 单位 = $0.12） |
| 其它渠道（香蕉 / GPT / 名创 seedream…） | 不受影响（改动全部限定在 `provider === "volc"` 分支内） |

## 3. 根因：五个独立失效点（逐层剥开）

### 3.1 端点不兼容 —— 火山没有 `/images/edits`
画板多图时全局走 `channelImagePath(hasImages)` → `/images/edits`；火山返回 404 → 外层中继转 502 → 前端归类 `CHANNEL_UNAVAILABLE`。

**实测（正确火山路径，非拼接错误）**：
- `POST https://ark.cn-beijing.volces.com/api/v3/images/edits` → **404**（空响应体）
- `POST .../api/v3/images/generations` + `reference_images` → **200 出图**

⇒ 编辑必须走 `/images/generations`。**由此否决了两套外部建议方案**（方案 A：nginx 把 edits 重写到 `/api/v3/...`；方案 B：new-api 建 AdvancedCustom 映射 edits）——重写后仍打到不存在的端点，且都要动 154。

### 3.2 换装走 `/api/generate-outfit`，且 model 被换成上游名 → provider 丢失
- 换装链路端点不是 `/api/images`，而是 **`/api/generate-outfit`**（`server/routes/outfit.routes.js`）。
- `imageParamsForCandidate` 会先把 `model` 换成**上游模型名** `doubao-seedream-5-0-flash-260915`，而 `ROUTING_CHANNELS` 登记的是 UI 模型名 `doubao-seedream-5-0`；`routingChannelForModel` 是"按 model 过滤渠道列表 → 再匹配 id"，上游名过滤结果为空 ⇒ 返回 `null` ⇒ **`provider` 丢失** ⇒ volc 专用分支（`provider === "volc"`）**不触发** ⇒ 回落通用分支发 `/images/edits`。

### 3.3 上传件是"落盘"的，`file.buffer` 为空 → 分支自弃
- `imageForwardUpload` 用 **`multer.diskStorage`**（`server/core/uploads.js:44-45`）⇒ `file` **只有 `path`、没有 `buffer`**。
- volc 分支原本同步取 `file.buffer` 拼参考图 ⇒ 全空 ⇒ `refs.length === 0` ⇒ **主动放弃 volc 分支** ⇒ 回落 `/images/edits`。
- ⚠️ 早期复现脚本用"带 buffer 的假文件"，掩盖了这个差异（假通过）。

### 3.4 尺寸字段错：`width/height` 应为 `size` 像素串
火山方舟原生认 **`size = "WIDTHxHEIGHT"`**（与已跑通的 volc 文生图分支一致），`width/height` 被**静默忽略**：

| 传法 | 实际输出 |
|---|---|
| `width/height=1536x2304` | 1776×2368（**3:4**）❌ 且同参数多次结果不定（另出 1664×2496 / 2048×2048） |
| `size="1536x2304"` | **1536×2304 严格 2:3** ✅ |

### 3.5 参考图字段错：`reference_images` 应为 `image`，且必须带 `data:` 前缀
对照官方文档（ark.volcengine.com 图片生成 API）：

| 项 | 错 | 对 |
|---|---|---|
| 字段名 | `reference_images` | **`image`**（string \| string[]） |
| 编码 | 裸 base64（去前缀） | **必须带 `data:image/<格式>;base64,` 前缀** |
| 附加参数 | `image_mode` / `reference_strength` | 属"豆包 LAS 数据算子"，方舟不认、被静默忽略 |

**实测对照**（同一人物原图 + "保持人物服装姿势不变，只把背景换成海边"）：
- 旧 → 输出变成**另一位穿夏装的女性**，参考图被忽略 ❌
- 新 → **同一位女性**，咖色羽绒服 / 灰高领 / 黑裤 / 棕靴全一致，背景换海边 ✅

### 3.6 1:1 生成失败 —— `size` 有面积上限
火山 flash 对 `size` 的**面积上限为 4,624,220 像素**（实测 400 原文 `image area must be at most 4624220 pixels`；官方网页写的 4096×4096 是**其它模型**的）。我们 2K 长边 = 2304，`1:1 → 2304×2304 = 5,308,416` 超限 ⇒ 400。其余比例（4:3/3:4、5:4/4:5、2:3、16:9/9:16、21:9）实测全部 200 —— **2K 档只有 1:1 踩线**（同等长边下正方形面积最大）。

## 7. 教训（已同步写入项目记忆）

1. **"改了没生效"先查生效点**：确认请求走哪个 route、该函数是否被调用、入参是什么；不能只看"代码写对了"。
2. **`logs/generation.jsonl` 是金矿**：`forward-outfit-request` / `forward-api-images-request` 记录 `url / requestVariant / requestFormat / requestedModel / requestedChannelId / fileCount`。`format` 带 `-volc` ⟺ `provider === "volc"`；`signed=false` ⟺ URL = baseUrl + variant.path。
3. **复现必须用与生产一致的入参形态**：`diskStorage` 下 `file` 无 `buffer`；用带 buffer 的假文件会假通过。
4. **"接口返回 200" ≠ 参数生效**：参考图这类被静默忽略的参数，必须设计**可视觉判定的对照实验**，不能只看状态码。
5. **新渠道传参对齐"该渠道已跑通分支"的字段风格**（本例：volc 文生图一直用 `size`，新分支却按文档字面写了 `width/height`）——以仓内已跑通代码为准。
6. **验证尺寸是否真生效要量落盘成品**，不要只看请求体。
