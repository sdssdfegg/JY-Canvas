## 1. 背景：为什么会变成"只能统一价"（2026-10-30 实测调研）

### 1.1 调用链路

```
客户/画板 → New API 聚合网关（api.jingyin.online，3001，进程 new-api-custom，SQLite 库 /opt/new-api/data/one-api.db）
              ↓ 渠道 id=8「静音的渠道」base_url=http://127.0.0.1:8792
           jingyin-silent-gpt-image-adapter（8792，配置 provider_families.json）
              ↓ 按请求里的 channelId 分流
           真实上游（LY:47.75.115.179:3018 / LK:api.lk888.ai / 云枢 / vakv / Subdirect …）
```

### 1.2 根因（三条，逐条实测）

1. **收费发生在"还不知道走哪条渠道"之前**。
   客户侧扣费由 New API 的 **`ModelPrice`（按模型名定价）** 决定，实测 `options` 表当前值：
   ```
   ModelPrice = {"nano-banana-pro":0.14, "tt-image-2":0.1, "banana-2":0.12, "tt-image-2.5":0.1,
                 "banana-2.1":0.12, "gpt-image-2":0.1, "doubao-seedream-5-0":0.11,
                 "doubao-seedream-5-0-pro":0.15, "doubao-seedream-5-0-flash-260915":0.12}
   ```
   ⇒ 所有 2.5 渠道客户侧一律按 **0.1** 扣。

2. **New API 看不见我们的渠道划分**。
   `abilities` 表（字段 `group / model / channel_id / enabled / priority / weight / tag`）里，
   `tt-image-2.5` 只有一行：`{'group':'default','model':'tt-image-2.5','channel_id':8,...}`。
   即：11 条 2.5 渠道在 New API 侧**只是同一个 channel(8)**，分流发生在 adapter 内部，New API 无从感知。

3. **New API 没有"渠道级/分组级"倍率**（已全量排查 `options` 表）：
   只有 `ModelRatio / CompletionRatio / ImageRatio / AudioRatio / CacheRatio / CreateCacheRatio`，
   **没有 GroupRatio，也没有渠道倍率字段** ⇒ 无法用"渠道倍率"绕开按模型定价。

### 1.3 现状价格对照（前端显示 vs 客户实际被扣）

前端 `server/channel-config.js` 的 `ROUTING_CHANNELS`（TT2.5 部分，已核准）：

| publicId | 渠道名 | 前端售价 | 客户实际被扣 | 是否隐藏 |
|---|---|---|---|---|
| silent-tt25-line-06 | Origin | 0.10 | 0.1 | 显示 |
| silent-tt25-line-01 | XT-image2-s | 0.10 | 0.1 | 显示 |
| silent-tt25-line-02 | XT-特殊分组 | 0.10 | 0.1 | 显示 |
| silent-tt25-line-03 | XT-default | 0.10 | 0.1 | 显示 |
| silent-tt25-line-08 | vakv | 0.10 | 0.1 | 显示 |
| silent-tt25-line-07 | Subdirect | 0.11 | 0.1 | 显示 |
| silent-tt25-line-11 | **LK-1K** | **0.12** | 0.1 | 显示 |
| silent-tt25-line-10 | **LY满血版** | **0.14** | 0.1 | 显示 |
| silent-tt25-line-05 | 云枢 | 0.10 | — | 已隐藏 |
| silent-tt25-line-04 | BR-default特价 | 0.12 | — | 已隐藏 |

**关键简化**：显示中的 8 条渠道实际只落在 **4 个价格档**（0.10 / 0.11 / 0.12 / 0.14）
⇒ 只需 **4 个对外模型名**，不是 11 个。

## 2. 目标

- **每个渠道按自己的价格独立计费**，前端显示价 = 客户实际被扣价。
- 不改渠道路由行为（adapter 仍靠 `channelId` 分流，现有链路已通、不动）。
- 同价渠道共用同一个对外模型名（模型名数量 = 价格档数量，而非渠道数量）。

---

## 3. 方案：按价格档建"对外模型名"

核心思路：既然 New API **只能按模型名定价**，就让**模型名本身携带价格档信息**。
New API 按模型名收费 = 按渠道价格收费；再用 `model_mapping` 映射回 adapter 认识的 `tt-image-2.5`。

### 3.1 模型名与价格对应表（建议，待确认）

| 对外模型名 | 定价 | 覆盖渠道 | 映射回 adapter 的模型名 |
|---|---|---|---|
| `tt-image-2.5` | 0.10 | Origin / XT-image2-s / XT-特殊分组 / XT-default / vakv | `tt-image-2.5` |
| `tt-image-2.5-p11` | 0.11 | Subdirect | `tt-image-2.5` |
| `tt-image-2.5-p12` | 0.12 | LK-1K | `tt-image-2.5` |
| `tt-image-2.5-p14` | 0.14 | LY满血版 | `tt-image-2.5` |

> 命名采用**价格后缀**（`p11/p12/p14`）而非渠道缩写后缀的理由：同价渠道天然共用、
> 未来调价只需改映射不必改名、模型名数量最少。**若用户偏好渠道缩写（如 `-ly`/`-lk`）则替换命名即可，方案不变。**

### 3.1.1 本轮试点范围（2026-10-30 用户口径：只修 LY + LK）

| 对外模型名 | 定价 | 本轮是否实施 | 覆盖渠道 |
|---|---|---|---|
| `tt-image-2.5` | 0.10 | ✅ 默认档（不动） | 其余所有未映射渠道 |
| `tt-image-2.5-p11` | 0.11 | ⏸️ **本轮暂缓** | Subdirect(line-07)、云枢高质量(line-09)、BR-default特价(line-04) 暂继续走默认档 |
| `tt-image-2.5-p12` | 0.12 | ✅ 本轮实施 | LK-1K(line-11) |
| `tt-image-2.5-p14` | 0.14 | ✅ 本轮实施 | LY满血版(line-10) |

前端 `CHANNEL_PUBLIC_MODEL` 当前仅含 line-10→p14、line-11→p12 两项；后续要补 p11 只需在两处 `routing.js`/`channel-config.js` 加一行并重建。

### 3.2 需要动的三处

| # | 位置 | 改什么 |
|---|---|---|
| A | **New API**（`/opt/new-api/data/one-api.db`） | ① `options.ModelPrice` 增 3 个键（p11/p12/p14）；② `abilities` 表为 3 个新模型名各插一行（均指向 `channel_id=8`）；③ channel 8 的 `model_mapping` 把新名映射回 `tt-image-2.5` |
| B | **adapter**（`/opt/jingyin-silent-gpt-image-adapter/`） | 原则上**不用改**（New API 用 `model_mapping` 映射回 `tt-image-2.5` 即可）。若选了"不用 model_mapping、直接透传新名"的路线，则需 adapter 支持模型名归一化（后缀剥离）——**推荐走 model_mapping 路线，adapter 零改动** |
| C | **前端**（真实源码 `D:/源码开发/静音AI画板v4.0源码`） | 请求构造时，把 `model` 字段由固定 `tt-image-2.5` 改为**按当前 channelId 查表得到的对外模型名**。落点见 §5.3 |

## 4. 执行前必读 / 红线

- **真实源码在 `D:/源码开发/静音AI画板v4.0源码`**（C 盘同目录是空壳，不要改错）。
- 前端构建必须用**项目自带 Node**：`export PATH="$PWD/runtime/node:$PATH"`（v24.9.0），禁用系统 Node。
- **改 `relay.env` 里的 KEY 必须 `systemctl restart jingyin-silent-gpt-image-adapter.service`**；
  adapter 的其它配置（含 pricing/capabilities）**每次请求实时读盘，免重启**。
- **KEY 绝不进源码/前端**，只存 `/etc/jingyin-silent-adapter/relay.env`。
- New API 数据库操作前**先备份**：`cp /opt/new-api/data/one-api.db /opt/new-api/data/one-api.db.bak-<时间戳>`
  （该库历史备份命名惯例 `one-api.db.bak-YYYYMMDD-HHMMSS-原因`，照此执行）。
- 前端两处配置**同源同步**：`server/channel-config.js` 与 `src/shared/routing.js`，只改一处会前后端不一致。
- 门禁脚本一次只跑一个套件（历史上有负载敏感的 flake）。

## 5. 实施步骤

### 5.1 A：New API 侧（在 154 上操作）

1. 备份数据库（见 §4）。
2. 读出现有 `ModelPrice` 并追加 3 键（`tt-image-2.5` 保持 0.10 不变作为默认档）：
   - `tt-image-2.5-p11` = 0.11
   - `tt-image-2.5-p12` = 0.12
   - `tt-image-2.5-p14` = 0.14
   可用 New API 管理接口（登录见下）或只读 SQLite 核对，**写入建议走管理接口而非直接改库**（避免绕过缓存）。
   - 登录：`POST https://api.jingyin.online/api/user/login` `{"username":…,"password":…}`
   - 后续管理请求需带 **`New-Api-User: <user_id>`**（实测 user_id=1，值不匹配会 401）
3. `abilities` 表为 3 个新模型名各插入一行，字段照抄现有 `tt-image-2.5` 行，仅改 `model`：
   `{'group':'default','model':'tt-image-2.5-pXX','channel_id':8,'enabled':1,'priority':81,'weight':100,'tag':'family:lk888-silent;models:tt-image-2,tt-image-2.5,banana-2;route:price_first'}`
4. channel 8 的 `model_mapping` 由 `{}` 改为：
   `{"tt-image-2.5-p11":"tt-image-2.5","tt-image-2.5-p12":"tt-image-2.5","tt-image-2.5-p14":"tt-image-2.5"}`
   （这样 adapter 收到的仍是它认识的 `tt-image-2.5`，**adapter 零改动**）
5. 重启 New API：`systemctl restart new-api-custom`（若走接口则按 New API 缓存策略决定，建议重启以确保生效）。

### 5.2 B：adapter 侧
走 model_mapping 路线 ⇒ **无需改动**。执行完 A 后做一次回归验证（§6）确认旧链路未受影响。

### 5.3 C：前端侧

新增"渠道 → 对外模型名"映射，并在发请求时按渠道选模型名：

1. 在 `server/channel-config.js` 新增导出（示例结构，命名按 §7 确认结果）：
   ```js
   // 渠道 → 对外模型名（价格档）。与 New API 的 ModelPrice 一一对应。
   export const CHANNEL_PUBLIC_MODEL = Object.freeze({
     "tt-image-2.5": {                     // 模型 → 默认对外名
       "silent-tt25-line-07": "tt-image-2.5-p11",
       "silent-tt25-line-11": "tt-image-2.5-p12",
       "silent-tt25-line-10": "tt-image-2.5-p14"
       // 未列出的渠道沿用模型原名 tt-image-2.5（0.10 档）
     }
   });
   export function publicModelForChannel(model, channelId) { … }
   ```
   ⚠️ 必须与 `src/shared/routing.js` **同源同步**（两处都要有，前端兜底用）。
2. 请求构造处（`server/channel.js` 的 `appendRoutingFields` / `buildTextImageBody` 等）
   把写入的 `model` 由 `params.model` 改为 `publicModelForChannel(params.model, params.channelId)`。
   **注意**：`channelId` 必须照常下发（adapter 靠它分流，这条不能动）。
3. `vite build` 重建 dist；浏览器硬刷新验证。

## 6. 验收标准

1. **扣费验证（核心）**：用一个测试令牌分别调用 4 个模型名，核对额度扣减：
   - `tt-image-2.5`（Origin 等）→ 扣 **0.10**
   - `tt-image-2.5-p11`（Subdirect）→ 扣 **0.11**
   - `tt-image-2.5-p12`（LK-1K）→ 扣 **0.12**
   - `tt-image-2.5-p14`（LY满血版）→ 扣 **0.14**
   > 验证方法：调用前后读 New API 该令牌的 `remain_quota` / 用量记录做差值。
2. **路由未受影响**：选 LK-1K 仍走 LK 渠道出图（adapter 日志 `channelId=silent-tt25-line-11` 且 HTTP 200）；
   选 LY 仍走 line-10。
3. **前端显示与实际一致**：画板上选各渠道，界面显示价 = 上一步实测扣费。
4. 回归：`routing-check` / `http-mock-check` / `check-syntax` / `size-ratchet` / `lint-ratchet` 全绿，`vite build` EXIT=0。
5. 未列出的渠道（0.10 档）行为与改动前完全一致。

## 8. 风险与回滚

| 风险 | 影响 | 处置 |
|---|---|---|
| 改 New API 计费表影响存量客户 | 客户扣费变化 | 保留旧名 `tt-image-2.5`=0.10（待确认 #4）；改动前备份数据库 |
| `model_mapping` 配置错误 | adapter 收到不认识的模型名 → 请求失败 | 回滚 channel 8 的 `model_mapping` 为 `{}`；adapter 侧有模型名校验会明确报错，易发现 |
| 前端漏改某处请求构造 | 部分链路仍走旧名 | 全局 grep `params.model` / `fields.model` 逐处核对 |
| New API 重启 | 短暂中断（秒级） | 选低峰操作；服务 `new-api-custom` 有 `Restart=always` |

**回滚步骤**：① 恢复 `one-api.db` 备份（或删掉新增的 3 个 ModelPrice 键 + abilities 行 + 清空 model_mapping）；
② 前端回退 §5.3 的两处改动并重新 build。adapter 全程零改动，无需回滚。
