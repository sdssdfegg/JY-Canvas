## 0. 一句话结论（三选一 · 全文统一）

**结论：对现有架构进行较大改造。**

理由：确定性执行内核（任务状态机 / 幂等键 / 重试退避 / 全局并发闸门 / 启动恢复）已被反复验证、结构健康、应**保留**；但上层的「智能执行」抽象——Agent 层（实为提示词模板）、Skill 层（无动态加载、存在死资产）、Tool 层（**完全缺失标准化工具体系**）、Context 层（多轮编辑历史不回灌）、Model Adapter 层（文本与图像两套并行 HTTP 实现）——存在结构性薄弱，无法支撑长期目标中的「无限画布 / 多图协作 / 连续编辑 / 长任务 / 专业视觉 / 用户可控」。**不推翻内核、不改画布、不重写可用出图链路**，只对上层做系统性改造。

## 1. 架构全貌（实际代码层面）

当前仓库**不存在独立的「智能执行层」概念实体**。所谓的 Agent / Skill / Orchestration 是分散在 `server/features/detail-studio/`、`server/ai-tryon/`、`server/ai-canvas-agent.js`、`src/features/ai-canvas/`、`server/outfit-*.js` 中的一组模块，靠 `postChatCompletion`（纯文本 HTTP 壳）与内部自调 `/api/images`（图像）这两个 Model Adapter 串联。

分层现实（自底向上）：

| 层 | 实际实现 | 是否独立抽象 |
|---|---|---|
| Model Adapter（文本） | `server/core/ai-chat-shared.js:151 postChatCompletion`（仅 `fetch`+`readTextSafely`） | 是，但**过薄** |
| Model Adapter（图像） | `server/routes/images.routes.js:223` 内联 `baseLoop`（候选×变体嵌套循环） | **否**，与文本两套并行实现 |
| Tool | 无注册表/接口；`server/features/detail-studio/generation/*` + `versions/*` 等业务模块直接被路由调用 | **否** |
| Skill | `prompts/detail-studio/**` 静态 `import`；无运行时发现/加载器 | 是定义层面，无运行时机制 |
| Agent | 角色=常量+提示词字符串，同一 `postChatCompletion` 调用 | **否**（见 §2） |
| Orchestration | `generation/orchestrator.js`（仅生成层有）；规划层无编排器，由前端按钮顺序驱动 | 部分 |
| Context | `project.json`（schema v2）为真相源，每次调用确定性重建 | 是（数据层） |
| Quality | 确定性 `checklist.js` + LLM `qc-review.js`（B4） | 是（混合） |

## 2. 六维度实际状况（E1）

### 2.1 Agent —— 不同提示词模拟角色，而非多角色执行

- **没有任何真 Agent**：全仓 `tool_calls`/`function_call` **无运行时调用**（`server/ai-canvas-agent.js:4-6` 注释自陈；字面 2 处命中均在注释，非运行时调用）。所有「角色」都是 `常量 + 提示词字符串 + 同一个 postChatCompletion 调用`。
- detail-studio 规划四步（analyze/director/compile/qc）**不是服务端编排器**，而是四个独立 HTTP 端点（`server/routes/detail-studio.routes.js:249/290/322/358`），由前端钩子 `use-detail-studio-state.js:360-407` 按按钮顺序驱动。**只有生成层有编排器**（`generation/orchestrator.js:78 submitBatch`）。
- ai-canvas 的 `planner`/`prompter` 是 `ROLE_SPEC` 对象里的 `system` 文案（`server/ai-canvas-agent.js:137-155`），串行两次单轮 LLM，**非并发多智能体**。
- ai-tryon 是纯状态机（`state-machine.js:20-34`），**无 LLM、无角色**。

> 判定：是「同一管道里不同提示词模拟角色」，不是「多角色执行」。新增行业/工作区无需新 Agent，但**任何「真正多智能体协作 / 工具调用 / 自主规划」能力目前都不可达**。

### 2.2 Skill —— 静态导入、无运行时加载器；资产消费严重分化

无动态加载器/插件注册表，全部为构建期 ES `import`。逐资产三列对照见本文件 §4 与 `V207-05-架构审查证据索引.md`。要点：

- **真正进模型上下文**：`core/global-lock.js`、`core/prompt-compiler.js`、`prompts/analyze-strategy.js`、`prompts/director-visual.js`、`quality/qc-prompt.js`、`industry/*`（含 7 行业文件）。
- **被确定性代码消费但未注入 LLM**：`core/option-trace.js`、`core/screen-composition.js`、`core/fact-grading.js`、`quality/checklist.js`、`references/copywriting.js`（`scanForbiddenWords`）、`references/methodology.js`（`narrativeSelfCheck`）。
- **仅门禁扫描（SCANNED-ONLY）**：`platform/index.js`、`references/reference-image-roles.js`、`references/case-library.js`。
- **零消费方（DEAD）**：`references/reference-image-guide.md`、`copywriting.js` 的 `CONSUMER_LANGUAGE/COPY_DIRECTIONS/copyHierarchy`、`methodology.js` 的 `NARRATIVE_ARC/INFO_RHYTHM/visualDiversityMethodology`。
- 行业选择数据驱动（`industry/index.js:57 getIndustryStrategy`），**新增行业 = 加数据 + 注册 2~3 处，业务代码不改**——这是好的。但平台规则走旧底座 `PLATFORM_SKILLS`（`prompts/server/detail-skills.js`，八文件禁改清单），新 `platform/index.js` 仅门禁用，**两条路径并存**。
- **缺陷**：① `qc-review.js:31-36` 调 `buildQcUserPrompt` 未传 `industryStrategy` → 行业 `promoBoundaries` 从未进质检模型（走通用兜底）。② `reference-image-roles.js` 与 server 内联常量 `DETAIL_STUDIO_REFERENCE_ROLES`（`project-store.js:23` 引用 `workspace-contract.js`）是**双真相源**，新增角色须同步两处，漂移风险。

### 2.3 Context —— project.json 真相源 + 每次重建；多轮历史不回灌（高风险）

- 结构可靠：每次文本规划请求先 `getDetailStudioProject(id)` 读全量 project，再 `buildAnalyzeContext(project)`（`analyze-strategy.js:74`）确定性重建；按 `id` 隔离（`project-store.js:126-129` 正则白名单），**跨项目污染风险低**。
- 多轮单屏编辑历史（`editThreads[]`、`screenVersions[]` 版本链、上一版图）**仅写不读进提示词**（搜全仓无读取进 prompt 的调用）→ 模型每轮只见最新 `frozenPrompt`，**历史丢失（history-loss 高风险）**。
- `currentPlanRunId`（`project-store.js:248`）**声明但从未赋值** → 「未完成规划续跑」仅设计、未实现。
- 两份 `globalLock` 来源（B2 实时重建 vs 持久化 `planning.globalLock` 供编译）确定性等价，但属漂移隐患。
- `note`（自由创作目标）只存未注入；参考图在文本模型侧仅传元数据（role/label/filename），像素仅生图侧按路径传入。
- 文本提示词**整体无长度护栏**（依赖源头字段限长）。

### 2.4 Tool —— 完全无标准化工具体系（关键缺口）

- 全仓搜索 `defineTool | registerTool | ToolExecutor | createTool | type:"tool"` **零命中**（`server/**`）。不存在统一 Tool 接口/注册表/执行器。
- 现状 = 按特性目录分散的业务模块 + 路由处理器（`store/*`、`generation/*`、`planning/*`、`versions/*`）。每个能力（出图、资产管理、任务 CRUD、版本切换、文件读写）散落在各自模块，靠路由直接调用，**无中间 Tool/Skill 运行时**。
- 出图永远走确定性链路（`local-images-generator.js` 内部自调 `/api/images`，复用全局 5 并发）；Agent 只产出「计划/提示词/动作 JSON」，由服务端 fail-closed 校验后执行。**Agent 不能越权触发出图**——边界清晰，但「Tool」这一层整体上不存在。

### 2.5 Orchestration —— 生成层成熟，规划层无编排器，确定性/LLM 分离清晰

- 生成层编排扎实：`orchestrator.js` 拆分→重试（`classifyError` `task-model.js:51`、`MAX_ATTEMPTS=3`、`computeBackoffMs:84`）、幂等（`idempotencyKey:37`，`submitBatch` 命中账本则 `idempotent_reuse` 不二次扣费）、启动恢复（`recoverOnStartup:284` 把 running 无结果任务标 `needs_confirm`，**不盲目重跑**）。
- ai-tryon 恢复（`recovery.js`）：`classifyInterruptedTask:30` 按 `result_asset_ids`/attempt 证据收敛终态，`advanceToTerminal` **绝不触发上游调用**。
- 确定性业务（compile/freeze/state/persist/retry/idempotency）与 LLM 推理（analyze/director/qc）**分离清晰**，编译零模型（`compile-screen.js:8`「展示==实际==落库三者同源」）。
- 短板：规划四步**无服务端串联**（前端驱动）；长任务进度可视化与用户介入主要在前端；复杂任务拆分只发生在生成层（每屏一任务），无跨批次的「子目标规划」。

### 2.6 Quality —— 确定性规则 + LLM 审查混合，但质检被抽掉行业上下文

- 确定性：`quality/checklist.js` 跑 `scanForbiddenWords`（`copywriting.js`）、`narrativeSelfCheck`（`methodology.js`）等，产出 findings。
- LLM：`qc-review.js` B4 批次，`MAX_AUTO_FIX=1`（一次定向修正 + 再审查上限）。
- **缺陷**：`buildQcUserPrompt` 未收 `industryStrategy`（§2.2①），行业 `promoBoundaries` 不进质检模型——质检主观判定缺行业约束。
- 质量是否「真参与执行闭环」：偏「提示词里让模型自检 + 确定性规则校验」，自动修正仅限于 `MAX_AUTO_FIX=1` 的 blocker 回写，`needsHuman` 交用户。**未验证**是否有端到端「用户反馈→模型改进下一轮」的闭环数据（E4 未验证）。

### C. 无限画布 AI 协作链路（选中对象→提创作要求→理解并工具执行）

**部分实现**（E1）。已实现：指令→结构化动作清单（单轮 JSON 规划 `server/ai-canvas-agent.js:225`）+ 双角色串行（planner→prompter `ai-canvas-orchestrator.js:26`）+ 前端 fail-closed 白名单应用（`src/features/ai-canvas/ai-canvas-agent.js:78-179`）+ 拓扑快照（`buildCanvasSnapshot`）。

**关键缺口（NOT-IMPLEMENTED）**：
- 选中集未传给 Agent：store 仅单数 `selectedNodeId`（`ai-canvas-store.js:200`），`runAgentPipeline` 取**整张画布**（`orchestrator.js:39-40`）。
- 图像理解缺失：快照仅 `hasImage: Boolean`（`ai-canvas-agent.js:52`），无 URL/像素/vision。
- Agent 被显式禁止触发生图（`server/ai-canvas-agent.js:101`：「不要自动触发生成」），只产结构动作。
- 语义图像关系仅靠用户连线 + 硬编码「图1/图2」文案（`server/ai-canvas-agent.js:100`）。
- 未复用 detail-studio 规划流水线（自建极简 planner）。

### D. 服装换装链路（上传图→调模型→传参考图→保存→后续修改）

- 主生成走 `server/routes/outfit.routes.js:138 /api/generate-outfit`，内联 `baseLoop`（`fetch` over `channel.js` 候选），**未用 postChatCompletion、未走 ai-tryon 的 generateTryOn**。
- `outfit-skill.js` 是 16 行转发壳（`server/outfit-skill.js:1-15`），真相源 `prompts/server/outfit-skill.js` **完全独立**于 detail-studio skill 系统（无任何 import 交集）。
- 三个 AI 分析模块（master-fit/pose/quality）各自重写 `for baseUrl × mode` 循环（`outfit-master-fit-ai.js:274`、`outfit-pose-ai.js:180`、`outfit-quality-ai.js:214`）——**复制粘贴，非参数化工具**。
- ai-tryon `execution.js:486-498` 的 `analyzeInputs/postProcess/evaluateResult` 是 `NotImplementedError` 桩。
- **结论**：新增复杂换装能力 = 再写一份 AI 调用模块 + 专属路由，**当前架构不支持「仅声明即可接入」**。
- 参考图处理口径不一致：生成路径默认只吃图1+图2（`outfit.routes.js:217-225` 仅当 prompt 显式提「图3」才保留第 3 张），质检路径显式传参考图。
